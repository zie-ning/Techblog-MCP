# 기술블로그 사례 검색 MCP 서버 기획

## 개요

코딩 에이전트가 개발 중에 국내 기업의 실제 해결 사례를 참고해 설계 판단을 하도록 돕는 사례 검색 MCP 서버.
국내 IT 기업 기술 블로그를 수집해 **문제 상황 / 해결 방법 / 성능·운영 포인트**(+ 글에 명시된 버린 대안)로 구조화하고, Claude Code·Cursor 같은 코딩 에이전트가 MCP 도구로 호출해 비슷한 사례를 받아보게 한다. 사용자가 검색하러 오는 게 아니라, 개발하는 곳으로 사례가 찾아가는 구조다.

## 문제 정의

코딩 에이전트는 설계 판단을 일반론으로 하고, 좋은 실무 사례는 흩어져 있어 개발 도중에 찾기 어렵다.

- **에이전트의 근거 부족**: "선착순 쿠폰 동시성" 같은 문제에 트래픽 규모나 트레이드오프 없이 교과서적인 답을 낸다. "A사는 X를 썼다" 같은 사례를 지어낼 위험도 있다.
- **사례의 분산**: 좋은 사례는 기업 블로그마다 흩어져 있고, 블로그 자체 검색은 제목 수준이며, 구글 검색에는 SEO용 짜깁기 글이 섞인다.
- **모르는 걸 모름**: 비슷한 문제를 누가 풀었는지 모르면 찾아볼 생각조차 못 한다. 물어보는 챗봇(pull)보다 개발 흐름 안에서 제시되는 방식(push)이 필요하다.

## 차별점

답변을 만드는 LLM은 같으므로, 차이는 검색과 데이터 구조에서만 난다. 사례·집계형 질문에서는 이기고, 개념 질문과 DB 밖 주제에서는 진다.

| 질문 유형 | LLM 단독 | 웹검색 LLM | 이 서비스 |
| --- | --- | --- | --- |
| 개념 ("Redis 분산락 원리") | 충분함 | 충분함 | 비슷하거나 열세 |
| 사례 ("쿠폰 동시성 어떻게 풀었나") | 지어낼 위험 | 2~3개 사례 | 더 많은 사례를 구조로 비교 |
| 집계 ("Kafka 쓰는 국내 회사") | 못함 | 부정확 | 확실히 우위 |
| DB에 없는 주제 | 답은 함 | 잘함 | 못함 |

핵심 강점은 세 가지다.

- **구조화된 사례 데이터**: 문제 상황·해결 방법·성능/운영 포인트로 정리하고, 글에 명시된 경우 버린 대안까지 담아 에이전트가 바로 설계 판단에 쓸 수 있다. 기술·문제 유형·버린 대안별 집계도 제공한다.
- **출처 품질**: 기업 기술 블로그만 사용하고 모든 사례에 원문 링크와 근거 발췌를 붙인다.
- **개발 흐름 안 제공**: 검색 1회로 빠르고 싸게, 에이전트가 필요할 때 직접 호출한다.

챗봇 자체는 웹검색 LLM과 큰 차이가 없으므로 핵심 가치로 내세우지 않는다.

### 유사 서비스: velopers.kr

국내 기업 기술 블로그 155곳을 모아 AI로 요약하는 웹 서비스. 글 유형에 따라 "문제 상황 / 원인 분석 / 해결 방법" 또는 "핵심 내용 / 적용해볼 점"으로 요약하고 기술 태그를 붙인다. 이 프로젝트의 유형별 구조는 이 방식을 참고했다.

| | velopers.kr | 이 서비스 |
| --- | --- | --- |
| 사용자 | 사람이 사이트에 와서 읽음 (pull) | 코딩 에이전트가 개발 중에 호출 (push) |
| 제공 방식 | 웹 목록·검색 | MCP 도구 (검색, 상세, 집계) |
| 집계 | 태그별 글 수 | 기술·문제 유형·버린 대안별 사례 수와 회사 수 |
| 근거 | 요약 | 요약 + 필드별 원문 발췌 (원문 존재 여부 자동 검증) |

### 구조화(추출)

| 항목 | 결정 |
| --- | --- |
| 추출 LLM (M3 확정) | OpenAI API, **`gpt-5.6-luna` (reasoning effort medium)**. M3에서 같은 프롬프트(v4)로 후보 6개(gpt-5-mini medium·low·high, gpt-5.6-luna, gpt-5.4-mini, gpt-5.6-terra)를 파일럿 80편에 추출하고 정답 24편으로 채점해 정함. luna는 전체 1,262편 추정 비용이 $5.3(gpt-5-mini $17.4, 상위 모델 terra $48.7)으로 가장 싸면서 품질은 terra와 비슷함: 추출 여부 정확 일치 100%, 완결성 78%(mini 61%), 도메인 정밀도/재현율 94%/96%, 충실성 4.89, 분할 4.62. gpt-5-mini가 프롬프트를 고쳐도 틀리던 분류 기준(조직 문화 글, 도구 장려 제도 글, 개념 글, 발표 소개 글 제외)을 모두 지킴. 같은 설정 2회 실행에서 gpt-5-mini는 추출 여부 일치 92% ↔ 79%, 분할 4.39 ↔ 3.62로 흔들렸지만 luna는 100% ↔ 100%, 4.62 ↔ 4.44로 안정적. 근거: [eval/reports/eval-step7-models.md](../eval/reports/eval-step7-models.md), [eval/reports/eval-stability.md](../eval/reports/eval-stability.md) |
| 항목 구조 | **문제 상황 / 해결 방법 / 성능·운영 포인트** 3포인트가 뼈대. 트래픽 규모는 별도 필드 없이 문제 상황 안에 원문 표현대로 서술(M3: 원문에 규모·제약 수치가 있으면 반드시 넣도록 프롬프트 강화. 정답셋 `key_facts` 포함률로 재고, 부족하면 M3 마감 전에 별도 필드 검토). 성능·운영 포인트에는 적용 후 결과를 먼저, 운영 주의점을 뒤에 담음. 버린 대안은 글에 명시된 경우에만 추출하고 없으면 비워 둠. 해결 방법만 필수이고, 팁·활용 경험 글은 문제 상황이 비어 있을 수 있음 |
| 사례·인사이트 구분 폐지 (M3) | 처음에는 사례형(문제 상황 / 해결 방법 / 성능·운영 포인트)과 인사이트형(핵심 내용 / 적용해볼 점)을 나눴으나, M3 정답셋 검수 중 **추출/제외만 판단**하고 구조를 하나로 합치기로 함. 이유: 둘의 경계가 자주 갈림(정답 17편 중 5편이 경계 글), 추출 모델도 같은 프롬프트에서 실행마다 사례 4개 ↔ 인사이트 1개를 오감(코틀린 팁 모음), 사람마다 판단이 갈리는 구분을 `kind` 필터로 쓰면 필터 결과도 믿기 어려움. 구분이 하던 일은 이렇게 옮김: 팁 모음을 잘게 쪼개지 않는 규칙 → 항목 나누기 규칙, 근거의 세기 → 판정 대신 **성능·운영 포인트(적용 결과)가 원문에 있는지**를 카드와 집계에 표시, `kind` 필터 → 제거. 이전 기록은 읽을 때 사례·인사이트를 추출로 바꾸고 인사이트의 핵심 내용·적용해볼 점을 해결 방법으로 옮김 |
| 단위 | 1글 = N항목 (독립적인 문제-해법 쌍마다 하나, 같은 문제의 단계적 해결은 한 항목). 팁 모음·도구 활용 경험 글은 1항목 |
| 분류 체계 | 2축 고정 분류 + 자유 태그. **문제 유형**(무슨 문제를 풀었나)과 **도메인**(어떤 영역에서 일어났나)을 별도 필드로 두어 "LLM·AI 도메인의 비용 절감 사례"처럼 교차 검색 가능. 목록은 초안을 만들고 파일럿 추출 후 조정 |
| 분류 목록 조정 기준 (M3) | ① 한 분류가 항목의 25%를 넘으면 나누기 검토 ② 파일럿과 정답셋 모두에서 0건이고 다른 분류와 뜻이 겹치면 합치기 검토 ③ 정답셋에서 일치율이 낮은 분류 쌍은 정의 문구 보강. baseline의 "개발 생산성"(23%)·"사내 플랫폼·개발 도구"(40%) 쏠림은 대상이 아닌 문화·팁 글이 들어온 영향이 커서, 분류 기준을 고친 v2 결과로 판단. **v3 결과로 내린 결정**: 목록은 바꾸지 않는다. 도메인 "사내 플랫폼·개발 도구"(39%)는 서비스 영역이 있는 인프라 작업(호텔 검색, 메신저 서버 등)이 잘못 들어온 영향이 커서 "서비스 영역이 있으면 그 도메인, 개발 도구·사내 공통 플랫폼 자체가 대상일 때만 사내 플랫폼" 기준을 정의와 프롬프트에 넣고, 정답셋·모델 비교에서 다시 잰다. 문제 유형 "개발 생산성"(21%)은 기준 미만이라 유지하고 정의를 "코드 작성 방식·언어 기능 활용, 리팩터링, 빌드·개발 환경, 개발 도구 도입(AI 코딩 도구 포함)"으로 좁힌다 (협업 방식은 대상 글에서 제외됐으므로 뺌). "AI 활용 개발" 문제 유형 신설은 하지 않음. **M3 마감 결정**: 목록(문제 유형 20개, 도메인 10개)은 그대로 확정. 다중 선택 전환과 luna 모델로 "개발 생산성"(항목 대비 36%)·"사내 플랫폼·개발 도구"(37%) 쏠림이 줄었고, 0건 분류는 표본 크기 탓으로 봄. 정답셋 라벨링에서 나온 공백 후보 2개(JVM·GC 성능 튜닝, 검색 품질·정확도)와 도메인 축의 "LLM·AI"·"사내 플랫폼·개발 도구" 성격 문제는 M4 전체 추출 결과로 검토. **M4 표본 결정** (블로그당 25편 + M1 20편, 항목 250개): 문제 유형 **"검색·추천·모델 품질"을 추가해 21개**로 한다. 검색 정확도·리랭킹·추천 모델·LLM 품질 평가 글 약 10개 항목이 맞는 유형이 없어 "DB 성능·쿼리 최적화"·"데이터 파이프라인"으로 흩어졌고, 문제 유형이 비어 나온 항목도 생겨서. JVM·GC 튜닝은 주제인 글이 3편 정도(1~2%)라 신설하지 않고 기존 유형과 기술 태그로 찾는다. 도메인 축은 그대로 둔다: "LLM·AI"가 "AI가 제품"과 "AI가 도구"(32개 중 17개가 "사내 플랫폼·개발 도구"와 함께 붙음) 두 의미로 쓰이지만 다중 선택이라 어느 쪽으로 검색해도 찾히고, 집계를 깔끔하게 하려고 검색 정확도를 낮추지 않는다는 "도구 우선순위" 원칙에 따름 |
| 분류 개수 (M3 변경) | **문제 유형 1~3개, 도메인 1~2개를 순서 없이 다중 선택**한다. "범용"은 다른 도메인이 없을 때만. 검색 필터는 항목의 값 중 하나라도 맞으면 찾고, 집계는 해당하는 값마다 센다(합계가 전체보다 클 수 있음을 결과에 표시). 처음에는 주 문제 유형 1개 + 보조 최대 2개, 도메인 1개였으나 M3 정답셋에서 항목 24개 중 문제 유형 17개(71%), 도메인 15개(63%)가 "하나만 고르면 갈리지만 둘 다 맞는" 경우여서 바꿈(예: 로그 플랫폼 재설계는 관측성이면서 비용 절감, 사내 AI 플랫폼은 사내 플랫폼이면서 LLM·AI). 주 유형은 집계를 중복 없이 세려고 둔 것이었는데, 아래 "도구 우선순위" 원칙에 따라 집계 편의보다 검색 정확도를 우선함. 과다 태깅은 개수 상한, "직접 해결한 것만" 규칙, 평가의 정밀도로 막음. 도메인 겹침의 근본 원인("LLM·AI"·"사내 플랫폼·개발 도구"가 서비스 영역이라기보다 기술 분야·대상 성격)은 M4 분류 검토에서 봄 |
| AI 분류 | 도메인 축에 "LLM·AI" 하나로 두고, 파일럿에서 글이 많이 모이면 세분화 (후보: LLM 애플리케이션 / AI 에이전트·워크플로 자동화 / AI 코딩 도구 도입 / LLM 인프라·운영) |
| 자동화 | AI와 무관한 사내 봇, 운영 스크립트 등은 문제 유형 "업무·운영 자동화"로 분류 |
| 기술명 정규화 | 기술 사전(표준 이름 + 별칭) + LLM 보조. 사전에 없는 이름은 리포트로 뽑아 검토 후 사전에 추가. technologies에는 제품·라이브러리·프레임워크·서비스 이름만 넣고 클래스·메서드명, 일반 개념, 사내 명칭, 버전 표기는 넣지 않음(M3 파일럿에서 미등록 이름 380종 중 상당수가 이런 값). **M4 보강 기준** (사용자 결정): 전체 추출에서 3회 이상 나온 미등록 이름을 추가하고, 표기만 다른 이름은 빈도와 상관없이 별칭으로 묶는다. 플랫폼·언어(Android, iOS, C++)와 프로토콜·표준(SSE, WebSocket, TLS, OpenAPI)은 넣고, 브라우저 API(Web Worker, WebView, Canvas API), 일반 개념·서비스명(LLM, 카카오톡, PPO, PCIe), 사내 기술(Kanana 계열, Central Dogma, Athenz, es-toolkit)은 넣지 않는다. 대소문자만 다른 다른 기술(Yarn 패키지 매니저 / Hadoop YARN / YaRN)은 사전이 대소문자를 무시해 구분할 수 없으므로 넣지 않는다. 사전에 없는 이름도 원래 이름이 전문 검색 색인에 들어가므로 검색은 되고, 기술 필터와 집계에서만 빠진다 |
| 기술 사전 구조 (M3) | 항목마다 **종류(category)** 와 **상위 기술(parent)** 을 둔다. 종류는 집계에서 모니터링 도구가 메시지 큐와 섞이는 문제(M1 시나리오 4)를, 상위 기술은 Amazon MSK가 Kafka와 따로 집계되는 문제를 풀기 위함. M3에서 형식·로딩 코드와 기존 항목의 종류를 채우고, 사전 대량 보강은 M4, 서버 `aggregate` 필터 반영은 M4 이후 |
| 버린 대안 | 글에 명시된 경우에만: 정규화된 대안명 + 버린 이유 + 근거 발췌 (집계 가능하도록 대안명도 사전으로 정규화). **M3에서 유형 추가**: `기술`(제품·라이브러리) / `설계 방식`(Outbox 패턴, 비관적 락 등). `aggregate`의 버린 대안 집계는 `기술`만 세고, 설계 방식은 `get_details`에 보여 줌. 이름은 짧은 명사구로 쓰고 진행 방식(리허설 순서, 회의 방식 등)은 넣지 않음. M3 파일럿에서 버린 대안 75개 중 사전에 있는 이름이 3개뿐이고 나머지가 긴 문장형 설계·진행 방식이어서 나온 결정 |
| 원문 정책 | 필드별 짧은 근거 발췌(1~2문장) + 원문 링크만 배포. 원문 전체는 로컬 캐시에만 두고 배포하지 않음. 경계는 **배포**다: 처리를 위해 외부 서비스로 보내는 것(추출용 OpenAI API, 평가·관측용 LangSmith 비공개 워크스페이스)은 허용하고, 원문 전체가 보이는 트레이스 공개 링크·화면 캡처를 공개하는 것은 배포로 보아 하지 않음 |
| 발췌 검증 | 발췌문이 원문에 실제로 존재하는지 코드로 자동 검사해 LLM이 지어낸 내용을 걸러냄 |
| 정답셋 | 추출 평가용 20~30편은 Claude Code 세션에서 초안을 만들고 직접 원문과 대조해 검수 (비교 대상인 OpenAI 모델과 계열이 달라 특정 후보 쪽으로 기울지 않게 함). 검색 평가용 질문 30개 |
| 추출 평가 | 자동 지표(분류 일치율, 발췌의 원문 존재율, 원문에 없는 버린 대안 비율) + 요약 품질은 LLM 채점(OpenAI API 스크립트, 채점 기준 프롬프트 고정) + 채점 결과 일부를 Claude Code 세션이 원문·추출 결과와 대조해 채점을 믿을 만한지 확인(M3 사용자 결정: 사람이 채점 결과를 검수하는 단계는 두지 않음). 채점 항목과 기준은 [추출평가.md](추출평가.md) |

| 평가·관측 도구 (M3) | **LangSmith**. 추출 과정(분류 → 구조화 → 재시도)을 원문 포함으로 트레이싱하고, 파일럿·정답셋·실패 사례 회귀셋을 Dataset으로, 모델·프롬프트 버전별 추출을 Experiment로 관리하며, 채점기 검증용 사람 검수는 Annotation queue에서 함. 도입 이유: 실패 트레이스 확인 → Playground에서 프롬프트 수정 → 회귀셋 확인으로 프롬프트 개선 주기를 짧게 하고, 원문을 옆에 둔 검수 화면을 직접 만들지 않기 위함. | 발췌 검증 실패 처리 (M3에서 현행 유지로 확정) | 공백·줄바꿈·따옴표 모양·대소문자·마크다운 강조 차이와 `...` 중간 생략만 허용하고 나머지는 불일치로 봄. 여러 줄 발췌는 떨어진 문장을 이어 붙인 것으로 보고 줄마다 원문에 있는지 검사. 실패 발췌가 있으면 실패 목록을 알려 주고 **한 번 다시 구조화**한 뒤, 두 시도 중 검증을 통과한 내용이 더 많은 쪽을 씀(재시도가 더 나쁠 때가 있음). 그래도 실패한 항목은 버리고, 해결 방법이 비면 그 항목을 통째로 버림(M3에서 문제 상황은 필수에서 뺌: 팁·활용 경험 글은 문제 상황이 없을 수 있음). 버린 발췌는 글별 기록에 남김. **M3 완화 실험 결과 현행 유지**(사용자 결정): 떨어진 문장을 한 줄로 이은 발췌까지 허용하는 문장 단위 검증은 baseline에서 탈락 50개 중 19개를 살렸지만, 프롬프트에 "떨어진 문장을 잇지 말라"를 넣은 v4에서는 0개였고, 이어 붙인 문장이 맥락을 바꾸는 위험이 있어 채택하지 않음. 남은 탈락은 바꿔 쓴 문장·코드 블록 등이라 재시도로 처리 ([eval/reports/evidence-relax.md](../eval/reports/evidence-relax.md)) |

| 기술명 정규화 규칙 | 대소문자·공백·`-_.` 차이 무시. 그대로 없으면 괄호 설명(`OGG(Oracle GoldenGate)`는 괄호 안도 후보)과 끝의 버전 번호(`RabbitMQ 3.12.14`)를 떼고 다시 찾음. 모델 버전은 제품군으로 묶음(`Claude 3.5 Sonnet` → Claude) |
| 버린 대안 이름 | 사전으로 정규화하되, 결과가 그 사례에서 쓴 기술과 같으면 원래 이름을 유지. "Claude 3 Haiku를 버리고 Claude 3.5 Sonnet을 씀"이 "Claude를 버렸다"로 기록되는 모순을 막기 위함 |
| 카드 요약 줄 | 문제 상황·해결 방법의 첫 항목이 `search` 카드에 쓰이므로, 해결 방법 첫 항목은 **최종 채택한** 해결책이어야 함을 프롬프트와 스키마 설명에 명시 (M1 사용 중 버린 대안이 카드에 해결 방법으로 나온 문제에서 나온 결정) |

### 검색

| 항목 | 결정 |
| --- | --- |
| 방식 | 형태소 기반 BM25 + 구조화 필터(문제 유형, 도메인, 기술, 유형)로 시작 |
| 엔진 | SQLite FTS5. 형태소 분석한 텍스트를 필드별로 색인하고 `bm25()` 가중치로 필드 중요도 조절, 필터·집계는 SQL |
| 임베딩 | **M5 결정: 도입하지 않고 임베딩 없이 검색 성능을 최대한 올린 뒤, 한계가 보이면 다시 검토한다** (사용자 결정). M5 하이브리드 실험에서 로컬 모델(MiniLM)은 BM25 + 관련도 기준 대비 Recall@5 +0.06에 그쳤고 설치 부담(패키지 약 70MB, 모델 0.22GB, 로딩 약 5초)이 있었다. OpenAI large와 결합하면 Recall@5가 0.551에서 0.761로 크게 올랐지만 검색어 임베딩에 사용자 키·외부 전송·네트워크가 필요하다. 다시 검토할 때 첫 후보는 **사용자 본인의 OpenAI 키가 있을 때만 하이브리드로 동작하는 선택 기능**이다(키가 없으면 BM25). 이 경우 `search`의 외부 통신 없음 표시(`open_world_hint`)를 바꿔야 한다. 수치는 [milestones/M5.md](milestones/M5.md#실험-결과) |
| 형태소 분석 | kiwipiepy로 명사·외국어·숫자·어근·동사/형용사 어간만 남김. 색인과 검색이 같은 함수(`techblog_mcp.search.analyzer`)를 씀. **M5 결정: 사용자 사전**(46단어)을 넣어 외래어 기술 용어가 조각나거나(시그널링 → 시그널 + 링), 같은 단어가 문장 안과 단독 검색어에서 다르게 잘리는 것(동시성 → 동시, 제로트러스트 → 제로 + 트러스트)을 막는다 (사용자 결정) |
| 문서 확장 | **M5 결정: 도입** (사용자 결정). 항목마다 LLM(`gpt-5.6-luna`, low)이 예상 검색어 5개와 본문에 없는 다른 표기·동의어(최대 10개)를 만들어 `data/expansions.jsonl`(커밋)에 두고 `expansion` FTS 열(가중치 2)로 색인한다. 추출과 **별도 파일·별도 단계**(`pipeline.expand`)로 두어 추출 프롬프트를 건드리지 않고, 항목 내용이나 지시문이 바뀐 것만 다시 만든다 (사용자 결정). 전체 생성 비용 약 $0.54. 카드·상세에는 보여 주지 않는 검색 보조 정보라 발췌 검증 대상이 아니다. M5 E7에서 IDF 50% 기준과 함께 Recall@5 0.489 → 0.569, 무관 비율 35% → 29% |
| 질의 재작성 | **M5 결정: 에이전트가 하도록 도구 설명으로 안내** (사용자 결정). 검색어를 한 주제의 짧은 명사구로 쓰고, 여러 하위 주제를 묶은 요구는 나눠 여러 번 검색하라고 `search` 설명·prompt·"결과 없음" 안내에 적었다. 서버 비용은 없다. M5 E8·E9에서 긴 검색어 약점(관련도 기준에 걸려 0건)이 크게 줄었다(최종 설정에서 Recall@5 0.589 → 0.627). 다만 짧은 검색어는 없는 주제에서 우연히 기준을 넘을 수 있다 |
| 검색어 매칭 | 검색어 토큰을 OR로 묶어 BM25 순위를 매긴 뒤 관련도 기준(아래 "결과 수 결정")으로 거른다. 검색어 속 기술 별칭은 표준 이름 토큰도 추가(예: "카프카" → kafka). 색인에는 요약과 근거 발췌를 함께 넣어 원문 표현으로도 찾히게 함 |
| 필드 가중치 | 제목 1.5, 문제 상황 3, 해결 방법 2, 성능·운영 1, 버린 대안 1, 키워드 2, 확장 2. M5 E2에서 조합에 따른 차이가 질문 몇 개 수준(±0.03)이라 기존 값을 유지하고 확장 열만 E7 결과로 정했다 |
| 글 묶기 | **M5 결정: 하지 않음** (사용자 결정). 같은 글의 항목을 글 점수로 묶어 올리면 한 글의 하위 항목이 상위를 차지해 다른 글이 밀려났다(E4) |
| 기술 필터 | 여러 기술을 주면 **하나라도** 쓴 항목을 찾음(OR). 에이전트가 기술을 많이 넣어도 결과가 0건이 되지 않게 하기 위함 |
| 분류 정의 위치 | `src/techblog_mcp/taxonomy/`(TOML). 서버가 enum과 기술 정규화에 런타임으로 써야 해서 설치 패키지 안에 두고, 파이프라인은 `techblog_mcp.taxonomy`를 import함 |

### MCP 인터페이스

| 도구 | 용도 | 반환 |
| --- | --- | --- |
| `search` | "비슷한 사례나 참고할 글 있어?" | 항목을 검색해 관련도 기준을 넘은 항목만 관련도 순 요약 카드로 반환. 최대 10건 |
| `get_details` | "그거 자세히 보여줘" | 항목의 전체 필드, 근거 발췌, 원문 링크 |

#### 공통 원칙

- **도구 우선순위 (M3 결정)**: 이 서버의 핵심은 `search`다. 코딩 에이전트에 비슷한 사례를 정확히 찾아 주는 것이 프로젝트의 주된 역할이고, `get_details`는 그 결과를 여는 도구, `aggregate`는 여러 회사의 선택을 비교할 때 쓰는 **보조 도구**로 중요도가 가장 낮다. 데이터 구조·분류·색인을 설계할 때 집계를 깔끔하게 만들려고 `search`의 검색 정확도를 낮추는 선택(예: 집계 중복을 피하려고 분류를 하나만 고르게 강제)은 하지 않는다. 둘이 부딪히면 `search`를 우선하고, 집계 쪽은 결과 표시(예: "건수 합이 전체보다 클 수 있음")로 보완한다
- **결과 형식**: JSON이 아닌 읽기 쉬운 텍스트. 토큰이 적고 에이전트가 답변에 바로 인용하기 쉬움
- **필터 값**: 문제 유형(21개), 도메인(10개)은 입력 스키마의 선택지 목록(`enum`)으로 제공해 에이전트가 정확한 값을 고르게 함. 선택지는 추출에 쓰는 분류 정의 파일에서 자동 생성해 항상 일치시킴. 기술은 종류가 많아 자유 입력으로 받고 서버가 기술 사전으로 정규화함 (예: "카프카" → Kafka)
- **회사·날짜 필터 없음**: 개발 흐름에서 회사나 날짜로 좁혀 찾을 일이 드물고, 데이터가 이미 최근 3년치라 날짜 필터의 효과가 작음. 파라미터가 적을수록 에이전트가 헷갈리지 않음. 대신 회사 이름을 검색 색인에 넣어 "토스 Kafka"처럼 검색어로 찾을 수 있게 하고, 카드에 발행일을 보여 에이전트가 오래된 글을 감안하게 함
- **사전에 없는 기술**: 필터에서 제외하고 그 사실과 비슷한 기술을 결과에 알려 줌
- **결과가 없거나 적을 때**: "이 주제는 사례가 N건뿐"이라고 명확히 알려 에이전트가 사례를 지어내지 않게 함

##### 결과 수 결정 (M5 구현)

| 항목 | 결정 |
| --- | --- |
| `limit` 파라미터 | **제거**. 에이전트는 결과를 보기 전에 몇 건이 적당한지 판단할 근거가 없어 값이 임의적임 (M1 테스트에서 8, 6을 임의로 지정). 파라미터가 적을수록 에이전트가 덜 헷갈린다는 원칙과도 맞음 |
| 반환 방식 | 서버가 **관련도 기준을 넘는 항목만 최대 10건** 반환. 현재는 검색어 단어 하나만 맞아도 후보가 되고 limit까지 채우므로 무관한 글이 섞임 |
| 구현 시점 | M5. limit만 먼저 없애고 10건으로 고정하면 잡음 카드가 늘어나므로 관련도 기준과 함께 바꿈 |
| 관련도 기준 | **IDF 가중 일치 비율 50% 이상** (M5 사용자 결정). 검색어 토큰의 IDF 합 중 항목에 있는 토큰의 IDF 합이 50% 이상인 항목만 돌려준다. 드문 단어(주제를 정하는 단어)가 빠지고 흔한 단어만 맞은 항목을 거르고, DB에 없는 주제에는 0건을 돌려준다. 기술 별칭과 표준 이름(카프카·kafka)은 한 단위로 보고 둘 중 하나만 있어도 맞은 것으로 센다. 후보였던 1위 대비 상대 점수·BM25 절대 점수는 없는 주제를 거의 거르지 못했고(E5), 40%로 낮추면 정답 비율은 조금 오르지만 없는 주제 판정이 60%로 떨어졌다. **M6 보완**: 필터(문제 유형·도메인·기술) 이름과 겹치는 검색어 단위는 기준 계산에서 뺀다. 색인 `keywords` 열에 분류·기술 이름이 있어 필터를 건 후보는 모두 그 토큰을 가지므로, 검색어가 필터 이름을 되풀이하면 기준이 무력해졌다(Claude Code 실사용에서 문제 유형 "트래픽 급증 대응" + 검색어 "이벤트 트래픽 급증 대기열"이 32건 통과, 수정 후 8건). 검색어가 필터 이름뿐이면 원래 단위로 잰다. `search` 설명에도 필터 조건을 검색어에 다시 쓰지 말라고 안내한다 |
| "결과가 적다" 안내 | 기준을 넘은 항목이 3건 이하면 "N건뿐"이라고 알린다. 0건이면 "결과 없음"과 함께 검색어를 나누거나 바꿔 다시 찾으라고 안내한다 |
| 최종 수치 (M5 E9) | Recall@5 0.589, MRR 0.920, 없는 주제 결과 없음 100%, 무관 비율 30% (M5 시작 시 BM25 상위 10건: 0.551 · 0.912 · 0% · 50%). OpenAI large 하이브리드 + 관련도 기준(0.595 · 0.900 · 100% · 30%)과 같은 수준. M6 보완 뒤 E9: 0.589 · 0.920 · 100% · 29%, 재작성 흉내 시 Recall@5 0.623 → 0.631, 원래 + 재작성 0.627 → 0.635 |

관찰 기록은 [milestones/M5.md](milestones/M5.md#관련도-기준-관찰-기록)의 "관련도 기준 관찰 기록"에 쌓는다.

출력: 조건에 맞는 전체 항목 수와 회사 수(**모수**), 항목별 건수·회사 수·회사 이름, 항목별 **예시 ID**(바로 `get_details`로 이어가도록). 기술·문제 유형·도메인은 항목마다 여러 개라 해당하는 값마다 세고, 건수의 합이 전체보다 클 수 있다고 결과에 적음.

- 건수 옆에 **수치 있는 성능·운영 포인트 건수**를 함께 표시함 (M3: 사례 N / 인사이트 M 구분을 대신함). **M5 결정** (사용자 결정): 성능·운영 포인트가 있는 항목이 96%(1,263/1,315)라 거의 모든 항목에 붙어 근거가 강한 사례를 구분하지 못했다. 그래서 성능·운영 포인트 문장에 숫자가 있는 항목(690개, 52%)만 센다. 색인 빌드 때 코드(`build_index.has_metrics`)로 판정하므로 재추출이 필요 없다. 카드의 성능·운영 줄은 문장이 있으면 그대로 보여 준다. 숫자가 없는 항목에도 정성적 결과나 운영 경험이 있을 수 있어 결과에 그렇게 적는다
- **기술 집계는 같은 계열을 합쳐 센다** (M5 결정, 사용자 결정): 기술 사전의 `parent`를 반영해 Amazon MSK·Kafka Connect 등을 Kafka 계열로 합치고 '포함'에 하위 기술별 건수를 보여 준다. 한 항목이 계열 안의 제품을 여럿 써도 계열로는 한 번만 센다(Kafka 132건 → 계열 141건). 회사 수도 계열 기준이다
- **기술 필터도 계열로 펼친다** (M6 결정, 사용자 결정): `search`·`aggregate`의 기술 필터에 상위 기술을 주면 하위 기술까지 찾는다("Kafka" → Amazon MSK, Kafka Connect, Kafka Streams, ksqlDB 포함, 132건 → 141건). 하위 기술을 주면 그 기술만 찾는다. 집계의 계열 합산과 필터 결과의 숫자가 같아져 에이전트가 차이를 기억할 필요가 없다. 검색 평가셋 E9(서버 search 그대로, 기술 필터 질문 Kafka·Iceberg 포함)의 지표는 변경 전과 같았다. 조건 표시에는 "Kafka 계열"로 보여 준다
- `rejected_alternative` 기준 집계는 기술 대안이 있는 항목만 대상

### 배포 로드맵

| 단계 | 코드 배포 | 데이터 전달 |
| --- | --- | --- |
| MVP | git 설치 후 실행 (`uv tool install git+…`, M6 결정) | GitHub Release에서 다운로드 (M6에서 앞당김, 아래) |
| 안정화 + 자동 갱신 | PyPI (`uvx techblog-mcp`, M8) | 같은 방식 + 새 DB 자동 확인 (M8) |

- **M6 결정: MVP 설치는 `uv tool install git+…`로 안내한다** (사용자 결정). 처음 계획한 `uvx --from git+…`는 깨끗한 환경 확인에서 약점이 드러났다. uvx는 git 주소를 실행할 때마다 GitHub에서 브랜치의 최신 커밋을 확인(`git fetch`)한다. 그래서 오프라인에서는 서버가 켜지지 않았고(20~30초 뒤 실패), 온라인에서도 initialize가 5.1~6.3초 걸렸다. `uv tool install`은 설치 때 한 번만 받고 실행 때는 GitHub에 접속하지 않아 initialize 2.4~2.6초, 오프라인에서도 정상이었다. 대신 설치·등록이 두 단계가 되고 업데이트는 `uv tool upgrade`로 직접 한다.
- **PyPI 전환은 M8로 넘긴다** (사용자 결정). Python MCP 서버의 일반적인 배포 형태는 PyPI + `uvx <패키지>`다. 이 경우 uvx가 버전 번호로 캐시해 매번 확인하지 않으므로, 한 줄 등록과 빠른 기동을 함께 얻는다. 사용자에게 Git이 필요 없고, 저장소 전체를 checkout하지 않아 Windows 경로 길이 문제도 없다. PyPI 계정과 버전 관리·배포 자동화가 필요해 M6 범위에서 뺐다. 이름 `techblog-mcp`는 2026-10-05 기준 PyPI에서 비어 있다.
- DB 경로를 불러오는 부분은 `src/techblog_mcp/db.py` 한 곳에 둔다.
- **M6 결정: 검색 DB는 GitHub Release에서 내려받는다** (사용자 결정). git 주소로 설치하면 패키지(`src/techblog_mcp/`)만 설치되고 저장소의 `data/techblog.sqlite`는 따라가지 않는다. 검토한 대안은 세 가지였다.
  - (A) 빌드한 DB를 패키지에 넣기: 가장 단순하지만, 갱신할 때마다 약 9MB 바이너리가 git 기록에 쌓인다.
  - (B) jsonl을 패키지에 넣고 첫 실행 때 빌드하기: 첫 실행이 느리고, 색인 빌드 코드를 서버로 옮겨야 한다.
  - (C) Release에서 내려받기: 원래 안정화 단계에 계획했던 방식이고 M8에 그대로 이어진다. C를 택했다.
- **내려받을 DB는 코드에 고정한다** (사용자 결정). Release 태그·sha256·크기·스키마 버전을 `src/techblog_mcp/db_release.json`에 두고, 받은 파일을 체크섬으로 검증한다. 같은 코드면 항상 같은 데이터를 쓰고, 실행할 때 최신 버전을 확인하는 네트워크 요청이 없다. 데이터를 갱신하려면 `pipeline.release_db --upload`로 새 Release를 만들고 바뀐 `db_release.json`을 커밋한다. 최신 DB 자동 확인은 M8에서 붙인다.
- DB는 환경 변수 `TECHBLOG_MCP_DB` → 저장소 `data/techblog.sqlite`(개발용) → 사용자 캐시(Windows `%LOCALAPPDATA%\techblog-mcp`, macOS `~/Library/Caches/techblog-mcp`, 그 외 `$XDG_CACHE_HOME/techblog-mcp`) 순으로 찾는다. 서버는 기동 때 백그라운드에서 DB를 준비해 initialize 응답을 막지 않고, 도구 호출은 준비가 끝날 때까지 기다린다. 다운로드·검증에 실패하면 도구 결과로 이유를 알리고 다음 호출에서 다시 시도한다.

  | 조건 | techblog MCP | 웹 검색(WebSearch·WebFetch) | 비교하는 것 |
  | --- | --- | --- | --- |
  | `mcp` | 있음 | 차단 | 이 서버를 쓸 때 |
  | `none` | 없음 | 차단 | 모델 기억만으로 답할 때 (기준선) |
  | `web` | 없음 | 허용 | 현실의 대안인 웹 검색으로 사례를 찾을 때 |
  | `web-ask` | 없음 | 허용 + 사례는 웹 검색으로 찾으라는 지시 | 웹 검색을 실제로 쓸 때 (추가, 아래) |

  `mcp`와 `none`의 차이로 서버의 효과를 분리하고, `web`과 비교해 웹 검색 대비 가치를 본다. `web`은 결과가 실행마다 달라 재현성이 낮고, 답변 속 웹 출처의 사실 여부를 따로 확인해야 한다.
- **에이전트 모델은 `sonnet`, 과제마다 조건별 3회** (사용자 결정, 2026-10-06). 호출 금지 과제(`no_call`)는 techblog 도구가 있을 때만 의미가 있어 `mcp` 조건만 돌린다. 과제 28개 기준 234회다.
- **`web-ask` 조건을 추가한다** (사용자 결정, 2026-10-06). `web` 조건 65회에서 에이전트가 웹 검색을 한 번도 쓰지 않았다. 사례를 직접 요청받아도 기억으로 답하고 "원하시면 웹 검색으로 찾아 드리겠다"고 되물었다. 그래서 `web`은 "웹 검색이 있어도 쓰지 않는 기본 행동"으로 그대로 두고, `--append-system-prompt`로 "선택지가 있는 작업에서는 WebSearch로 국내 기업 기술 블로그 사례를 찾고, 회사명·원문 링크를 밝히고, 못 찾은 사례는 만들지 않는다"고 지시한 `web-ask`를 따로 둔다. 지시문은 사용자가 CLAUDE.md에 넣을 만한 수준으로 맞췄다(`eval/agent_run.py`의 `WEB_ASK_PROMPT`). 호출 금지 과제를 뺀 25개 × 3회 = 75회.
- **전역 `~/.claude/CLAUDE.md`는 그대로 둔다** (사용자 결정). 헤드리스 실행에서 OAuth 로그인을 유지하면서 이 파일만 뺄 방법이 없다(`--bare`는 API 키 필요, `--safe-mode`는 MCP 서버까지 끔). 내용이 응답 언어 규칙뿐이고 세 조건에 똑같이 들어가 비교에는 영향이 없다. 실행 옵션은 [M7 진행 기록](milestones/M7.md#진행-기록)에 있다.

### 조사에서 드러난 사항

- **피드만으로 3년치를 모을 수 있는 곳은 올리브영과 컬리뿐**이다. 나머지는 사이트맵이나 공개 API로 과거 글 목록을 확보해야 한다.
- **수집 방식이 블로그마다 네 가지로 갈린다**: 피드(올리브영, 컬리), 사이트맵 + HTML(우아한형제들, 카카오, 카카오페이, LY), 공개 JSON API(토스, D2), 피드만(Medium 3곳).
- 수집기는 브라우저로 위장하지 않고, 누가 왜 수집하는지 밝히는 User-Agent(예: `TechblogCaseBot/0.1 (+저장소 URL)`)를 사용한다. robots.txt를 지킨다. 봇 확인(Cloudflare 등) 우회는 운영 측 허락을 받은 경우에만 한다 ("수집 예절").
- **Medium 3곳(당근, 무신사, 29CM)은 과거 글을 모을 수 없다** (→ 수집 대상에서 제외하기로 결정). 아카이브 목록은 봇 확인(Cloudflare)으로 막혀 있으며, 당시 원칙에 따라 우회하지 않았다. 피드로 최근 10편씩만 확보할 수 있다.
- **Medium 라이선스 파일(RSL)** 은 AI 입력·색인·검색 용도를 출처 표기 조건으로 허용하고 AI 학습만 금지한다. 이 프로젝트의 용도(추출·색인 + 원문 링크)는 허용 범위에 가깝지만, 같은 사이트의 robots.txt는 AI 크롤러를 전면 차단하고 있어 입장이 일관되지 않는다.
- 카카오는 Nuxt 기반이라 본문이 HTML이 아닌 스크립트 데이터에 들어 있어 블로그 전용 파서가 필요하다. 토스는 Next.js지만 글 페이지에 본문이 서버 렌더링돼 있다 (M2에서 확인).
- **우아한형제들은 수집기의 요청을 WAF가 차단한다** (M2에서 확인). 차단 페이지는 "올바른 접근 요청이 아니어서 접근할 수 없다"는 안내이고, User-Agent가 같아도 curl은 통과하므로 클라이언트 지문으로 거르는 것으로 보인다. 운영 측 허락을 받은 뒤(2026-09-30) 이 호스트만 시스템 curl로 요청해 수집했다. User-Agent·robots.txt·요청 간격은 그대로 적용한다.
- 각 블로그의 이용약관은 M6에서 확인했다 (위 "저작권과 이용약관").
