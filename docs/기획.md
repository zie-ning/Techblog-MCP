# 기술블로그 사례 검색 MCP 서버 기획

## 개요

코딩 에이전트가 개발 중에 국내 기업의 실제 해결 사례를 참고해 설계 판단을 하도록 돕는 사례 검색 MCP 서버.
국내 IT 기업 기술 블로그를 수집해 **문제 상황 / 해결 방법 / 성능·운영 포인트**(+ 글에 명시된 버린 대안)로 구조화하고, Claude Code·Cursor 같은 코딩 에이전트가 MCP 도구로 호출해 비슷한 사례를 받아보게 한다. 사용자가 검색하러 오는 게 아니라, 개발하는 곳으로 사례가 찾아가는 구조다.

## 문제 정의

코딩 에이전트는 설계 판단을 일반론으로 하고, 좋은 실무 사례는 흩어져 있어 개발 도중에 찾기 어렵다.

- **에이전트의 근거 부족**: "선착순 쿠폰 동시성" 같은 문제에 트래픽 규모나 트레이드오프 없이 교과서적인 답을 낸다. "A사는 X를 썼다" 같은 사례를 지어낼 위험도 있다.
- **사례의 분산**: 좋은 사례는 기업 블로그마다 흩어져 있고, 블로그 자체 검색은 제목 수준이며, 구글 검색에는 SEO용 짜깁기 글이 섞인다.
- **모르는 걸 모름**: 비슷한 문제를 누가 풀었는지 모르면 찾아볼 생각조차 못 한다. 물어보는 챗봇(pull)보다 개발 흐름 안에서 제시되는 방식(push)이 필요하다.

## 차별점

답변을 만드는 LLM은 같으므로, 차이는 검색과 데이터 구조에서만 난다. 사례·집계형 질문에서는 이기고, 개념 질문과 DB 밖 주제에서는 진다.

| 질문 유형 | LLM 단독 | 웹검색 LLM | 이 서비스 |
| --- | --- | --- | --- |
| 개념 ("Redis 분산락 원리") | 충분함 | 충분함 | 비슷하거나 열세 |
| 사례 ("쿠폰 동시성 어떻게 풀었나") | 지어낼 위험 | 2~3개 사례 | 더 많은 사례를 구조로 비교 |
| 집계 ("Kafka 쓰는 국내 회사") | 못함 | 부정확 | 확실히 우위 |
| DB에 없는 주제 | 답은 함 | 잘함 | 못함 |

핵심 강점은 세 가지다.

- **구조화된 사례 데이터**: 문제 상황·해결 방법·성능/운영 포인트로 정리하고, 글에 명시된 경우 버린 대안까지 담아 에이전트가 바로 설계 판단에 쓸 수 있다. 기술·문제 유형·버린 대안별 집계도 제공한다.
- **출처 품질**: 기업 기술 블로그만 사용하고 모든 사례에 원문 링크와 근거 발췌를 붙인다.
- **개발 흐름 안 제공**: 검색 1회로 빠르고 싸게, 에이전트가 필요할 때 직접 호출한다.

챗봇 자체는 웹검색 LLM과 큰 차이가 없으므로 핵심 가치로 내세우지 않는다.

### 유사 서비스: velopers.kr

국내 기업 기술 블로그 155곳을 모아 AI로 요약하는 웹 서비스. 글 유형에 따라 "문제 상황 / 원인 분석 / 해결 방법" 또는 "핵심 내용 / 적용해볼 점"으로 요약하고 기술 태그를 붙인다. 이 프로젝트의 유형별 구조는 이 방식을 참고했다.

| | velopers.kr | 이 서비스 |
| --- | --- | --- |
| 사용자 | 사람이 사이트에 와서 읽음 (pull) | 코딩 에이전트가 개발 중에 호출 (push) |
| 제공 방식 | 웹 목록·검색 | MCP 도구 (검색, 상세, 집계) |
| 집계 | 태그별 글 수 | 기술·문제 유형·버린 대안별 사례 수와 회사 수 |
| 근거 | 요약 | 요약 + 필드별 원문 발췌 (원문 존재 여부 자동 검증) |

### 구조화(추출)

| 항목 | 결정 |
| --- | --- |
| 추출 LLM | OpenAI API 사용. 모델은 정답셋으로 비교 평가한 뒤 결정 |
| 항목 구조 | **문제 상황 / 해결 방법 / 성능·운영 포인트** 3포인트가 뼈대. 트래픽 규모는 별도 필드 없이 문제 상황 안에 원문 표현대로 서술(M3: 원문에 규모·제약 수치가 있으면 반드시 넣도록 프롬프트 강화. 정답셋 `key_facts` 포함률로 재고, 부족하면 M3 마감 전에 별도 필드 검토). 성능·운영 포인트에는 적용 후 결과를 먼저, 운영 주의점을 뒤에 담음. 버린 대안은 글에 명시된 경우에만 추출하고 없으면 비워 둠. 해결 방법만 필수이고, 팁·활용 경험 글은 문제 상황이 비어 있을 수 있음 |
| 사례·인사이트 구분 폐지 (M3) | 처음에는 사례형(문제 상황 / 해결 방법 / 성능·운영 포인트)과 인사이트형(핵심 내용 / 적용해볼 점)을 나눴으나, M3 정답셋 검수 중 **추출/제외만 판단**하고 구조를 하나로 합치기로 함. 이유: 둘의 경계가 자주 갈림(정답 17편 중 5편이 경계 글), 추출 모델도 같은 프롬프트에서 실행마다 사례 4개 ↔ 인사이트 1개를 오감(코틀린 팁 모음), 사람마다 판단이 갈리는 구분을 `kind` 필터로 쓰면 필터 결과도 믿기 어려움. 구분이 하던 일은 이렇게 옮김: 팁 모음을 잘게 쪼개지 않는 규칙 → 항목 나누기 규칙, 근거의 세기 → 판정 대신 **성능·운영 포인트(적용 결과)가 원문에 있는지**를 카드와 집계에 표시, `kind` 필터 → 제거. 이전 기록은 읽을 때 사례·인사이트를 추출로 바꾸고 인사이트의 핵심 내용·적용해볼 점을 해결 방법으로 옮김 |
| 단위 | 1글 = N항목 (독립적인 문제-해법 쌍마다 하나, 같은 문제의 단계적 해결은 한 항목). 팁 모음·도구 활용 경험 글은 1항목 |
| 분류 체계 | 2축 고정 분류 + 자유 태그. **문제 유형**(무슨 문제를 풀었나)과 **도메인**(어떤 영역에서 일어났나)을 별도 필드로 두어 "LLM·AI 도메인의 비용 절감 사례"처럼 교차 검색 가능. 목록은 초안을 만들고 파일럿 추출 후 조정 |
| 분류 목록 조정 기준 (M3) | ① 한 분류가 항목의 25%를 넘으면 나누기 검토 ② 파일럿과 정답셋 모두에서 0건이고 다른 분류와 뜻이 겹치면 합치기 검토 ③ 정답셋에서 일치율이 낮은 분류 쌍은 정의 문구 보강. baseline의 "개발 생산성"(23%)·"사내 플랫폼·개발 도구"(40%) 쏠림은 대상이 아닌 문화·팁 글이 들어온 영향이 커서, 분류 기준을 고친 v2 결과로 판단. **v3 결과로 내린 결정**: 목록은 바꾸지 않는다. 도메인 "사내 플랫폼·개발 도구"(39%)는 서비스 영역이 있는 인프라 작업(호텔 검색, 메신저 서버 등)이 잘못 들어온 영향이 커서 "서비스 영역이 있으면 그 도메인, 개발 도구·사내 공통 플랫폼 자체가 대상일 때만 사내 플랫폼" 기준을 정의와 프롬프트에 넣고, 정답셋·모델 비교에서 다시 잰다. 문제 유형 "개발 생산성"(21%)은 기준 미만이라 유지하고 정의를 "코드 작성 방식·언어 기능 활용, 리팩터링, 빌드·개발 환경, 개발 도구 도입(AI 코딩 도구 포함)"으로 좁힌다 (협업 방식은 대상 글에서 제외됐으므로 뺌). "AI 활용 개발" 문제 유형 신설은 하지 않음 |
| 분류 개수 (M3 변경) | **문제 유형 1~3개, 도메인 1~2개를 순서 없이 다중 선택**한다. "범용"은 다른 도메인이 없을 때만. 검색 필터는 항목의 값 중 하나라도 맞으면 찾고, 집계는 해당하는 값마다 센다(합계가 전체보다 클 수 있음을 결과에 표시). 처음에는 주 문제 유형 1개 + 보조 최대 2개, 도메인 1개였으나 M3 정답셋에서 항목 24개 중 문제 유형 17개(71%), 도메인 15개(63%)가 "하나만 고르면 갈리지만 둘 다 맞는" 경우여서 바꿈(예: 로그 플랫폼 재설계는 관측성이면서 비용 절감, 사내 AI 플랫폼은 사내 플랫폼이면서 LLM·AI). 주 유형은 집계를 중복 없이 세려고 둔 것이었는데, 아래 "도구 우선순위" 원칙에 따라 집계 편의보다 검색 정확도를 우선함. 과다 태깅은 개수 상한, "직접 해결한 것만" 규칙, 평가의 정밀도로 막음. 도메인 겹침의 근본 원인("LLM·AI"·"사내 플랫폼·개발 도구"가 서비스 영역이라기보다 기술 분야·대상 성격)은 M4 분류 검토에서 봄 |
| AI 분류 | 도메인 축에 "LLM·AI" 하나로 두고, 파일럿에서 글이 많이 모이면 세분화 (후보: LLM 애플리케이션 / AI 에이전트·워크플로 자동화 / AI 코딩 도구 도입 / LLM 인프라·운영) |
| 자동화 | AI와 무관한 사내 봇, 운영 스크립트 등은 문제 유형 "업무·운영 자동화"로 분류 |
| 기술명 정규화 | 기술 사전(표준 이름 + 별칭) + LLM 보조. 사전에 없는 이름은 리포트로 뽑아 검토 후 사전에 추가. technologies에는 제품·라이브러리·프레임워크·서비스 이름만 넣고 클래스·메서드명, 일반 개념, 사내 명칭, 버전 표기는 넣지 않음(M3 파일럿에서 미등록 이름 380종 중 상당수가 이런 값) |
| 기술 사전 구조 (M3) | 항목마다 **종류(category)** 와 **상위 기술(parent)** 을 둔다. 종류는 집계에서 모니터링 도구가 메시지 큐와 섞이는 문제(M1 시나리오 4)를, 상위 기술은 Amazon MSK가 Kafka와 따로 집계되는 문제를 풀기 위함. M3에서 형식·로딩 코드와 기존 항목의 종류를 채우고, 사전 대량 보강은 M4, 서버 `aggregate` 필터 반영은 M4 이후 |
| 버린 대안 | 글에 명시된 경우에만: 정규화된 대안명 + 버린 이유 + 근거 발췌 (집계 가능하도록 대안명도 사전으로 정규화). **M3에서 유형 추가**: `기술`(제품·라이브러리) / `설계 방식`(Outbox 패턴, 비관적 락 등). `aggregate`의 버린 대안 집계는 `기술`만 세고, 설계 방식은 `get_details`에 보여 줌. 이름은 짧은 명사구로 쓰고 진행 방식(리허설 순서, 회의 방식 등)은 넣지 않음. M3 파일럿에서 버린 대안 75개 중 사전에 있는 이름이 3개뿐이고 나머지가 긴 문장형 설계·진행 방식이어서 나온 결정 |
| 원문 정책 | 필드별 짧은 근거 발췌(1~2문장) + 원문 링크만 배포. 원문 전체는 로컬 캐시에만 두고 배포하지 않음. 경계는 **배포**다: 처리를 위해 외부 서비스로 보내는 것(추출용 OpenAI API, 평가·관측용 LangSmith 비공개 워크스페이스)은 허용하고, 원문 전체가 보이는 트레이스 공개 링크·화면 캡처를 공개하는 것은 배포로 보아 하지 않음 |
| 발췌 검증 | 발췌문이 원문에 실제로 존재하는지 코드로 자동 검사해 LLM이 지어낸 내용을 걸러냄 |
| 정답셋 | 추출 평가용 20~30편은 Claude Code 세션에서 초안을 만들고 직접 원문과 대조해 검수 (비교 대상인 OpenAI 모델과 계열이 달라 특정 후보 쪽으로 기울지 않게 함). 검색 평가용 질문 30개 |
| 추출 평가 | 자동 지표(분류 일치율, 발췌의 원문 존재율, 원문에 없는 버린 대안 비율) + 요약 품질은 LLM 채점(OpenAI API 스크립트, 채점 기준 프롬프트 고정) + 채점 결과 일부를 Claude Code 세션이 원문·추출 결과와 대조해 채점을 믿을 만한지 확인(M3 사용자 결정: 사람이 채점 결과를 검수하는 단계는 두지 않음) |
| 검색 평가 | 검색 평가셋(질문 + 정답 사례)으로 **Recall@5**(정답이 상위 5건 안에 든 비율)와 **MRR**(정답 순위 역수의 평균)을 측정. 임베딩 도입 여부와 검색 필드 가중치 결정의 근거로 사용 |
| 파일럿 | 80편(블로그당 10편)으로 파서, 글 유형 분류, 분류 목록, 추출 프롬프트를 점검한 뒤 전체 추출 |
| M1 임시 모델 | `gpt-5-mini` (reasoning effort medium). `--model`로 바꿀 수 있고 M3 비교 평가 후 확정 |
| 추출 호출 구조 | 글마다 ① 글 유형·추출 여부 분류 호출 → ② 추출이면 구조화 호출. 분류를 따로 두어 M3에서 분류 일치율을 따로 잴 수 있게 함 |
| 평가·관측 도구 (M3) | **LangSmith**. 추출 과정(분류 → 구조화 → 재시도)을 원문 포함으로 트레이싱하고, 파일럿·정답셋·실패 사례 회귀셋을 Dataset으로, 모델·프롬프트 버전별 추출을 Experiment로 관리하며, 채점기 검증용 사람 검수는 Annotation queue에서 함. 도입 이유: 실패 트레이스 확인 → Playground에서 프롬프트 수정 → 회귀셋 확인으로 프롬프트 개선 주기를 짧게 하고, 원문을 옆에 둔 검수 화면을 직접 만들지 않기 위함. M8 자동 갱신에서 운영 모니터링으로 이어서 씀. 지표 함수와 LLM 채점기는 직접 구현하고 결과는 저장소(`eval/runs/`, `eval/reports/`)에도 남겨 LangSmith 없이 재현 가능하게 함. 트레이싱은 환경 변수로 켜고 기본은 끔 |
| 발췌 검증 실패 처리 (M1 기준, M4에서 재검토) | 공백·줄바꿈·따옴표 모양·대소문자·마크다운 강조 차이와 `...` 중간 생략만 허용하고 나머지는 불일치로 봄. 여러 줄 발췌는 떨어진 문장을 이어 붙인 것으로 보고 줄마다 원문에 있는지 검사. 실패 발췌가 있으면 실패 목록을 알려 주고 **한 번 다시 구조화**한 뒤, 두 시도 중 검증을 통과한 내용이 더 많은 쪽을 씀(재시도가 더 나쁠 때가 있음). 그래도 실패한 항목은 버리고, 해결 방법이 비면 그 항목을 통째로 버림(M3에서 문제 상황은 필수에서 뺌: 팁·활용 경험 글은 문제 상황이 없을 수 있음). 버린 발췌는 글별 기록에 남김 |
| 추출 결과 파일 | `data/entries.jsonl`(항목) + `data/posts.jsonl`(글별 기록: 글 유형, 추출 여부, 분류 이유, 원문 해시, 모델, 프롬프트 버전, 항목 ID, 버린 발췌). 제외된 글도 기록해 다시 추출하지 않음. 둘 다 커밋 |
| 프롬프트 버전 기록 | LLM에 전달되는 지시 전체(분류·구조화 지시문, 입력 형식, 재시도 문구, 출력 스키마와 필드 설명)의 SHA-256 앞 12자리를 글별 기록(`posts.jsonl`)의 `prompt_version`에 저장. 사람이 올리는 번호는 잊기 쉬워 자동 해시를 씀. 해시만으로는 내용을 알 수 없으므로 새 버전이 처음 쓰일 때 전문을 `data/prompt_versions/{버전}.md` 스냅샷으로 저장(커밋). 기본 실행은 새 글·원문이 바뀐 글만 추출하고, `--outdated`를 주면 다른 프롬프트·모델로 추출한 글도 다시 추출(프롬프트를 고칠 때마다 자동 전체 재추출하면 비용이 커서 명시적으로 켬) |
| 항목 ID | `case_0001` 형식, 한 번 붙으면 바뀌지 않음. 글을 다시 추출하면 옛 항목을 지우고 새 번호를 붙임(번호 재사용 없음) |
| 기술명 저장 | 정규화된 `technologies`와 원래 이름 `technologies_raw`를 함께 저장. 사전을 보강하면 LLM 재호출 없이 `pipeline.normalize --apply`로 다시 정규화 |
| 기술명 정규화 규칙 | 대소문자·공백·`-_.` 차이 무시. 그대로 없으면 괄호 설명(`OGG(Oracle GoldenGate)`는 괄호 안도 후보)과 끝의 버전 번호(`RabbitMQ 3.12.14`)를 떼고 다시 찾음. 모델 버전은 제품군으로 묶음(`Claude 3.5 Sonnet` → Claude) |
| 버린 대안 이름 | 사전으로 정규화하되, 결과가 그 사례에서 쓴 기술과 같으면 원래 이름을 유지. "Claude 3 Haiku를 버리고 Claude 3.5 Sonnet을 씀"이 "Claude를 버렸다"로 기록되는 모순을 막기 위함 |
| 카드 요약 줄 | 문제 상황·해결 방법의 첫 항목이 `search` 카드에 쓰이므로, 해결 방법 첫 항목은 **최종 채택한** 해결책이어야 함을 프롬프트와 스키마 설명에 명시 (M1 사용 중 버린 대안이 카드에 해결 방법으로 나온 문제에서 나온 결정) |

### MCP 인터페이스

| 도구 | 용도 | 반환 |
| --- | --- | --- |
| `search` | "비슷한 사례나 참고할 글 있어?" | 항목을 검색해 관련도 순 요약 카드로 반환. 기본 5건, 최대 10건 |
| `get_details` | "그거 자세히 보여줘" | 항목의 전체 필드, 근거 발췌, 원문 링크 |

#### 공통 원칙

- **도구 우선순위 (M3 결정)**: 이 서버의 핵심은 `search`다. 코딩 에이전트에 비슷한 사례를 정확히 찾아 주는 것이 프로젝트의 주된 역할이고, `get_details`는 그 결과를 여는 도구, `aggregate`는 여러 회사의 선택을 비교할 때 쓰는 **보조 도구**로 중요도가 가장 낮다. 데이터 구조·분류·색인을 설계할 때 집계를 깔끔하게 만들려고 `search`의 검색 정확도를 낮추는 선택(예: 집계 중복을 피하려고 분류를 하나만 고르게 강제)은 하지 않는다. 둘이 부딪히면 `search`를 우선하고, 집계 쪽은 결과 표시(예: "건수 합이 전체보다 클 수 있음")로 보완한다
- **결과 형식**: JSON이 아닌 읽기 쉬운 텍스트. 토큰이 적고 에이전트가 답변에 바로 인용하기 쉬움
- **필터 값**: 문제 유형(20개), 도메인(10개)은 입력 스키마의 선택지 목록(`enum`)으로 제공해 에이전트가 정확한 값을 고르게 함. 선택지는 추출에 쓰는 분류 정의 파일에서 자동 생성해 항상 일치시킴. 기술은 종류가 많아 자유 입력으로 받고 서버가 기술 사전으로 정규화함 (예: "카프카" → Kafka)
- **회사·날짜 필터 없음**: 개발 흐름에서 회사나 날짜로 좁혀 찾을 일이 드물고, 데이터가 이미 최근 3년치라 날짜 필터의 효과가 작음. 파라미터가 적을수록 에이전트가 헷갈리지 않음. 대신 회사 이름을 검색 색인에 넣어 "토스 Kafka"처럼 검색어로 찾을 수 있게 하고, 카드에 발행일을 보여 에이전트가 오래된 글을 감안하게 함
- **사전에 없는 기술**: 필터에서 제외하고 그 사실과 비슷한 기술을 결과에 알려 줌
- **결과가 없거나 적을 때**: "이 주제는 사례가 N건뿐"이라고 명확히 알려 에이전트가 사례를 지어내지 않게 함

#### `search`

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `query` | ✅ | 찾는 문제 상황 (자연어) |
| `problem_type` | | 문제 유형 (선택지). 항목의 문제 유형(여러 개) 중 하나라도 맞으면 매칭 |
| `domain` | | 도메인 (선택지). 항목의 도메인(여러 개) 중 하나라도 맞으면 매칭 |
| `technologies` | | 기술 목록 (자유 입력, 서버가 정규화) |
| `limit` | | 결과 수. 기본 5, 최대 10. **M5에서 제거 예정** (아래 "결과 수 결정") |

출력: 항목별 요약 카드. 근거 발췌는 넣지 않음. M3에서 `kind` 필터와 카드의 [사례]/[인사이트] 표시를 없앰(위 "사례·인사이트 구분 폐지").

- 카드: ID, 회사, 발행일, 문제 유형들, 도메인들, **원문 제목**, 문제 상황 한 줄(있을 때만), 해결 방법 한 줄, 성능·운영 포인트 한 줄(있을 때만), 기술, **버린 대안 이름**(있을 때만), 원문 링크
- 성능·운영 줄은 적용 결과나 운영 경험이 원문에 있다는 표시이기도 하다. 없으면 팁·도입 경험 위주의 항목

##### 결과 수 결정 (M5에서 구현)

| 항목 | 결정 |
| --- | --- |
| `limit` 파라미터 | **제거**. 에이전트는 결과를 보기 전에 몇 건이 적당한지 판단할 근거가 없어 값이 임의적임 (M1 테스트에서 8, 6을 임의로 지정). 파라미터가 적을수록 에이전트가 덜 헷갈린다는 원칙과도 맞음 |
| 반환 방식 | 서버가 **관련도 기준을 넘는 항목만 최대 10건** 반환. 현재는 검색어 단어 하나만 맞아도 후보가 되고 limit까지 채우므로 무관한 글이 섞임 |
| 구현 시점 | M5. limit만 먼저 없애고 10건으로 고정하면 잡음 카드가 늘어나므로 관련도 기준과 함께 바꿈 |
| 기준 후보 | ① 1위 점수 대비 상대 점수 ② 검색어 형태소 일치 비율 ③ BM25 절대 점수(검색어·데이터 규모에 따라 달라져 부적합할 가능성). 하나 또는 조합으로, 검색 평가셋(Recall@5, MRR)과 M1~M4 테스트 관찰 기록으로 결정 |
| 부수 효과 | "결과가 적다" 안내가 의미 있는 숫자가 됨 (지금의 "검색어가 하나라도 걸린 항목 N건"은 대부분 잡음) |

관찰 기록은 [milestones/M5.md](milestones/M5.md#관련도-기준-관찰-기록)의 "관련도 기준 관찰 기록"에 쌓는다.

#### `get_details`

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `ids` | ✅ | 사례 ID 목록. 최대 5건 (`search` 기본 결과 수와 같게 두어 기본 검색 결과를 한 번에 열 수 있게 함. M1에서 3건 제한 때문에 관련 사례 6건 중 3건만 열린 사례에서 상향) |

출력: 사례별 전체 필드와 필드마다 근거 발췌, 분류(문제 유형들, 도메인들), 원문 제목과 링크, **같은 글의 다른 사례 ID**.

#### `aggregate`

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `group_by` | ✅ | `technology` / `problem_type` / `domain` / `company` / `rejected_alternative` |
| 필터 | | `search`와 같은 필터 |
| `top_n` | | 상위 몇 개. 기본 10 |

출력: 조건에 맞는 전체 항목 수와 회사 수(**모수**), 항목별 건수·회사 수·회사 이름, 항목별 **예시 ID**(바로 `get_details`로 이어가도록). 기술·문제 유형·도메인은 항목마다 여러 개라 해당하는 값마다 세고, 건수의 합이 전체보다 클 수 있다고 결과에 적음.

- 건수 옆에 **성능·운영 포인트가 있는 건수**를 함께 표시함(M3: 사례 N / 인사이트 M 구분을 대신함). 성능·운영 포인트가 없는 항목은 팁·도입 경험 위주라 "실제 운영 결과"가 아닐 수 있음
- `rejected_alternative` 기준 집계는 기술 대안이 있는 항목만 대상

```
조건: 문제 유형 = 메시징·비동기 처리 → 31건 (성능·운영 포인트 있음 24) / 7개사
1. Kafka  18건 (성능·운영 포인트 있음 15) · 6개사 (토스, 우아한형제들, 카카오, …)  예시: case_0012, case_0087
2. SQS  5건 (성능·운영 포인트 있음 3) · 3개사 (…)  예시: case_0203
```

#### 호출 유도

| 항목 | 결정 |
| --- | --- |
| 장치 | 도구 설명 + README의 CLAUDE.md·Cursor rules용 지시문 스니펫(사용자가 복사해 붙여넣음) + MCP prompt `/techblog` |
| `/techblog` 제공 방식 | MCP prompt로 제공. 서버만 설치하면 생기고 Cursor 등에서도 동작함. Claude Code에서는 `/mcp__서버이름__techblog` 형태로 표시됨 |
| `/techblog` 동작 | 주제를 받아 `search` → 소개할 사례는 모두 `get_details`로 열고, 같은 문제에 다른 선택을 한 사례도 비교 자료로 함께 엶 → 회사별 접근 방식을 출처와 함께 소개 → 각 사례의 조건(규모, 제약, 기존 인프라)이 현재 작업과 어떻게 다른지 짚음 → 사례에 얽매이지 않은 선택지를 트레이드오프와 함께 제안. 답변은 "참고 사례"와 "제안"으로 나눔 |
| 사례 활용 원칙 | **사례는 설계 정답이 아니라 참고 자료.** 해당 회사의 규모·조직·기존 인프라에서 내린 선택이므로, 에이전트는 사례를 출처와 함께 소개하되 그대로 적용하라고 권하지 않고, 사용자 상황과 다른 점을 짚으며, 사례 소개와 자신의 제안을 구분함. 서버 안내·`search` 설명·`/techblog`에는 전문을, 결과마다 붙는 안내에는 짧은 버전을 넣음 (M1 실사용 테스트에서 에이전트가 사례를 "설계의 근거"로 녹여 넣어 사례와 자기 의견의 경계가 흐려진 데서 나온 결정) |
| 인용 전 확인 | `search`·`get_details` 설명에 "답변에 소개할 사례는 모두 get_details로 열어 확인하고, 카드에 없는 내용을 추측으로 채우지 말 것"을 명시. 소개하지 않을 사례까지 열 필요는 없다고 함께 적어 과도한 호출을 막음 (M1에서 열지 않은 글의 내용을 출처처럼 붙이고, 인용한 글과 연 글이 어긋난 사례에서 나온 결정) |
| 다른 선택을 한 사례 | `search` 설명과 `/techblog`에 "같은 문제에 다른 선택을 한 사례가 있으면 비교 자료로 함께 소개할 가치가 있다"를 명시 (M1에서 같은 회사가 다른 과업에서 상용 API를 고른 사례를 놓친 데서 나온 결정) |
| 도구 성격 표시 | 세 도구 모두 MCP 도구 annotation으로 읽기 전용(`readOnlyHint`)·비파괴·멱등·외부 통신 없음을 표시. 검색 DB를 읽기만 하는 도구의 성격을 클라이언트에 정확히 알림. 클라이언트가 이를 자동 허용에 쓰는지는 클라이언트마다 다름 |
| 호출 시점 | 동시성, 캐시, 메시징, 장애 대응, LLM 활용처럼 **선택지가 있는 설계를 시작하기 전**. 단순 CRUD, 버그 수정, 리팩터링에는 호출하지 않음 |
| 인용 규칙 | 결과를 인용할 때 회사명과 원문 링크를 반드시 밝히고, 결과에 없는 사례는 지어내지 않으며, 결과가 없거나 적으면 그렇다고 말함. 도구 설명과 결과 문구 양쪽에 명시 |
| 없는 주제 처리 | 결과가 없거나 적으면 그 사실을 명확히 반환 |

### 조사에서 드러난 사항

- **피드만으로 3년치를 모을 수 있는 곳은 올리브영과 컬리뿐**이다. 나머지는 사이트맵이나 공개 API로 과거 글 목록을 확보해야 한다.
- **수집 방식이 블로그마다 네 가지로 갈린다**: 피드(올리브영, 컬리), 사이트맵 + HTML(우아한형제들, 카카오, 카카오페이, LY), 공개 JSON API(토스, D2), 피드만(Medium 3곳).
- 수집기는 브라우저로 위장하지 않고, 누가 왜 수집하는지 밝히는 User-Agent(예: `TechblogCaseBot/0.1 (+저장소 URL)`)를 사용한다. robots.txt를 지킨다. 봇 확인(Cloudflare 등) 우회는 운영 측 허락을 받은 경우에만 한다 ("수집 예절").
- **Medium 3곳(당근, 무신사, 29CM)은 과거 글을 모을 수 없다** (→ 수집 대상에서 제외하기로 결정). 아카이브 목록은 봇 확인(Cloudflare)으로 막혀 있으며, 당시 원칙에 따라 우회하지 않았다. 피드로 최근 10편씩만 확보할 수 있다.
- **Medium 라이선스 파일(RSL)** 은 AI 입력·색인·검색 용도를 출처 표기 조건으로 허용하고 AI 학습만 금지한다. 이 프로젝트의 용도(추출·색인 + 원문 링크)는 허용 범위에 가깝지만, 같은 사이트의 robots.txt는 AI 크롤러를 전면 차단하고 있어 입장이 일관되지 않는다.
- 카카오는 Nuxt 기반이라 본문이 HTML이 아닌 스크립트 데이터에 들어 있어 블로그 전용 파서가 필요하다. 토스는 Next.js지만 글 페이지에 본문이 서버 렌더링돼 있다 (M2에서 확인).
- **우아한형제들은 수집기의 요청을 WAF가 차단한다** (M2에서 확인). 차단 페이지는 "올바른 접근 요청이 아니어서 접근할 수 없다"는 안내이고, User-Agent가 같아도 curl은 통과하므로 클라이언트 지문으로 거르는 것으로 보인다. 운영 측 허락을 받은 뒤(2026-09-30) 이 호스트만 시스템 curl로 요청해 수집했다. User-Agent·robots.txt·요청 간격은 그대로 적용한다.
- 각 블로그의 이용약관은 아직 확인하지 않았다.

## 미결정 사항

- 블로그별 이용약관 확인
- `get_details`, `aggregate`의 도구 설명 문구 (`search`는 초안 작성됨)

- 설치 사용자에게 검색 DB를 전달하는 방법 (MVP는 저장소 안 `data/techblog.sqlite`를 빌드해 씀. `uvx` 설치 시에는 이 경로가 없으므로 M6에서 결정)
