# 추출 평가

LLM이 블로그 글에서 뽑은 구조화 데이터(`data/entries.jsonl`)의 품질을 어떻게 재는지 정리한다. 결정 사항과 근거의 요약은 [기획.md](기획.md) "추출 평가" 행, 진행 기록과 수치는 [milestones/M3.md](milestones/M3.md)에 있다.

## 전체 구조

평가는 세 겹이다.

| 층 | 무엇 | 어디 |
| --- | --- | --- |
| 정답셋 | 24편(블로그당 3편)의 정답 항목과 항목마다 "꼭 담겨야 할 핵심 사실"(`key_facts`) | `eval/gold/` ([라벨링 기준](../eval/gold/README.md), [검수 참고표](../eval/gold/REFERENCE.md)) |
| 자동 지표 | 계산만으로 정해지는 지표. 코드가 센다 | `eval/extract_eval.py` |
| LLM 채점 | 의미 판단이 필요한 것만 채점 모델이 판정하고, 그 판정을 코드가 지표로 바꾼다 | `eval/judge.py` → `eval/runs/{run}/judge.jsonl` |

원칙: **LLM에 맡길 이유가 없는 것은 맡기지 않는다.** 글자 비교나 집합 비교로 되는 것(추출 여부, 기술명, 발췌 존재율, 비용)은 코드로 세고, 표현이 달라 의미로만 판단할 수 있는 것(어느 항목끼리 같은 문제인가, 이 문장이 원문에 근거하는가)만 LLM이 판정한다.

## 자동 지표 (코드)

| 지표 | 계산 |
| --- | --- |
| 추출 여부 일치 | 추출/제외가 정답과 같은 글 비율. 정답의 허용 답(`kind_alternatives`)도 맞음으로 세는 값과 정확 일치를 함께 본다 |
| 글 유형 일치 | 문제 해결형, 기술 선택·도입형 등 5개 중 정답과 같은 비율 |
| 항목 수 차이 | 추출 항목 수 − 정답 항목 수의 분포 (양쪽 모두 추출인 글) |
| 기술 정밀도·재현율 | 글마다 기술 이름 집합을 비교해 24편 합산. 사전에 있으면 표준 이름, 없으면 대소문자·구분자를 무시한 이름으로 맞춘다. 양쪽 모두 항목이 있는 글만 |
| 발췌 원문 존재율 | 검증 전 발췌 중 원문에 실제로 있는 비율 |
| 비용 | 글별 토큰 사용량 × 단가(`eval/pricing.toml`). 전체 1,262편 추정치도 낸다 |

## LLM 채점

### 입력과 출력

채점 모델에 글 한 편마다 세 가지를 함께 준다.

- **원문 평문**: 충실성·버린 대안 판정의 근거
- **정답**: 정답 항목마다 요약 한 줄(`summary`), 핵심 사실(`key_facts`), 버린 대안. 추출 여부와 허용 답
- **추출 결과**: 항목마다 문제 상황·해결 방법·성능·운영 포인트의 요약 문장, 버린 대안(이름·유형·이유), 문제 유형·도메인, 기술. 발췌는 이미 코드로 원문 대조를 마쳤으므로 넣지 않는다

출력은 구조화 출력(`JudgeOutput`)으로 받아 형식이 흔들리지 않게 한다. 채점 지시문 전문은 `eval/judge.py`의 `INSTRUCTIONS`다.

### 채점 항목

| 항목 | 단위 | LLM이 판정하는 것 | 판정 기준 | 계산하는 지표 |
| --- | --- | --- | --- | --- |
| ① 항목 대응 | 정답 항목마다 | 같은 문제-해법을 다룬 추출 항목 id. 정답 하나가 추출 여러 개로 나뉘었으면 모두, 없으면 빈 목록 | 표현이 아니라 다룬 문제가 같은지 | ②의 기준. 대응된 쌍에서 문제 유형·도메인 정밀도·재현율 |
| ② 핵심 사실 포함 | 정답 핵심 사실마다 | 대응한 추출 항목들에 그 사실이 담긴 정도 | **담김**: 핵심 내용과 수치가 모두 있음(표현이 달라도 같은 뜻이면 담김) / **일부**: 핵심 내용은 있지만 수치·조건·이유 중 일부가 빠짐 / **없음**: 그 사실이 없거나 수치가 틀림. 대응 항목이 없으면 모두 없음 | **완결성** = 담김 1, 일부 0.5, 없음 0의 평균 |
| ③ 충실성 | 추출 항목마다, 1~5 | 항목의 모든 문장이 원문에 근거하는가. 근거 없는 문장은 그대로 옮겨 적는다 | 5 = 전부 원문에 있음 / 3 = 과장·추측·다른 맥락의 내용이 섞임 / 1 = 핵심 내용이 원문과 다름 | 충실성 평균, 원문 근거 없는 주장 목록 |
| ④ 카드 요약 적합성 | 추출 항목마다, 1~5 | 검색 카드에 보이는 첫 줄(문제 상황(있으면)·해결 방법·성능·운영 포인트(있으면))만 읽고 이 항목을 고를 수 있는가 | 5 = 문제와 최종 해결책(팁 글은 요지)을 구체적으로 담음 / 3 = 막연하거나 최종 해결책이 아닌 중간 단계·배경 / 1 = 무엇을 했는지 알 수 없음 | 카드 요약 점수 |
| ⑤ 버린 대안 | 추출한 버린 대안마다 | 정답의 어느 대안과 같은지(없으면 빈 값), 원문에 "검토했거나 쓰다가 이런 이유로 안 썼다"가 명시돼 있는지 | 언급만 되거나 추출기가 추측한 대안이면 근거 없음 | 버린 대안 정밀도·재현율, 정답에 없는 대안 중 원문 근거가 없는 비율 |
| ⑥ 분할 적절성 | 글마다, 1~5 | 항목을 나눈 방식이 기준에 맞는가 | 기준: 독립된 문제-해법마다 항목 하나, 같은 문제의 단계적 해결은 한 항목, 팁 모음·도구 활용 경험 글은 항목 하나. 정답과 항목 수가 달라도 기준에 맞으면 높게. 5 = 기준에 맞음 / 3 = 곁가지를 항목으로 만들거나 독립된 문제를 합침 / 1 = 핵심 내용이 빠지거나 뒤섞임. 정답이 제외이고 추출을 허용하지 않은 글에서 추출했으면 1 | 분할 점수 |

판정마다 한국어 한두 문장의 이유(`reason`)를 함께 받아, 점수가 이상할 때 근거를 확인할 수 있게 한다.

### 판정을 지표로 바꾸는 방식

- **완결성**: 정답 항목이 있는 글마다 (핵심 사실 점수 합 ÷ 핵심 사실 수)를 내고 글 평균을 낸다. 정답은 추출인데 추출 결과가 제외면 0%로 넣는다.
- **문제 유형·도메인**: 다중 선택이라 ①에서 대응된 쌍마다 집합으로 비교한다. 판정은 코드가 하고, 어느 쌍을 비교할지만 ①을 쓴다.
  - 정밀도 = 추출한 값 중 정답(꼭 들어갈 값 + 허용 값)에 드는 비율
  - 재현율 = 정답의 꼭 들어갈 값 중 추출에 들어간 비율
- **버린 대안**: 정밀도 = 정답 대안과 대응된 추출 대안 수 ÷ 추출 대안 수, 재현율 = 대응된 정답 대안 수 ÷ 정답 대안 수. 채점 모델이 정답 이름을 "이름 (유형)" 형식으로 돌려줄 때가 있어 유형 표시를 떼고 비교한다.
- **충실성·카드 요약·분할**: 범위를 벗어난 점수는 1~5로 자른 뒤 평균한다.

### LLM에 판정을 맡기면서 지킨 것

- **점수를 통째로 묻지 않는다.** "완결성 몇 점?" 대신 핵심 사실 하나하나가 담겼는지 판정하게 해서 주관이 덜 들어가게 한다.
- **1~5점은 1·3·5점이 무엇인지 문장으로 고정한다.**
- **정답이 기준표다.** 완결성의 기준은 사람이 검수한 핵심 사실이고, 채점 모델이 무엇이 중요한지 정하지 않는다.
- **채점 모델은 추출 후보와 겹치지 않는 상위 모델로 고정한다**(`JUDGE_MODEL = gpt-5.5`, medium). 같은 모델이면 자기 출력을 후하게 볼 위험이 있어 같은 계열을 추출 후보에서 뺐다. 채점 모델을 바꾸면 이전 채점 결과와 직접 비교하지 않는다.

### 캐시와 다시 채점하는 조건

채점 결과는 run 디렉터리의 `judge.jsonl`에 글 단위로 쌓는다. 아래가 모두 같으면 다시 부르지 않는다.

- 채점 모델과 추론 강도
- 채점 프롬프트 버전: 지시문 + 출력 스키마의 SHA-256 앞 12자리
- 입력 해시: 그 글의 정답 + 추출 결과

정답을 검수해 고치면 그 글만, 채점 기준을 고치면 전체가 다시 채점된다. 추출 항목이 없는 글(정답만 있거나 양쪽 다 없음)은 LLM을 부르지 않고 계산으로 처리한다.

## 채점기 검증

사람이 채점 결과를 검수하는 단계는 두지 않고(M3 사용자 결정), Claude Code 세션이 채점 결과를 원문·추출 결과와 대조한다.

- **M3 검증**: v4 채점 6편(핵심 사실 판정 37개, 항목 점수 8개, 분할 6개)을 대조
  - 핵심 사실 판정은 모두 납득 가능했다. 담김/일부 경계에서 다소 엄격한 쪽이다.
  - 충실성 3점 1건은 원문 대조 결과 실제 오류였다. 원문은 ROLLBACK이 스냅샷을 갱신한다고 했는데, 추출은 반대로 썼다.
- **알려진 한계**
  - 분할 점수는 정답의 "나눠도 무방" 메모를 채점기가 보지 못해 다소 엄격하다.
  - 같은 입력을 다시 채점하면 충실성·카드 요약·분할 평균이 0.1~0.2 정도 흔들린다. 작은 차이로는 결론을 내지 않는다.
  - 정답이 24편이라 모델 선택처럼 차이가 큰 결정에 쓰고, 미세 조정의 근거로는 쓰지 않는다.

## 실행

```bash
uv run python eval/judge.py eval/runs/{run} --dry-run                # 채점할 글 수와 예상 비용
uv run python eval/judge.py eval/runs/{run} --workers 4 [--trace]    # 채점 (OPENAI_API_KEY 필요)
uv run python eval/extract_eval.py eval/runs/{run} [eval/runs/{run2} ...]   # 지표 리포트 → eval/reports/eval-*.md
uv run python eval/langsmith_sync.py experiment eval/runs/{run} --gold      # LangSmith Experiment 등록 (채점 결과 재사용)
```
