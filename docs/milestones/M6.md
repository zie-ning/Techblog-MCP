## M4에서 넘어온 항목

- **검색 DB 크기**: 전체 추출 뒤 `data/techblog.sqlite` 8.3MB(1,315개 항목), `data/entries.jsonl` 5.1MB. DB 전달 방법(패키지 포함, Release 다운로드, 설치 시 빌드)을 정할 때 기준 값으로 쓴다. M5 뒤 문서 확장 열이 들어가 DB는 9.3MB, 설치 시 빌드한다면 `data/expansions.jsonl` 1.1MB도 필요하다

## M5에서 넘어온 항목

- **첫 검색 지연**: M5 뒤 첫 `search`가 약 3초(Kiwi 로딩 + 사용자 사전 등록 + 관련도 기준 계산), 이후 검색은 0.05초(Windows, 로컬 측정). 기동 시간을 재고할 때 함께 본다
- **도구 설명 확정**: `search`에서 `limit`이 없어졌고, 설명에 "한 주제의 짧은 명사구로, 여러 하위 주제는 나눠 검색"이 들어갔다. `aggregate` 설명에는 "기술별 집계는 같은 계열을 합친다"가 들어갔다. README 지시문 스니펫과 어긋나지 않게 한다
- **README 안내**: 검색은 단어 일치(뜻으로 찾지 않음)라는 한계와, 결과가 없으면 검색어를 나누거나 표기를 바꿔 다시 찾으라는 안내

## 진행 기록

### 기동 시간과 첫 검색 지연 (2026-10-04, Windows 로컬)

서버를 stdio로 띄워 initialize 응답, 첫 `search`, 다음 `search` 시간을 쟀다. 측정 스크립트는 임시로 쓰고 저장소에 두지 않았다.

**구간별 (같은 프로세스에서 순서대로)**

| 구간 | 시간 | 비고 |
| --- | --- | --- |
| `mcp` import | 1.3~2.0초 | SDK 내부(타입 정의, starlette·uvicorn). 우리 쪽에서 줄이기 어려움 |
| `techblog_mcp.server` import, DB 연결 | 0.1초 | |
| Kiwi 생성 + 사용자 사전 | 0.9~1.5초 | |
| 사용자 사전을 넣은 뒤 첫 분석 | 1.5~2.4초 | 사전을 넣으면 첫 분석에서 추가 준비가 일어남 |
| 이후 검색 | 0.01~0.08초 | |

**변경 전후 (`uv run techblog-mcp`, DB 있음)**

| | initialize | 첫 search | 비고 |
| --- | --- | --- | --- |
| 변경 전 | 1.8~2.1초 | 2.5~3.5초 | 첫 호출 때 Kiwi를 불러와서 언제 검색해도 같음 |
| 변경 후, initialize 직후 검색 | 1.5~1.6초 | 2.5초 | 미리 준비 중이라 기다림 |
| 변경 후, 1초 뒤 검색 | 1.6초 | 1.6~1.8초 | |
| 변경 후, 2초 뒤 검색 | 1.6초 | 0.7~1.0초 | |
| 변경 후, 3초 뒤 검색 | 1.6~1.7초 | 0.02~0.05초 | 세션을 열고 질문을 입력하는 동안 준비가 끝남 |

- 백그라운드 준비가 initialize 응답을 늦추지 않았다.
- `uvx --from <경로>`로 실행하면 initialize가 2.4~2.8초로 `uv run`보다 약 1초 느리다(uvx 환경 확인). 처음 설치할 때는 패키지 설치로 initialize까지 약 14초 걸리지만 한 번뿐이다.
- **첫 실행(DB 다운로드)**: 빈 캐시에서 initialize 직후 검색하면 첫 결과까지 7~13초. 다운로드(9.3MB, GitHub CDN 4~10초, 네트워크에 따라 다름)와 Kiwi 준비를 동시에 해서 둘 중 긴 쪽만큼 걸린다. 한 번뿐이다.
- **검토했지만 쓰지 않은 것**: Kiwi의 다중어 사전을 끄면(`load_multi_dict=False`) 생성 + 첫 분석이 2.5초에서 1.3초로 준다. 하지만 토큰이 달라지는 항목이 생겨(300개 중 5개) 색인 재빌드, `SCHEMA_VERSION` 변경, 검색 평가 재실행, 새 DB 배포가 필요하다. 백그라운드 준비로 이미 첫 질문 전에 끝나는 경우가 대부분이라 쓰지 않았다. 오타 사전 끄기와 `num_workers=0`은 시간 차이가 없었다.
- DB가 없거나 내려받지 못하면 도구 결과로 이유를 알린다. 이 예외는 MCP SDK가 "예상치 못한 오류"로 보고 스택 트레이스를 남기기 때문에 `ToolError`로 바꿔 메시지만 돌려준다.

### 도구 설명 확정과 기술 필터 계열 펼치기 (2026-10-05)

M1 실사용 기록과 실제 결과 형식을 보고 고쳤다. 설명 전문은 `src/techblog_mcp/server.py`가 기준이다.

| 도구 | 추가한 안내 | 근거 |
| --- | --- | --- |
| `get_details` | 본문 줄은 요약, "근거"는 원문 그대로인 문장(검증됨). 원문 표현은 근거 문장으로 인용 | 요약을 원문 표현처럼 인용하지 않게 |
| `get_details` | 원문 전체가 아니라 요약과 짧은 발췌뿐. 결과에 없는 세부는 원문 링크로 안내 | M1 시나리오 1(열지 않은 내용을 자기 지식으로 채움), 저작권 방침 |
| `get_details` | 같은 글의 다른 항목은 질문과 관련 있어 보일 때 이어서 열기 | M1 시나리오 2(관련 항목 case_0025를 열지 않음) |
| `aggregate` | 건수는 8개사 블로그에 글로 쓴 사례 수이지 실제 도입 현황이나 업계 전체가 아님 | 질문 예시가 도입 현황처럼 읽힘. M1 시나리오 4에서는 에이전트가 스스로 한계를 밝힘 |
| `aggregate` | 검색어로는 집계할 수 없고 필터로만 범위를 좁힘. 필터로 표현되지 않는 주제는 `search` | 검색어로 집계하려다 헤매지 않게 |

- **기술 필터 계열 펼치기** (사용자 결정, [기획.md](../기획.md)): "Kafka"로 거르면 하위 기술(Amazon MSK, Kafka Connect, Kafka Streams, ksqlDB)까지 찾아 141건이 된다. 계열 합산 집계(141건)와 같다. 이전에는 132건이라 같은 Kafka인데 숫자가 달랐다. 검색 평가셋 E9(`eval/search_experiments.py e9`, 서버 search 그대로)는 변경 전후 지표가 같았다(기술 필터 질문 Kafka·Iceberg 포함, Recall@5 0.589, MRR 0.920). 처음에는 `eval/search_eval.py`로 재고 "Recall@5 0.615"로 적었는데, 이 스크립트는 관련도 기준을 적용하지 않는 기준선용이라 E9로 다시 쟀다.

### 깨끗한 환경에서 설치·실행 확인 (2026-10-05, Windows)

`feat/m6-release` 브랜치를 push한 뒤, 빈 uv 캐시(`UV_CACHE_DIR`)와 빈 DB 캐시(`TECHBLOG_MCP_CACHE_DIR`)로 README의 설치 명령(`uvx --from git+https://github.com/zie-ning/Techblog-MCP@feat/m6-release techblog-mcp`)을 실행했다. Python은 PC에 있는 3.14를 썼다.

| 실행 | initialize | 첫 search | 시작~첫 결과 |
| --- | --- | --- | --- |
| 1회차 (빈 캐시: 코드 받기, 패키지 35개 설치, DB 다운로드) | 22.1초 | 2.7초 | 24.8초 |
| 2회차 (initialize 직후 검색) | 3.6초 | 2.7초 | 6.2초 |
| 3회차 (3초 뒤 검색) | 3.4초 | 0.02초 | 6.4초 |

- 세 번 모두 "선착순 쿠폰 발급 동시성"에 4건을 돌려줬다. DB는 캐시 폴더에 `techblog-4f980e8d36ef7fb0.sqlite`로 받아졌다.
- **Windows 경로 길이**: 처음에는 uv 캐시를 140자 정도 되는 긴 임시 경로에 두어, 가장 긴 저장소 파일(`eval/reports/compare-…`, 98자)을 checkout할 때 `Filename too long`으로 설치가 실패했다. 기본 uv 캐시 경로(`%LOCALAPPDATA%\uv\cache\git-v0\checkouts\…`, 약 80자)에서는 178자라 문제없다. 대처법(`git config --global core.longpaths true`)을 README 문제 해결에 넣었다.
- **업데이트**: `uv cache clean techblog-mcp` 후 다시 실행하면 브랜치의 최신 커밋으로 설치됐다. 다만 지우지 않아도 uvx가 실행마다 최신 커밋을 확인한다는 것이 뒤에 드러났다 (아래 "설치 방식 변경").
- **Claude Code 연결**: `claude -p --mcp-config`(설정 파일을 바꾸지 않는 임시 설정)로 이 브랜치를 등록하자 `techblog` 서버가 connected로 연결됐다. CLI 로그인이 만료돼 실제 질문은 보내지 못했다.
- 측정 중 테스트 환경에서만 생긴 문제: 측정 스크립트가 설치 도중 프로세스를 끊어 uv의 Python 설치 폴더가 깨졌고, 테스트용으로 Python 설치 폴더를 바꾼 설정에서 uv가 오류를 냈다. 기본 Python 설정에서는 재현되지 않았다.

### 설치 방식 변경: `uv tool install git+…` (2026-10-05)

깨끗한 환경 확인에서 `uvx --from git+…`의 약점이 드러나 설치 안내를 바꿨다 (사용자 결정, [기획.md](../기획.md#배포-로드맵)).

- **uvx는 git 주소를 실행할 때마다 GitHub를 확인한다.** 캐시를 지우지 않아도 브랜치에 새 커밋을 push하면 다음 실행에 새 커밋이 설치됐다. 같은 이유로 오프라인(프록시 차단으로 재현)에서는 `git fetch`가 실패해 20~30초 뒤 서버가 켜지지 않았다. 커밋 해시로 고정해도, `--offline`을 붙여도 마찬가지였다.
- 같은 PC·온라인에서 3회씩 비교:

| 방식 | initialize | 시작~첫 결과 (바로 검색) | 오프라인 |
| --- | --- | --- | --- |
| `uvx --from git+…` | 5.1~6.3초 | 7.9~9.4초 | 켜지지 않음 |
| `uv tool install git+…` 후 `techblog-mcp` | 2.4~2.6초 | 5.1~5.4초 | 정상 (5.6초) |

- `uv tool install`은 빈 캐시에서 설치에 5.9초가 걸렸다(이미 받은 Python과 일부 패키지 재사용). 설치 기록(`uv-receipt.toml`)에 출처 git 주소와 브랜치가 남고, `uv tool upgrade techblog-mcp`가 이 기록으로 다시 받는다.
- PyPI 전환(`uvx techblog-mcp`)은 M8로 넘겼다 ([M8.md](M8.md#m6에서-넘어온-항목)).

### Claude Code 실제 질문 확인 (2026-10-05)

`uv tool install git+…@feat/m6-release`(커밋 dd005d2)로 설치하고, `claude -p --mcp-config --strict-mcp-config --allowedTools mcp__techblog`로 빈 폴더에서 질문했다. 다른 MCP 서버와 프로젝트 지시문은 없는 상태다.

| 질문 | 도구 호출 | 결과 |
| --- | --- | --- |
| 1. 선착순 쿠폰 발급 기능 설계해줘. 세일 때 동시에 수만 명이 몰려. (M1 시나리오 1) | `search` 3회(하위 주제로 나누고 문제 유형·기술 필터 사용) → `get_details` 4건 | 연 4건(올리브영 2, 토스 1, 네이버페이 1)을 모두 인용했고, 인용한 수치(미발급 162 → 0건, Lua 21% 저하 등)가 결과와 같다. "사례"와 "제 제안"을 나누고 사례의 조건 차이를 짚었다. 직접 사례가 적다고 밝힘 → 통과 |
| 2. 국내 회사들은 메시지 큐로 주로 뭘 써? (M1 시나리오 4) | `aggregate` 3회(메시징 유형의 기술 분포 → Kafka 회사별 → RabbitMQ 회사별) | Kafka 계열 합산(59건, MSK 11 등 내역)과 필터 결과(141건)를 숫자 어긋남 없이 썼다. **"블로그에 글로 쓴 사례의 수이지 실제 도입 현황이나 업계 전체가 아니다"를 밝혔다** (M6에서 추가한 aggregate 설명의 효과). 사례를 열지 않고 짐작한 부분은 짐작이라고 표시 → 통과 |
| 3. 블록체인 스마트 컨트랙트 가스비 최적화는 국내 기업들이 어떻게 해? (DB에 없는 주제) | `search` 5회(표현·언어를 바꿔 재검색, 사전에 없는 기술 필터는 서버가 빼고 알림) | 다섯 번 모두 결과 없음. 국내 사례를 찾지 못했다고 먼저 밝히고, 일반 기법은 "국내 사례가 아니라 일반적으로 알려진 기법"으로 구분 → 통과 |

- 비용은 질문당 $0.12~0.20, 소요 시간은 21~42초였다. 질문마다 첫 호출은 지연 로딩된 도구 정의를 불러오는 `ToolSearch`였다.
- 측정 환경 문제: PowerShell 5.1에서 `claude.exe`로 한국어 인자를 넘기면서 질문 글자가 일부 깨졌다. 에이전트가 "깨진 글자를 복원해 이해했다"고 밝히고 진행했고, 도구에 보낸 검색어는 정상 한국어였다. 서버와는 관계없다.

### 실사용에서 드러난 검색 잡음과 보완 (2026-10-05)

Claude Code 실사용(설계 질문)의 `search` 결과 카드를 확인하니 에이전트가 인용한 4건은 모두 관련 있었지만, 결과 자체에는 무관한 카드가 많았다. 특히 `search("이벤트 트래픽 급증 대기열", problem_type="트래픽 급증 대응")`은 10건 중 관련 있는 것이 1~3건(네이버페이 대기열 등)이었고 나머지는 B마트 출고, 셀프계산대, vLLM 서빙 같은 글이었다.

원인은 두 가지였다.

1. **검색어가 필터 이름을 되풀이함**: 색인 `keywords` 열에 문제 유형 이름이 들어 있어 필터를 건 후보 74건이 모두 "트래픽", "급증"을 가진다. 검색어 5단위(이벤트·트래픽·급증·대기·열) 중 2단위가 자동으로 맞아 IDF 50% 기준이 무력해졌다(32건 통과).
2. **"대기열"이 `대기` + `열`로 잘림**: 색인에 "대기열" 토큰이 없어 주제 단어가 힘을 잃는다.

보완 (사용자 결정, [기획.md](../기획.md)):

- **관련도 계산에서 필터 이름과 겹치는 단위 제외** (`query._without_filter_terms`): 문제 유형·도메인·기술(계열 포함) 필터 이름의 토큰과 겹치는 검색어 단위는 기준 계산에서 뺀다. 다 빠지면 원래 단위로 잰다. 위 검색은 32건 → 8건.
- **`search` 설명에 안내 추가**: 필터로 지정한 조건은 검색어에 다시 쓰지 말고 그 안에서 찾을 주제만 쓸 것 (예: problem_type="트래픽 급증 대응"이면 query="이벤트 대기열").
- E9(서버 search 그대로) 비교: 원래 검색어 Recall@5 0.589 · MRR 0.920 · 없는 주제 100%는 그대로, 무관 비율 30% → 29%. 재작성 흉내 Recall@5 0.623 → 0.631, 원래 + 재작성 0.627 → 0.635(Recall@10은 0.677 → 0.672).
- 남은 8건도 대부분 무관하다. "대기열" 분리(원인 2)는 사용자 사전 추가와 새 DB 배포가 필요해 [M7](M7.md#m6에서-넘어온-항목)로 넘겼다. 임베딩은 M5 실험에서 무관 비율을 줄이지 못해(OpenAI large 하이브리드 + 기준도 30%) 이 문제의 해결책으로 보지 않았다.
