# M10. 검색 개편 (임베딩·리랭커)

> 상태: **진행 중** · 직무 근거: AI · 허브: [docs/README.md](../README.md)

M5에서 임베딩 없이 시작한 검색을 다시 설계한다. 목표는 두 가지다.

- 뜻이 같은데 표현이 다른 글도 찾는다 (느린 쿼리 ↔ 슬로우 쿼리, 서킷브레이커 ↔ Circuitbreaker)
- 글이 늘어도 사람이 관리할 목록(동의어 사전, 사용자 사전) 없이 같은 방식으로 동작한다

## 작업

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| 0 | 현재 `search`가 정답을 놓치는 이유 진단 (R0) | ✅ |
| 1 | 리랭커 점수로 "관련 / 결과 없음"을 가를 수 있는지 확인 (R1) | ✅ |
| 2 | 평가셋 보강: 표현이 다른 질문, 비슷하지만 다른 주제(근접 주제) 질문, 미판정 항목 판정 | ✅ |
| 3 | 임베딩·리랭커 API 모델 비교 (품질, 응답 시간, 비용) | ✅ voyage-4-large + rerank-3 |
| 4 | 결합 방식과 판정 기준 확정 | 🔄 |
| 5 | 서버 통합(파이프라인 임베딩, DB 스키마, `search` 교체)과 문서 반영 | ⏳ |

## 완료 기준

보강한 평가셋에서 현재 서버(M5 E9)보다 Recall@5가 높고, 없는 주제의 "결과 없음" 판정을 유지(또는 사용자가 정한 수준 이상)하는 `search`를 서버에 반영

## 결정

- 2026-10-13: **방향** (사용자 결정): 후보는 BM25 + 임베딩 하이브리드로 넓게 찾고, 통과 판정은 리랭커로 한다(현재 IDF 일치 50% 기준을 대체). 질의 쪽 동의어 사전을 넓히는 방법은 글이 늘수록 관리할 단어가 끝없이 늘어 한계가 있다는 사용자 의견으로 주 방향에서 뺐다. BM25는 정확한 용어(Kafka, 아웃박스, 픽스처)를 찾는 역할로 남긴다
- 2026-10-13: **API 사용** (사용자 결정): 임베딩·리랭커는 로컬 모델이 아니라 API로 쓴다. 대형 서비스가 아니라 API가 간단하다는 판단이다. 사용자마다 API 키가 필요한 문제는 일단 고려하지 않는다(보류, 아래 "열린 결정")
- 2026-10-13: **리랭커 비교 대상** (추천 수락): Cohere(`rerank-v4.0-pro`·`-fast`)와 Voyage(`rerank-3`). Voyage `rerank-2.5`는 무료 토큰이 없을 수 있어(가격 페이지 표기가 엇갈림) 비용이 생기지 않도록 뺐다. Jina(`jina-reranker-v3.5`)는 후보 목록 전체를 한 번에 보고 점수를 매기는 방식(listwise)이라 절대 기준선으로 판정하는 용도와 맞지 않을 수 있고, API 가격·한국어 지원을 확인하지 못해 뺐다. OpenAI는 리랭커 API가 없다
- 2026-10-13: **모델 선택** (사용자 결정): 임베딩은 Voyage `voyage-4-large`, 리랭커는 Voyage `rerank-3`. 판정 품질은 Cohere v4 pro가 조금 앞섰지만(2단 판정 Recall@5 0.792 vs 0.757) 평가셋 크기상 확실하지 않은 차이이고, Voyage 하나로 통일하면 키가 하나이고 더 싸고(검색당 약 $0.0015) 빠르다(약 1초). 근거는 아래 3단계
- 2026-10-13: **추출 모델은 바꾸지 않음** (논의): Cohere 요약 기능 도입을 검토했다. 요약 전용 엔드포인트는 2025-09에 지원 종료됐고, 우리 추출은 요약이 아니라 분류·필드 구조화·발췌 검증이라 형식을 잘 따르는 범용 LLM이 맞다. 재추출하면 항목 ID가 바뀌어 검색 평가셋 판정이 모두 무효가 되므로 검색 개편 중에는 추출을 건드리지 않는다. 필요하면 개편 뒤 M3 정답셋으로 비교한다

## 진행 기록

### 0단계: 현재 search 진단 (2026-10-13)

[eval/search_diagnose.py](../../eval/search_diagnose.py), 리포트 [m10-r0-diagnosis.md](../../eval/reports/m10-r0-diagnosis.md). 평가셋의 정답(`관련`) 221건이 현재 서버 결과(최대 10건)에 드는지와, 빠졌다면 이유를 나눴다.

| 결과 | 정답 수 | 비율 | 그중 임베딩 10위 안 | 30위 안 |
| --- | --- | --- | --- | --- |
| 서버 결과에 듦 | 99 | 45% | | |
| 검색어 토큰이 하나도 없음 | 3 | 1% | 0 | 0 |
| **IDF 일치 기준에서 잘림** | **75** | **34%** | 28 | 32 |
| 기준 통과, 10위 밖 (정답이 많은 넓은 주제) | 44 | 20% | 16 | 16 |

- 단어가 아예 안 겹치는 정답은 거의 없다. 대부분 **일부 단어만 다르게 써서** 관련도 기준에 잘린다. 드문 단어일수록 IDF 비중이 큰데, 주제를 정하는 드문 단어일수록 글마다 표현이 달라 가장 중요한 단어가 가장 쉽게 어긋난다
  - "느린 조회 쿼리 개선과 인덱스 설계" → "슬로우 쿼리 해결기: 함수형 인덱스로…" 일치 37% (느리·조회가 없음)
  - "외부 시스템 연동 장애 전파 차단 서킷브레이커" → "Circuitbreaker를 사용한 장애 전파 방지"
  - "데이터 레이크 테이블 포맷 도입과 운영" → "로그 유형별 Iceberg 테이블 적재 및 운영 전략"
- **형태소 분리 문제**: "조회"가 `조` + `회`로 잘린다. 드문 조각이라 IDF가 커서(4.4, 4.9) 정답이 기준에서 크게 손해를 본다. 사용자 사전으로 막는 방식은 사전 관리가 끝없이 늘어나는 같은 문제가 있다
- **코사인으로는 "결과 없음"을 가를 수 없다**: 질문별 임베딩 1위 코사인이 없는 주제(COBOL 0.529, Elixir 0.452)와 정답 있는 질문(아웃박스 0.356, 서킷브레이커 0.398)에서 뒤섞인다. COBOL 질문의 1위는 "PL/SQL → Java 이관", "20년 레거시 재개발" 글이다. 임베딩은 문장 전체 뜻을 점 하나로 만들어 "레거시를 자바로 옮김"이 겹치면 가깝게 보고, COBOL이라는 핵심 조건이 맞는지는 따로 보지 않는다. M5 E6에서 "IDF 기준 통과 또는 코사인 0.6 이상"이 Recall@5 0.595에 그친 이유다
- 같은 캐시로 순위만 비교하면(기준 없음, 상위 10건) BM25 0.615, 임베딩 0.695, **BM25 + 임베딩 RRF 0.791**이다. 상위 10건 안의 정답 중 BM25만 찾은 것이 33건, 임베딩만 찾은 것이 36건으로, 둘은 서로 다른 정답을 찾는다. BM25만 찾은 정답은 Kafka 멱등성·아웃박스·픽스처처럼 구체적인 용어가 핵심인 질문에 몰려 있다

결론: 개편의 핵심은 임베딩 추가보다 **통과 판정을 다시 설계하는 것**이다. 임베딩은 순위에는 강하지만 판정에는 약하다.

### 1단계: 리랭커 판정 가능성 R1 (2026-10-13)

[eval/search_rerank.py](../../eval/search_rerank.py), 리포트 [m10-r1-rerank.md](../../eval/reports/m10-r1-rerank.md).

**설정**

- 후보: 질문마다 BM25(서버 가중치, 필터 적용)와 OpenAI `text-embedding-3-large` 상위 50건씩을 RRF로 합친 상위 50건
- 리랭커 입력: 항목의 제목 + 문제 상황 + 해결 방법 + 성능·운영 + 기술 (M5 임베딩 입력과 같은 텍스트, 항목당 평균 약 535토큰). 원문은 배포하지 않으므로 서버가 가진 항목 정보만 쓴다
- 보는 것: ① 질문별 1위 점수로 정답 있는 질문과 없는 주제 질문이 기준선 하나로 갈리는가 ② 후보 점수와 판정 라벨의 일치(AUC) ③ 리랭커 순위 + 기준선을 서버로 쓴다고 볼 때의 M5 지표
- Voyage는 결제 수단을 등록하지 않으면 분당 3회·1만 토큰으로 제한되는데, 요청 한 번이 약 3만 토큰이라 처음에는 호출할 수 없었다. 사용자가 결제 수단을 등록한 뒤 돌렸다(무료 2억 토큰 안에서 사용, 약 100만 토큰)

**1위 점수로 가르기** (정답 있는 질문 25개, 없는 주제 5개)

| 설정 | 정답 있는 질문 최저 | 없는 주제 최고 | 겹침 | 최적 기준선 | 결과 돌려줌 | 결과 없음 |
| --- | --- | --- | --- | --- | --- | --- |
| 코사인 (OpenAI large) | 0.356 | 0.529 | 13 | 0.396 | 24/25 | 3/5 |
| **Cohere v4 pro** | 0.529 | 0.717 | **1** | 0.781 | 24/25 | **5/5** |
| Cohere v4 fast | 0.439 | 0.539 | 2 | 0.415 | 25/25 | 3/5 |
| **Voyage rerank-3** | 0.436 | 0.629 | **1** | 0.651 | 24/25 | **5/5** |

겹침은 없는 주제의 최고 1위 점수보다 낮은 정답 있는 질문 수다. 코사인은 13개가 겹치지만 Cohere v4 pro와 Voyage rerank-3는 1개(m03)뿐이다.

**응답 시간** (후보 50건 한 번, 질문 5개 평균, 네트워크 포함): 두 번 잰 값이 실행마다 달랐다. Cohere v4 pro 1.36~1.83초, Cohere v4 fast 0.88~1.47초, Voyage rerank-3 0.96초(최대 1.23초). Cohere는 체험 키 기준이다

**비용** (검색 1회 = 후보 50건): Voyage rerank-3는 100만 토큰당 $0.05라 약 3만 토큰이면 검색당 약 $0.0015. Cohere는 검색 단위(질의 1개 + 문서 최대 100개) 과금이고 공식 단가는 확인하지 못했다(중개 사이트 기준 약 $0.0025). 문서가 질의 포함 500토큰을 넘으면 나눠 세므로 항목이 긴 경우 더 나올 수 있다

**관찰**

- **Cohere v4 pro는 기준선 하나로 결과 없음을 가를 수 있어 보인다.** 0.78 기준에서 현재 서버보다 Recall@5 +0.13, 무관 비율 29% → 19%이고 없는 주제는 모두 결과 없음이다. 기준 없이 순위만 매겨도 MRR 1.000(모든 질문의 1위가 정답)이다
- 겹친 1개는 m03(WebRTC TURN 서버 설계)이다. 정답으로 판정된 항목(LINE Planet으로 그룹 영상 통화 구축)이 TURN 서버를 직접 설계한 글이 아니라 0.529에 그쳤다. M5 판정이 후했을 수 있다
- **리랭커도 일부 조건만 맞는 글에 높은 점수를 준다.** 없는 주제 a03(IoT 펌웨어 무선 업데이트 배포 전략)의 1위는 일반 서비스의 "카나리·블루-그린 배포 전략" 항목으로 0.717이다. "배포 전략"은 맞고 "IoT 펌웨어"는 다르다. a02(Unity 게임 서버)의 1위 0.587은 SSE·Redis로 게임 상태를 전파한 `일부 관련` 항목이다
- fast는 pro보다 빠르지만 판정력이 떨어진다(겹침 2, 0.41 기준에서 없는 주제 3/5)
- **Voyage rerank-3는 순위는 가장 좋고 판정 여유는 좁다.** AUC 0.925, 기준 없는 Recall@5 0.811로 셋 중 가장 높다. 하지만 정답 있는 질문의 점수가 좁은 범위에 몰려 있어, 없는 주제 최고(a02 0.629)와 다음 정답 있는 질문(m06 0.673)의 간격이 0.04다(Cohere pro는 0.717과 0.846로 0.13). 그래서 결과 없음 100%를 지키는 기준선에서는 정답도 많이 잘려 Recall@5 0.632로 Cohere pro(0.723)보다 낮다
- **두 리랭커가 어려워하는 질문이 다르다.** Cohere pro는 a03(IoT 펌웨어)에 0.717, Voyage는 0.471이다. Voyage는 a02(Unity 게임 서버) 0.629, a04(COBOL) 0.539로 Cohere(0.587, 0.432)보다 높다. 각자 다른 실수를 하므로 둘을 함께 쓰면 판정이 나아질 수 있지만 비용과 응답 시간이 두 배가 된다
- **한계**: 기준선(Cohere 0.78, Voyage 0.65)은 같은 30개 질문으로 고른 값이라 낙관적이다. 기준선 근처의 여유도 크지 않다. 없는 주제가 5개뿐이고 근접 주제(a03 같은 유형)가 적어, 2단계 평가셋 보강 뒤 다시 재야 한다. 리랭커 결과 상위에 미판정 항목이 나왔다(기준 없음 6건, 0.78 이상 2건)

**1단계 결론**: 리랭커 점수로 "결과 없음"을 가르는 방식은 가능성이 있다. 코사인은 정답 있는 질문과 없는 주제가 13개 겹쳤지만 두 리랭커는 1개만 겹쳤다. 어느 리랭커를 쓸지는 기준선 근처 여유가 좁고 평가셋이 작아 지금 정하지 않는다. 2단계에서 근접 주제 질문을 늘린 평가셋으로 3단계에서 다시 비교한다. 이때 두 리랭커를 함께 쓰는 방법도 후보에 넣는다.

### 2단계: 평가셋 보강 (2026-10-13)

1단계의 기준선이 질문 30개(없는 주제 5개)로 고른 값이라 낙관적이고, 리랭커가 약한 "비슷하지만 다른 주제"가 거의 없었다. 리랭커·임베딩을 공정하게 비교하려고 질문 32개를 더했다(총 62개). 질문 성격은 평가셋의 새 필드 `tags`에 적는다.

| 태그 | 수 | 내용 | 예 |
| --- | --- | --- | --- |

**과정**

1. 질문 초안마다 BM25·임베딩 후보를 두 리랭커로 정렬해 상위 글을 보고, 근접 주제는 정말 그 주제가 없는지, 표현 차이는 정답이 있는지 확인했다. "음성 합성 TTS 모델 서빙"은 카카오 Kanana-O 음성 모델 서빙 글이 있어 근접 주제에서 빼고 표현 차이 질문(p13)으로 옮겼다
2. 판정 풀: 62개 질문마다 BM25, 임베딩, RRF, 리랭커(Cohere v4 pro·fast, Voyage rerank-3)별 상위 15건 중 미판정 항목을 모았다(`eval/search_rerank.py --pool`). 새 질문 32개에서 1,105건, 기존 질문에서 리랭커가 새로 올린 67건, 총 1,172건
3. 판정: 판정 기준(eval/search/README.md "판정")을 똑같이 준 Claude 하위 에이전트 6개가 질문 묶음을 나눠 판정했다. 기존 질문은 이미 있는 라벨을 함께 보여 기준을 맞췄다. 사용자 검수 없이 진행한다는 M5 결정을 따른다
4. 검토: 리랭커 점수와 판정이 크게 엇갈린 항목(점수 0.8~0.9 이상인데 무관, 두 리랭커 모두 0.5 미만인데 관련) 11건을 직접 다시 봤다. 단어나 분야만 겹치고 다른 문제를 다룬 글이라 판정을 바꾸지 않았다

**결과**: 평가셋 62개 질문(정답 있는 질문 45개, 없는 주제 17개), 판정 3,269건(관련 293 · 일부 관련 386). 3단계에서 판정 899건을 더 했다(아래). 새 질문의 관련 항목은 질문당 1~9건이고, 근접 주제 12개에는 관련 항목이 없다(일부 관련 1~11건).

**관찰**

- 근접 주제를 고르면서 리랭커가 일부 조건만 맞는 글에 높은 점수를 주는 사례를 더 찾았다. "Snowflake 데이터 웨어하우스 비용 최적화"에 사내 데이터 분석 봇 글이 Cohere 0.88, "스마트 TV 앱 성능 최적화"에 웹뷰 도입 글이 Cohere 0.77이다. 1단계 기준선(0.78)이면 둘 다 결과로 나간다
- 같은 항목이 질문에 따라 다른 등급을 받은 경우가 있다. case_1187(Iceberg 커밋과 Kafka 발행의 부분 성공을 Flink 2PC로 해결)은 p01("DB 저장과 메시지 발행 중 하나만 성공")에서 관련, m09("트랜잭셔널 아웃박스")에서 일부 관련이다. 문제는 같지만 아웃박스 패턴은 아니라서다

**한계**: 판정은 Claude 하위 에이전트가 했고 사람 검수는 없다. 한 묶음(p05~p10)은 입력이 커서 항목 필드를 160~320자에서 잘라 읽었다. 근접 주제의 "없음"은 후보 풀(설정별 상위 15건) 안에서 확인한 것이다.

### 3단계: 임베딩·리랭커 비교 (2026-10-13)

[eval/search_rerank.py](../../eval/search_rerank.py)와 [eval/search_embed.py](../../eval/search_embed.py)(Voyage·Cohere 임베딩 추가). 리포트는 [R3 임베딩](../../eval/reports/m10-r3-embeddings.md), [R2 리랭커(OpenAI large 후보)](../../eval/reports/m10-r2-rerankers.md), [R2 리랭커(voyage-4-large 후보)](../../eval/reports/m10-r2-rerankers-voyage.md).

**추가 판정**: 2단계 판정 풀은 OpenAI large 후보로 만들어, 다른 임베딩 모델이 상위 10건에 올린 항목 19~155건이 미판정이었다(미판정은 정답으로 세지 않아 그 모델이 불리해진다). 임베딩 모델별 단독·RRF 상위 15건과 voyage-4-large 후보의 리랭커 상위 15건 중 미판정 899건을 2단계와 같은 방식(하위 에이전트 6개)으로 판정했다. 판정된 ID가 질문별 후보 풀과 정확히 맞는지, 관련·일부 관련 107건의 이유가 질문과 맞는지, 리랭커 점수가 높은데 무관인 항목이 있는지 확인했다(하위 에이전트들이 임시 파일 이름을 겹쳐 쓴 일이 있어 확인함, 이상 없음). 평가셋은 판정 4,168건(관련 310 · 일부 관련 482)이 됐고, 아래 수치는 모든 설정의 상위 10건에 미판정이 0건인 상태로 쟀다.

**관찰**

- **현재 서버는 근접 주제에 약하다.** 근접 주제 12개 중 결과 없음 판정이 4개(33%)뿐이다. 기존 없는 주제 5개만 볼 때의 100%는 평가셋이 쉬웠던 탓이다. 표현 차이 질문의 Recall@5는 0.434다
- **순위는 리랭커끼리 비슷하다.** 기준 없는 Recall@5가 0.81~0.83이고 MRR은 거의 1이다. 차이는 판정에서 난다
- **항목마다 기준선을 적용하면 재현율을 많이 잃는다.** 결과 없음 판정을 위해 기준선을 올리면 1위가 아닌 정답 항목도 함께 잘린다. Voyage rerank-3는 정답 있는 질문과 없는 주제가 3개만 겹쳐 결과 없음 판정은 잘하지만, 점수가 좁은 범위에 몰려 있어 항목 기준선 0.64에서 Recall@5가 0.629로 떨어진다
- **2단 판정이 낫다.** 1위 점수로 결과 있음/없음만 정하고 항목은 더 낮은 기준선으로 고르면, 같은 결과 없음 판정(94%)에서 Recall@5가 Cohere pro 0.754 → 0.792, Voyage 0.629 → 0.757로 오른다. 항목 기준선을 낮출수록 재현율은 조금 오르고 무관 카드가 는다(Cohere pro 항목 0.10: Recall@5 0.801, 무관 27%)
- **Cohere pro가 판정에서 조금 앞선다.** 2단 판정에서 Voyage보다 Recall@5 +0.035다. 단 놓친 질문이 Snowflake(0.879)처럼 기준선보다 크게 높아 기준선을 올려서는 고칠 수 없다. Voyage는 놓친 질문(0.668)이 기준선 바로 위다
- **Voyage 지시문은 효과가 없다.** AUC가 0.936 → 0.938로 거의 같고 짧은 검색어에서는 오히려 나빠졌다(Recall@5 0.708 → 0.625)
- **두 리랭커 평균은 없는 주제 17개를 모두 거른 유일한 설정이다.** 두 모델이 서로 다른 질문에서 틀려 평균이 둘 다 낮게 만든다. 대신 검색마다 리랭커를 두 번 불러 비용과 응답 시간이 늘고 키가 두 개 필요하다
- 정답 있는 질문 중 1위 점수가 낮아 결과 없음이 된 질문은 m03(WebRTC TURN 서버, 정답 판정이 후했을 수 있음, 1단계 참고)이다

**한계**: 기준선은 같은 평가셋으로 고른 값이라 낙관적이다. 없는 주제 17개 중 1~2개 차이로 결론이 바뀔 수 있다. 판정은 사람 검수 없이 Claude 하위 에이전트가 했다. 응답 시간은 1단계 측정(후보 50건 기준 Cohere pro 1.4~1.8초, Voyage rerank-3 약 1.0초)에 검색어 임베딩 호출이 더해진다.

## 열린 결정

- **판정 방식** (4단계): 2단 판정의 1위·항목 기준선, 재현율과 무관 카드의 절충
- **사용자 API 키**: 서버가 사용자 컴퓨터에서 돌기 때문에 검색마다 임베딩·리랭커를 부르려면 사용자 각자의 키가 필요하다. 키가 없으면 지금 방식으로 대체할지, [M9](M9.md) 원격 서버가 키를 보관할지 정해야 한다. 지금은 보류(사용자 결정)
- **외부 통신 표시**: API를 쓰면 `search`의 `open_world_hint`(외부 통신 없음 표시)를 바꿔야 한다
- **"결과 없음" 판정 수준**: M5의 "없는 주제 결과 없음 100%"를 계속 지킬지, 재현율을 위해 조금 내줄지
- **형태소 분리("조회" → 조 + 회)**: 개편 뒤에도 BM25가 남으므로 고칠지 4단계에서 정한다
