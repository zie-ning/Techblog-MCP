# M5. 검색 평가와 튜닝

> 상태: **진행 중** (브랜치 `feat/m5-search-eval`) · 허브: [docs/README.md](../README.md)

## 작업

- 검색 평가셋 30개 작성 (질문 + 정답 항목)
- Recall@5, MRR 측정 → 검색 필드 가중치 조정, "결과가 적다" 기준 결정
- **`search` 결과 수 결정 구현**: `limit` 파라미터 제거, 관련도 기준을 넘는 항목만 최대 10건 반환 (결정 배경은 [기획.md](../기획.md) "결과 수 결정"). 기준은 아래 관찰 기록과 평가셋 수치로 정함
- **하이브리드 검색 실험(필수)**: 로컬 임베딩 + BM25 결합을 BM25 단독과 비교. 도입 여부는 수치와 설치 부담(패키지 크기, 시작 시간)을 함께 보고 결정. 단어는 겹치지만 뜻이 다른 글(예: "선착순 동시성" 검색에 "멤버십 대량 일괄 발급" 글이 2위)을 구분하는지 확인

## 진행 방식

실행 계획 전문은 [.claude/plans/m5-search-eval.md](../../.claude/plans/m5-search-eval.md)에 있다.

| 항목 | 방식 (사용자 결정) |
| --- | --- |
| 평가셋 질문 | 30개. M1 시나리오·관찰 기록 검색어 약 10개 + 데이터 분포에서 뽑은 질문 약 15개(문제 유형이 고르게) + DB에 없는 주제 약 5개 |
| 정답 판정 | BM25·임베딩 후보를 합친 풀을 Claude가 판정하고 판정 이유를 남긴다. 사용자 검수 없이 진행하고 애매한 질문만 보고 |
| 정답·지표 단위 | 라벨은 항목 단위(관련 / 일부 관련 / 무관), 지표는 항목 단위와 글 단위(같은 글은 하나로 봄)를 함께 계산 |
| 지표 | Recall@5, MRR (보조 Recall@10). 관련도 기준은 통과 결과 수, 무관 항목 비율, 없는 주제의 "결과 없음" 판정률도 봄 |
| 임베딩 후보 | 로컬 경량 ONNX 모델(fastembed)이 도입 후보. OpenAI 임베딩은 품질 기준점으로만 측정 |
| 경계 글 | 평가에서 잡음으로 나오면 M5 안에서 분류 프롬프트를 보강하고 해당 글만 재추출 |
| 평가 기록 | 저장소 스크립트(`eval/search_eval.py`)와 리포트(`eval/reports/m5-*.md`)만 사용, LangSmith는 쓰지 않음 |
| aggregate 넘어온 항목 | 검색 작업을 마친 뒤 M5 마지막에 처리 |

관찰:

- **가중치(E2)**: 조합에 따라 Recall@5가 ±0.03 움직이는 정도다. 질문 하나의 R@5 변화가 평균을 0.008 움직이므로 질문 4개 정도의 차이다
- **형태소(E3)**: 효과는 작지만(+0.008) 문맥에 따라 "동시성"이 `동시`/`동시성`으로 달리 잘리던 불일치(샘플 테스트에서도 재현)와 시그널링·아웃박스 같은 외래어 분리를 없앤다
- **글 묶기(E4)**: 글 단위로 올리면 같은 글의 하위 항목이 상위 10건을 차지해 다른 글이 밀려난다(Recall@10 0.670 → 0.547~0.598). 1위 정확도(MRR)도 떨어진다
- **관련도 기준(E5)**: 상대 점수(①)와 절대 점수(④)로는 없는 주제를 거의 거르지 못한다. IDF 가중 일치 비율(③)만 없는 주제를 걸러낸다. 50%면 없는 주제 5개를 모두 "결과 없음"으로 판정하지만 정답도 일부 잘린다
  - 긴 검색어에 약하다: m10("사내 LLM 직접 서빙 sLLM 자체 호스팅 vs 상용 API 비용")은 0건이 된다. 드문 토큰 상위 k개로만 재는 변형은 더 나빴다("vs", "sllm" 같은 토큰이 상위에 올라옴)
  - 표기 차이에 약하다: d11에서 "제로트러스트"로 물으면 "Zero Trust"로 쓴 글이 잘린다
- **하이브리드(E6)**: MiniLM은 단독으로 BM25보다 크게 나쁘고, 결합해도 기준 없이는 BM25와 비슷하다. IDF 기준과 함께 쓰면(코사인 0.6 이상이면 IDF 기준을 못 넘어도 살림) BM25 + IDF 50% 대비 Recall@5 +0.06, MRR +0.03이고 "결과 없음" 판정은 그대로 100%다. OpenAI large와 결합하면 기준 없이 Recall@5 0.761로 크게 오른다. 품질 좋은 임베딩이면 의미 검색의 효과가 크다는 뜻이다
- **MiniLM 도입 비용** (Windows, 측정): 추가 패키지 약 70MB(onnxruntime 42MB, pillow 15MB, tokenizers 8MB 등. numpy는 kiwipiepy가 이미 씀), 모델 파일 0.22GB를 첫 사용 때 내려받음, import + 모델 로딩 약 5초(첫 검색 때로 미룰 수 있음), 검색어 임베딩 6.6ms. 항목 임베딩은 검색 DB에 넣어야 해서 DB가 약 2MB(384차원 × 1,315개, float32) 늘어난다

## M1에서 넘어온 과제

근거가 된 실사용 테스트 기록은 [M1 사용 피드백](M1.md#사용-피드백)에 있다.

- **관련도 기준**: OR 매칭이라 흔한 단어 하나만 맞아도 후보가 되고 limit까지 채워 무관한 글이 섞임. DB에 없는 주제에서도 "결과 없음" 대신 무관한 카드를 반환(시나리오 6) → 순위 품질뿐 아니라 "없으면 없다고 말한다"는 안전장치를 위해서도 필요
- **형태소 분석 일관성**: "동시성"이 문맥에 따라 `동시`와 `동시성`으로 다르게 잘림. 외래어 기술 용어가 잘못 분리됨("시그널링" → `시그널` + `링`, "아웃박스" → `아웃` + `박스`) → 사용자 사전·토큰 정규화 검토
- **1글 = N사례 구조의 순위 불이익**: 하위 문제별로 나뉜 사례는 검색어가 적게 걸려 관련 글이 무관한 글보다 아래로 감(시나리오 2) → 같은 글의 사례를 묶어 올리는 방식 검토
- **비교 대상이 되는 사례**: 질문과 다른 각도에서 관련 있는 사례(시나리오 5의 case_0030)는 점수가 낮음 → 관련도 기준이 이런 사례를 잘라내지 않는지 확인

## M4에서 넘어온 항목

M4 전체 추출(1,315개 항목) 뒤 검색해 보며 발견한 것. 기록: [M4.md](M4.md)

- **데이터 규모 변화**: M1 관찰 기록은 32개 항목 기준이다. 1,315개에서 BM25 점수 분포와 "걸린 항목 수"가 크게 달라지므로 관련도 기준은 새 데이터로 다시 잰다. 예: "검색 정확도 개선" + 문제 유형 필터에서 걸린 항목이 203건 = 그 유형 전체("개선" 같은 흔한 단어가 모두 걸림)
- **"성능·운영 포인트 있음" 표시의 변별력**: 항목의 96%(1,263/1,315)가 성능·운영 포인트를 가져 `aggregate`에서 거의 항상 건수와 같게 나온다. 표시를 유지할지, 수치가 있는 경우만 세는 등 기준을 바꿀지 검토
- **상위 기술 묶음이 집계에 반영되지 않음**: 메시징 집계에서 Amazon MSK(11건)가 Kafka와 따로 나온다. 사전의 `parent`를 `aggregate`에 반영하는 작업은 기획.md "기술 사전 구조"에서 M4 이후로 미뤄 둔 것
- **완결성·항목 분할**: M3에서 넘어온 과제. 같은 글이 여러 카드로 나오는 영향과 조건·수치가 빠진 카드가 비교에 부족한지 검색 평가셋으로 확인
- **경계 글**: "2025년 1분기 블로그 글 모음", 클라우드 행사 참관기 같은 글이 일부 추출돼 검색 결과에 섞일 수 있음. 평가셋에서 잡음으로 나오면 분류 프롬프트 보강 후보

- 상대 점수는 검색어가 짧고 주제가 좁을 때 잘 작동하지만, 여러 주제를 섞은 긴 검색어에서는 점수가 고르게 퍼져 잡음을 거르지 못한다.

- 흔한 단어("도입", "서버", "설계") 하나만 맞은 글을 거르는 단어 일치 기준이 좁은 주제, 넓은 주제, 없는 주제 모두에 유효해 보인다.
- 에이전트가 문제 유형·도메인·기술 필터를 쓰면 후보가 크게 줄어 잡음이 거의 사라진다.
