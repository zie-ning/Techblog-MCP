# M8. 자동 갱신 파이프라인 (확장)

> 상태: **대기** · 직무 근거: 백엔드 · 허브: [docs/README.md](../README.md)

## 작업

- GitHub Actions 주기 실행, 새 글만 증분 수집·추출
- 실패 재시도와 멱등성 (프롬프트 버전 기록과 `--outdated` 재추출을 기반으로 함)
- 새 DB를 GitHub Release로 자동 배포하고 서버가 새 DB를 확인해 내려받음 (Release 다운로드와 태그·체크섬 고정은 M6에서 구현, `pipeline.release_db`. 기획서 배포 로드맵의 "안정화 + 자동 갱신" 단계)
- 코드를 PyPI 배포로 전환 (아래 "M6에서 넘어온 항목")
- 발췌 검증 실패 항목은 버리지 않고 격리 보관, 탈락률을 지표로 관리하고 급등 시 알림 (모델 변경·블로그 HTML 구조 변경·프롬프트 회귀의 신호)

## M5에서 넘어온 항목

- **문서 확장 단계**: 새 글을 추출한 뒤 `pipeline.expand`로 새 항목의 확장(예상 검색어·다른 표기)을 만든 다음 색인을 빌드해야 한다. 확장이 없는 항목은 다른 표현으로 찾히기 어렵다(빌드는 경고만 내고 진행). 항목당 약 $0.0004

## M6에서 넘어온 항목

근거는 [기획.md](../기획.md#배포-로드맵)와 [M6 진행 기록](M6.md#진행-기록)에 있다.

- **PyPI 전환**: 설치를 `uv tool install git+…`(두 단계, 수동 업데이트)에서 `uvx techblog-mcp`(한 줄 등록, 버전 캐시)로 바꾼다. 할 일:
  - PyPI 계정 준비와 Trusted Publishing 등록 (사용자가 직접)
  - 버전 관리 규칙: 코드나 `db_release.json`이 바뀌면 `pyproject.toml` 버전을 올린다 (패키지 버전 = 코드 + DB 조합)
  - 태그를 push하면 빌드·업로드하는 GitHub Actions 워크플로, TestPyPI로 먼저 확인
  - README 설치 안내를 `uvx techblog-mcp`로 바꾸고, 업데이트는 `uvx techblog-mcp@latest` 안내
  - 확인할 것: uvx가 캐시된 버전으로 오프라인에서 켜지는지 (uv 문서에 명시 없음)
