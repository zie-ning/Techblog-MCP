# M8. 자동 갱신 파이프라인 (확장)

> 상태: **진행 중** · 직무 근거: 백엔드 · 허브: [docs/README.md](../README.md)

## 작업

- GitHub Actions 주기 실행, 새 글만 증분 수집·추출
- 실패 재시도와 멱등성 (프롬프트 버전 기록과 `--outdated` 재추출을 기반으로 함)
- 새 DB를 GitHub Release로 자동 배포하고 서버가 새 DB를 확인해 내려받음 (Release 다운로드와 태그·체크섬 고정은 M6에서 구현, `pipeline.release_db`. 기획서 배포 로드맵의 "안정화 + 자동 갱신" 단계)
- 코드를 PyPI 배포로 전환 (아래 "M6에서 넘어온 항목")
- 발췌 검증 실패 항목은 버리지 않고 격리 보관, 탈락률을 지표로 관리하고 급등 시 알림 (모델 변경·블로그 HTML 구조 변경·프롬프트 회귀의 신호)

## M5에서 넘어온 항목

- **문서 확장 단계**: 새 글을 추출한 뒤 `pipeline.expand`로 새 항목의 확장(예상 검색어·다른 표기)을 만든 다음 색인을 빌드해야 한다. 확장이 없는 항목은 다른 표현으로 찾히기 어렵다(빌드는 경고만 내고 진행). 항목당 약 $0.0004

## M6에서 넘어온 항목

근거는 [기획.md](../기획.md#배포-로드맵)와 [M6 진행 기록](M6.md#진행-기록)에 있다.

- **PyPI 전환**: 설치를 `uv tool install git+…`(두 단계, 수동 업데이트)에서 `uvx techblog-mcp`(한 줄 등록, 버전 캐시)로 바꾼다. 할 일:
  - PyPI 계정 준비와 Trusted Publishing 등록 (사용자가 직접)
  - 버전 관리 규칙: 코드나 `db_release.json`이 바뀌면 `pyproject.toml` 버전을 올린다 (패키지 버전 = 코드 + DB 조합)
  - 태그를 push하면 빌드·업로드하는 GitHub Actions 워크플로, TestPyPI로 먼저 확인
  - README 설치 안내를 `uvx techblog-mcp`로 바꾸고, 업데이트는 `uvx techblog-mcp@latest` 안내
  - 확인할 것: uvx가 캐시된 버전으로 오프라인에서 켜지는지 (uv 문서에 명시 없음)

## 완료 기준

사람 개입 없이 새 글이 반영된 DB가 배포됨

## 진행 기록

단계: ① 증분 갱신 명령 → ② 발췌 검증 실패 격리·탈락률 지표 → ③ GitHub Actions 주기 실행·Release 배포 → ④ 서버의 새 DB 확인 → ⑤ PyPI 전환.

### 1단계: 증분 갱신 명령 (2026-10-11)

`uv run python -m pipeline.update`가 새 글만 수집 → 추출 → 문서 확장 → 검색 DB 빌드를 한 번에 한다. 결정 사항(새 글 판단 기준, 블로그별 상한, 부분 실패 처리)은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- 수집기 8곳이 추출 기록이 있는 글(`known`)을 건너뛴다. 목록에 본문이 함께 오는 올리브영·우아한형제들은 공용 함수(`save_feed_posts`)로 같은 기준을 적용한다
- 수집·추출 반복문을 `pipeline/collect/run.py`, `pipeline/extract/run.py`로 옮겨 기존 명령과 갱신 명령이 함께 쓴다
- 블로그별 추출 대상이 상한(기본 30편, `--max-new`)을 넘으면 보류. `--dry-run`은 수집과 추출 대상 확인까지만 하고 LLM을 부르지 않는다
- 종료 코드 0 정상, 2 일부 실패·보류, 1 실행 불가. 3단계 워크플로가 이 값으로 배포 여부와 알림을 정한다
- 테스트: 전체 단계 실행, 원문 캐시를 지운 뒤 재실행 시 LLM 호출 없음과 jsonl 바이트 동일(멱등), 새 글만 추가, 실패한 글 다음 실행 재시도, 상한 보류와 해제, dry-run

실제 블로그로 `--dry-run`을 실행한 결과 (2026-10-11): 새 글 6편(D2·카카오·LY·올리브영·우아한형제들·토스 각 1편)을 찾았고, 나머지는 원문을 다시 받지 않았다.

- **토스 수집 실패를 고침**: langsmith가 끌어오는 `zstandard`가 설치돼 있으면 httpx가 zstd 압축도 받겠다고 알리는데, 토스 API의 zstd 응답을 httpx 0.28.1이 풀지 못했다(`DecodingError`). 이번 변경과 무관하게 기존 수집에도 있던 문제라 공통 클라이언트가 gzip·deflate만 받도록 했다
- 카카오페이는 사이트맵에 날짜가 없어 기간 밖 글 50편을 매번 받아 본 뒤 버린다. 기존 동작이고 요청 간격을 지키므로 그대로 둔다

### 2단계: 발췌 검증 실패 격리와 탈락률 지표 (2026-10-11)

결정 사항(격리 방식, 급등 판단 기준, 급등 시 동작)은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- 발췌 검증이 실패한 포인트를 필드·요약·발췌와 함께 `data/quarantine.jsonl`에 항목 단위로 격리한다(`QuarantineRecord`). 해결 방법이 모두 탈락해 버린 항목도 검증 전 항목 전체를 남긴다. 실패가 없으면 파일을 만들지 않는다
- 글별 기록(`PostRecord`)에 재시도 전 발췌 수·탈락 수(`first_attempt_total`, `first_attempt_dropped`)를 추가했다. 기존 기록은 None
- `pipeline/extract/quality.py`가 이번 실행의 최종·재시도 전 탈락률을 이전 기록과 비교한다. `pipeline.update`는 결과를 출력하고 급등이면 종료 코드 2로 끝낸다(DB는 만든다)
- 기존 데이터 기준: 추출 글 863편의 최종 탈락률 0.64%(79/12,414), 재시도한 글 267편(31%). 블로그별로는 LY가 1.78%로 가장 높다
- 테스트: 격리 기록 내용(통째로 버린 항목·일부 탈락 항목), 재추출 시 격리분 교체, 실패 없으면 파일 없음, 표본 부족 시 판단 안 함, 배수·하한 기준, 재시도 전 기준값 없을 때 하한만, 재추출 글의 기준값 제외, 급등 시 종료 코드 2와 DB 빌드
