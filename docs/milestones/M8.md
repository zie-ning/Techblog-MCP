### 1단계: 증분 갱신 명령 (2026-10-11)

`uv run python -m pipeline.update`가 새 글만 수집 → 추출 → 문서 확장 → 검색 DB 빌드를 한 번에 한다. 결정 사항(새 글 판단 기준, 블로그별 상한, 부분 실패 처리)은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- 수집기 8곳이 추출 기록이 있는 글(`known`)을 건너뛴다. 목록에 본문이 함께 오는 올리브영·우아한형제들은 공용 함수(`save_feed_posts`)로 같은 기준을 적용한다
- 수집·추출 반복문을 `pipeline/collect/run.py`, `pipeline/extract/run.py`로 옮겨 기존 명령과 갱신 명령이 함께 쓴다
- 블로그별 추출 대상이 상한(기본 30편, `--max-new`)을 넘으면 보류. `--dry-run`은 수집과 추출 대상 확인까지만 하고 LLM을 부르지 않는다
- 종료 코드 0 정상, 2 일부 실패·보류, 1 실행 불가. 3단계 워크플로가 이 값으로 배포 여부와 알림을 정한다
- 테스트: 전체 단계 실행, 원문 캐시를 지운 뒤 재실행 시 LLM 호출 없음과 jsonl 바이트 동일(멱등), 새 글만 추가, 실패한 글 다음 실행 재시도, 상한 보류와 해제, dry-run

실제 블로그로 `--dry-run`을 실행한 결과 (2026-10-11): 새 글 6편(D2·카카오·LY·올리브영·우아한형제들·토스 각 1편)을 찾았고, 나머지는 원문을 다시 받지 않았다.

- **토스 수집 실패를 고침**: langsmith가 끌어오는 `zstandard`가 설치돼 있으면 httpx가 zstd 압축도 받겠다고 알리는데, 토스 API의 zstd 응답을 httpx 0.28.1이 풀지 못했다(`DecodingError`). 이번 변경과 무관하게 기존 수집에도 있던 문제라 공통 클라이언트가 gzip·deflate만 받도록 했다
- 카카오페이는 사이트맵에 날짜가 없어 기간 밖 글 50편을 매번 받아 본 뒤 버린다. 기존 동작이고 요청 간격을 지키므로 그대로 둔다

### 2단계: 발췌 검증 실패 격리와 탈락률 지표 (2026-10-11)

결정 사항(격리 방식, 급등 판단 기준, 급등 시 동작)은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- 발췌 검증이 실패한 포인트를 필드·요약·발췌와 함께 `data/quarantine.jsonl`에 항목 단위로 격리한다(`QuarantineRecord`). 해결 방법이 모두 탈락해 버린 항목도 검증 전 항목 전체를 남긴다. 실패가 없으면 파일을 만들지 않는다
- 글별 기록(`PostRecord`)에 재시도 전 발췌 수·탈락 수(`first_attempt_total`, `first_attempt_dropped`)를 추가했다. 기존 기록은 None
- `pipeline/extract/quality.py`가 이번 실행의 최종·재시도 전 탈락률을 이전 기록과 비교한다. `pipeline.update`는 결과를 출력하고 급등이면 종료 코드 2로 끝낸다(DB는 만든다)
- 기존 데이터 기준: 추출 글 863편의 최종 탈락률 0.64%(79/12,414), 재시도한 글 267편(31%). 블로그별로는 LY가 1.78%로 가장 높다
- 테스트: 격리 기록 내용(통째로 버린 항목·일부 탈락 항목), 재추출 시 격리분 교체, 실패 없으면 파일 없음, 표본 부족 시 판단 안 함, 배수·하한 기준, 재시도 전 기준값 없을 때 하한만, 재추출 글의 기준값 제외, 급등 시 종료 코드 2와 DB 빌드

실제 실행 (2026-10-11): `pipeline.update`로 1단계 dry-run에서 찾은 새 글 6편을 추출했다.

- 6편 모두 추출, 항목 9개 추가(1,315 → 1,324), 확장 9개, 호출 15회(약 $0.03). 종료 코드 0
- 최종 탈락률 1/99(1.0%), 재시도 전 4/96(4.2%)로 둘 다 정상. 격리 1건(LY 글의 문제 상황 포인트: 요약은 맞지만 발췌가 "다음과 같은 리스크"라는 도입 문장뿐이고 원문 표기와도 달라 탈락)
- 바로 다시 실행하면 추출·확장 대상 0, `posts.jsonl` 바이트 동일(멱등)
- **고친 것**: 새 선택 필드(재시도 전 탈락 수)가 옛 기록 1,262줄 모두에 `null`로 쓰여 `posts.jsonl` 전체가 바뀌었다. 값이 없는 필드는 쓰지 않도록 바꿔 새 글 6줄만 추가되게 했다
- 검색 DB는 로컬에서만 새로 만들었다. Release 배포와 `db_release.json` 갱신은 3단계에서 자동화한다

### 3단계: GitHub Actions 주기 실행과 Release 배포 (2026-10-11)

결정 사항(실행 주기, main 반영 방식, 알림)은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- `.github/workflows/update.yml`: 매주 월요일 09:00(KST)과 수동 실행. `pipeline.update` → (데이터가 바뀌면) 린트·테스트 → `release_db --upload` → 데이터 브랜치 PR 생성·Merge commit 병합 → (문제가 있으면) `auto-update` 라벨 이슈
- main에서만 실행한다. 다른 브랜치에서 돌리면 데이터 PR에 그 브랜치의 병합 안 된 커밋까지 들어가기 때문이다
- `pipeline.update --summary-file`: 실행 요약(새로 반영한 글, 탈락률, 문제)을 마크다운으로 저장해 PR 본문·커밋 본문·알림 이슈·실행 요약에 쓴다
- `release_db`: 태그를 주지 않으면 `db-YYYY.MM.DD`, 같은 날 이미 있으면 `.2`, `.3`을 붙인다(수동 재실행 대비)
- **고친 것**: 추출 보고서가 저장 전 기록을 담아 요약의 항목 수가 0으로 나왔다. 항목 ID가 채워진 저장본을 담도록 바꿨다
- 필요한 저장소 설정: 시크릿 `OPENAI_API_KEY`, Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests"
- actionlint 통과. 실제 실행 확인은 워크플로가 main에 병합된 뒤 수동 실행으로 한다(`workflow_dispatch`는 기본 브랜치에 있는 워크플로만 실행 가능)

### 4단계: 서버의 새 DB 확인 (2026-10-13)

결정 사항은 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- `release_db --upload`: DB와 함께 버전 정보 파일 `db_release.json`을 올리고 `--latest`로 최신 Release 표시
- `db.cached_db`: 받아 둔 최신 버전과 고정 버전 중 스키마가 맞고 태그가 새 것을 쓴다. 하나도 없으면(첫 실행) 최신을 확인해 받고, 실패하면 고정 버전
- `db.check_for_update`: 하루 한 번(`state.json`의 마지막 확인 시각) `releases/latest/download/db_release.json`을 받아, 스키마가 맞는 새 버전이면 받아 둔다. 지금 쓰는 DB는 지우지 않는다. 환경 변수·저장소 DB를 쓸 때는 확인하지 않는다
- 서버는 기동 때 백그라운드에서 DB를 연 뒤 `check_for_update`를 부른다. 새 DB는 다음 기동부터 쓴다
- 테스트: 첫 실행에 최신 받기, 확인 후 다음 기동부터 새 DB, 하루 한 번 확인, 스키마 다른 최신 무시, 오프라인이면 기존 DB, 코드 업데이트로 고정 버전이 더 새로우면 그것, 환경 변수·저장소 DB면 확인 안 함
- 실제 확인(2026-10-13): 기존 Release `db-2026.10.04`에는 버전 정보 파일이 없어 최신 확인이 404로 실패했다(고정 버전 사용). 이 Release에 `db_release.json`을 올린 뒤, 실제 GitHub에서 최신 확인이 고정 버전과 같은 정보를 돌려주고, 빈 캐시에서 DB를 받아 열고 확인 시각을 기록하는 것까지 확인했다

### 조용한 고장 감지 (2026-10-14, 이슈 #16)

블로그 형식 변경으로 수집기가 오류 없이 빈 결과를 내는 경우를 알린다. 결정 사항과 기준값 근거는 [기획.md](../기획.md#자동-갱신-m8)에 있다.

- `CollectResult.listed_known`: 목록에서 본 글 중 추출 기록이 있는 글 수. `collect_each`와 `save_feed_posts`가 센다
- `pipeline.update`: 이 값이 추출 기록의 90% 미만인 블로그를 "목록 감소"로, 평문 300자 미만인 추출 대상을 "본문 짧음"으로 보고하고 종료 코드 2. 짧은 글은 추출하지 않고 원문 캐시를 지워 다음 실행에서 다시 받는다
- 공백 기간 검사와 블로그별 탈락률 표시는 넣지 않았다(근거는 기획.md)
- 테스트: 새 글 없이 목록이 그대로면 정상, 기존 글이 사라지면 목록 감소, 짧은 본문 보류 후 고친 다음 실행에서 추출, 목록에 없는 기록·기간 밖 글은 세지 않음
