# M3. 파일럿과 추출 평가

> 상태: **진행 중** · 브랜치 `feat/m3-pilot-eval` · 허브: [docs/README.md](../README.md)

## 작업

- 파일럿 80편(블로그당 10편) 추출 → 파서, 글 유형 분류, 분류 목록, 추출 프롬프트 점검 → 분류 목록 조정
- 추출 정답셋 20~30편 작성 (Claude Code 세션 초안 + 직접 검수)
- 평가: 자동 지표(분류 일치율, 발췌 원문 존재율, 원문에 없는 버린 대안 비율) + LLM 채점 + 샘플 직접 검수
- OpenAI 모델 후보 비교
- 아래 "M1에서 넘어온 점검 항목"을 파일럿 결과로 확인하고 프롬프트·스키마에 반영

## 완료 기준

추출 모델 결정, 분류 목록 확정, 평가 결과 기록, 발췌 검증 완화 여부 결정

## 진행 방식

실행 계획 전문은 [.claude/plans/m3-pilot-eval.md](../../.claude/plans/m3-pilot-eval.md)에 있다.

| 항목 | 방식 |
| --- | --- |
| 파일럿 표본 | 블로그마다 시드를 고정해 무작위 10편 (`eval/sample_pilot.py` → `eval/pilot_posts.txt`). 올리브영은 M1 20편 제외 |
| 결과 저장 | 평가용 추출은 `eval/runs/{run}/`에 따로 저장 (`--out-dir`). `data/`는 건드리지 않음 |
| 정답셋 초안 | Claude Code 세션에서 원문을 읽고 작성 → 직접 원문과 대조해 검수. 비교 대상인 OpenAI 모델과 계열이 달라 특정 후보 쪽으로 기울지 않게 함 |
| LLM 채점 | `eval/` 아래 OpenAI API 채점 스크립트. 채점 기준을 프롬프트로 고정해 다시 돌릴 수 있게 하고 일부는 직접 검수 |
| 평가·관측 | LangSmith 도입 (원문 포함 트레이싱, Dataset, Experiment, 사람 검수). 결정과 근거는 [기획.md](../기획.md) "평가·관측 도구" 행 |
| 모델 후보 | 가성비 중심: 기준 `gpt-5-mini`(medium), nano급, mini의 effort 변형, 상위 모델 1개. 이름은 실행 시점 모델 목록으로 확정 |

## 진행 기록

- 2026-09-30: 평가 기반 도구 추가. 추출 CLI에 `all`·`--out-dir`·`--workers`·`--save-drafts`, 글별 기록에 토큰 사용량·검증 전 발췌 수. 파일럿 표본 80편 확정 (평문 1,500자 미만 짧은 글 8편 포함: D2 4, 토스 2, 카카오 1, 올리브영 1)
- 2026-09-30: baseline 추출 (gpt-5-mini medium, 현재 프롬프트, 80편). 실패 0편, 비용 $1.30 (편당 $0.016, 전체 1,262편 추정 $20.5 / Batch $10.2). 리포트: [eval/reports/baseline-gpt-5-mini-medium.md](../../eval/reports/baseline-gpt-5-mini-medium.md)

### baseline 점검 결과 (넘어온 항목별)

| 항목 | 결과 |
| --- | --- |
| 분류 편향 | **확인됨.** 80편 중 사례 62 / 인사이트 2 / 제외 16. 팁 모음("코틀린, 저는 이렇게 쓰고 있습니다" → 사례 4개), 직무 소개("TPM은 어떤 일을 하나요?"), 조직 문화("실패를 장려하는 실험적 문화", "요즘 협업 잘하는 팀") 글이 사례로 분류됨. 회고·문화·행사 글 14편 중 3편이 사례·인사이트로 들어감 |
| 짧은 글 (M2) | **부분적으로 문제.** 1,500자 미만 8편 중 행사·인터뷰·간식 글 4편과 개념 글 1편은 제외로 잘 걸러짐. 그러나 D2 발표 소개 글 3편(842·1,342·796자)은 목차·요약만으로 사례 2개, 인사이트 1개가 만들어짐. 그중 NCrashlytics 글은 제목과 목차 줄을 발췌로 써서 탈락 |
| 주 문제 유형 | "개발 생산성"이 23%로 가장 많고 사내 도구·문화 글이 몰림. 동시성·락, MSA는 0건(표본이 작아 판단 보류). 도메인은 "사내 플랫폼·개발 도구" 40%로 쏠림 |
| technologies 품질 | **확인됨.** 사전에 없는 이름 380종. 클래스·API명(`TransactionSynchronizationManager`, `res.arrayBuffer()`), 일반 개념(DNS, CSS, DB, 클라우드, 방화벽, AI), 사내 명칭(실록봇, 박씨), 버전 표기(`Vite (^6.2.1)`)가 섞임. 실제 기술인데 사전에 없는 이름(Vite, Webpack, Jira, Locust, Iceberg 등)도 많아 사전 보강 필요 |
| 버린 대안 | 사례 93개에 75개. 기술이 아닌 진행 방식("CTO 리허설 순서", "롤백 대신 핫픽스")도 들어가 집계에 잡음. technologies와 겹친 경우는 1건(OpenSearch) |
| 발췌 검증 | 921개 중 25개 탈락(존재율 97%), 재시도 27편. 탈락 25개 중 앞뒤 따옴표만 붙은 것 2개, 떨어진 문장을 이어 붙였고 문장마다 따로 찾으면 모두 원문에 있는 것 약 5개, 일부 문장만 있는 것 약 5개, 표·코드·목록 서식 차이나 바꿔 쓴 것 약 13개 (6단계 실험에서 정밀히 분류) |
| 조건 정보 누락 | 정답셋의 `key_facts`로 측정 예정 (4·5단계) |
| 기술 사전 구조 | 380종을 보면 GPU(MIG, MPS), 빌드 도구(Webpack, Vite, esbuild, Rspack), 검색 엔진·분석기(OpenSearch, Kuromoji, Sudachi)처럼 묶을 분류가 필요해 보임. 3단계에서 결정 |

## M1에서 넘어온 점검 항목

근거가 된 실사용 테스트 기록은 [M1 사용 피드백](M1.md#사용-피드백)에 있다.

- **분류 편향**: 인사이트가 0건. "Redis 꿀팁 모음"도 사례 4개로 쪼개짐 → 분류 프롬프트가 사례 쪽으로 치우침
- **주 문제 유형 오분류**: "대용량 키" 팁(case_0017)이 "인프라·컨테이너", sLLM 구축(case_0008)이 "인프라·컨테이너" (비용 절감이 적절)
- **사례의 조건 정보 누락**: 트래픽 규모, 데이터 규모, 지연 요구 등이 추출에서 빠져 에이전트가 사용자 상황과 비교하려다 빈칸을 추측으로 채움 (시나리오 1, 5). 원문에 있는데 빠진 비율 점검
- **technologies 품질**: LLM이 개념·클래스 이름(`kafkaTemplate`, "관계형 데이터베이스")을 넣음. 버린 대안(Lua 스크립트)이 technologies에도 들어가는 경우가 있음 → 프롬프트 보강
- **발췌 검증 완화 여부**: 서로 다른 섹션의 문장을 한 줄로 이어 붙인 발췌가 탈락해 사례의 핵심 내용(case_0013의 이벤트 기반 캐시 무효화)이 빠진 사례가 시나리오 3에서 확인됨. 문장 단위 검증으로 완화하면 되살아나는 내용(재현율)과 떨어진 문장을 섞어 뜻이 바뀐 발췌가 통과하는 비율(정밀도 손실)을 함께 평가. "떨어진 문장은 따로 인용하라"는 프롬프트 보강도 대안으로 비교. M4 전체 추출 전에 결정
- **기술 사전 구조**: 기술 집계에 모니터링·알림 도구가 메시지 큐와 섞임(시나리오 4) → 기술에 분류(메시지 브로커, 모니터링, DB 등)를 붙일지. Kafka와 Amazon MSK가 별개로 집계됨 → 기술 간 상하 관계를 둘지

## M2에서 넘어온 점검 항목

- **본문이 짧은 글의 분류**: D2 156편 중 약 절반이 사내 발표 영상 소개 글로 평문 1,500자 미만(발표 요약·목차뿐)이고, 카카오·LY·우아한형제들에도 행사 스케치·등록 안내·블로그 개편 공지처럼 수백 자짜리 글이 있다. 파일럿에서 이런 글이 대상 아님으로 잘 걸러지는지, 영상 소개 글의 목차만으로 사례를 지어내지 않는지 확인 ([M2 진행 상황](M2.md#진행-상황))
