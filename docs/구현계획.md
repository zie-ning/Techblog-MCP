# 구현 계획

기획 문서([기획.md](기획.md))를 바탕으로 한 구현 순서와 기술 선택.

## 진행 원칙

- **수직 슬라이스 먼저**: 수집이 가장 쉬운 올리브영 한 곳으로 수집 → 추출 → 검색 → MCP 서버까지 끝까지 연결하고, Claude Code에서 직접 써 본 뒤 나머지 블로그로 확장한다. 설계 문제를 일찍 발견하고 동작하는 데모를 빨리 확보하기 위함.
- **테스트는 핵심 로직 중심**: 발췌 검증, 기술명 정규화, 검색·필터·집계, MCP 도구 응답 형식에 단위 테스트를 둔다. 수집기는 저장해 둔 HTML·JSON 샘플로 파서만 테스트한다. 품질은 평가 스크립트로 본다.
- **MVP 먼저, 확장은 그다음**: M1~M6(MVP)을 끝낸 뒤 확장 마일스톤(M7~M9)을 순서대로 붙인다. 목표 직무(백엔드, AI 엔지니어)별 근거를 보강하기 위한 확장이다.
- **서버와 파이프라인 분리**: 사용자가 설치하는 MCP 서버에는 검색에 필요한 의존성만 둔다. 수집·추출용 의존성(OpenAI SDK, 크롤링 라이브러리 등)은 파이프라인에만 둔다.

## 기술 선택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 패키지 관리 | uv | `uvx --from git+…` 배포와 맞춤 |
| MCP 서버 | 공식 Python MCP SDK 2.x (`MCPServer`, 1.x의 FastMCP) | stdio 방식 |
| 검색 | **SQLite FTS5** + kiwipiepy 형태소 분석 | 색인·검색 양쪽에서 같은 분석기 사용. 필드 가중치는 `bm25()` 인자, 필터·집계는 SQL |
| 추출 | OpenAI API + structured output + Pydantic 스키마 | 모델은 M3 평가 후 결정. M1은 임시 모델 사용 |
| 수집 | httpx + 표준 라이브러리 XML 파서, 본문 평문화는 BeautifulSoup, 블로그별 전용 파서 | 피드 파서·범용 본문 추출기(feedparser, trafilatura)는 필요해지면 도입 |
| 테스트·린트 | pytest, ruff | |

- Python 버전은 kiwipiepy 등 의존성의 지원 범위를 셋업 때 확인해 정한다.
- OpenAI API 키는 사용자가 환경 변수(`OPENAI_API_KEY`)로 직접 설정한다. 저장소에는 넣지 않는다.

## 디렉터리 구조

```
techblog-mcp/
├─ pyproject.toml
├─ src/techblog_mcp/        # 배포되는 MCP 서버 패키지
│   ├─ server.py            #   도구 3개(search, get_details, aggregate) + /techblog prompt
│   ├─ render.py            #   도구 결과를 읽기 쉬운 텍스트로 변환
│   ├─ search/              #   FTS5 검색, 필터, 집계, 형태소 분석, DB 스키마
│   ├─ taxonomy/            #   문제 유형·도메인 정의, 기술 사전 (추출과 서버가 공유, 설치 패키지에 포함)
│   └─ db.py                #   DB 경로 로딩 (나중에 다운로드 방식으로 교체할 지점)
├─ pipeline/                # 수집·추출 (배포 패키지에 포함하지 않음)
│   ├─ collect/             #   블로그별 수집기, 공통 HTTP 클라이언트, 원문 캐시
│   ├─ extract/             #   본문 평문화, 글 유형 분류, 구조화, 발췌 검증, 결과 저장
│   ├─ normalize/           #   기술명 재정규화, 사전에 없는 이름 리포트
│   └─ build_index.py       #   entries.jsonl → SQLite FTS5
├─ data/
│   ├─ raw/                 #   원문 캐시 (git 제외)
│   ├─ posts.jsonl          #   글별 추출 기록 (커밋)
│   ├─ prompt_versions/     #   프롬프트 버전별 전문 스냅샷 (커밋)
│   ├─ entries.jsonl        #   추출 결과 (커밋)
│   └─ techblog.sqlite      #   검색 DB (빌드 산출물, git 제외)
├─ eval/                    # 정답셋, 검색 평가셋, 평가 스크립트
├─ tests/
└─ docs/
```

## 마일스톤

### M0. 셋업

- uv 프로젝트 생성, 위 디렉터리 구조, `.gitignore`(`data/raw/`, `.env` 등), ruff·pytest 설정
- CI: GitHub Actions에서 push·PR마다 테스트와 린트 자동 실행 (GitHub 저장소 연결 후 동작)
- **완료 기준**: `uv run pytest`와 `uv run ruff check`가 통과하는 빈 프로젝트

### M1. 수직 슬라이스 (올리브영)

| 순서 | 작업 | 결과물 |
| --- | --- | --- |
| 1 | 올리브영 피드 수집기, 원문 로컬 캐시, 3년치 필터 | `data/raw/`, 글 메타데이터 |
| 2 | 분류 정의 파일(문제 유형·도메인 초안), 기술 사전 초기 버전 | `taxonomy/` |
| 3 | 추출기: 글 유형 분류 + 사례형·인사이트형 구조화 (Pydantic 스키마, structured output) + 발췌 원문 검증 | `pipeline/extract/` |

#### M1 사용 피드백

도구를 직접 호출해 본 결과 (Claude Code 연결 전):

| 발견 | 조치 |
| --- | --- |
| 재시도한 결과가 첫 결과보다 나빠 캐시 글의 사례가 통째로 사라짐 (발췌 6개 탈락) | 두 시도 중 검증을 통과한 내용이 더 많은 쪽을 쓰고, 버린 발췌를 기록 |
| 떨어진 두 문장을 줄바꿈으로 이어 붙인 발췌가 탈락 | 줄마다 따로 검사 |
| 카드의 해결 방법 줄에 버린 대안(Lua 스크립트)이 나옴 | 프롬프트에서 해결 방법 첫 항목은 최종 채택안으로 명시 → 재추출 후 해소 |
| "Claude 3 Haiku를 버리고 Claude 3.5 Sonnet 사용"이 "Claude를 버림"으로 기록됨 | 버린 대안이 사용 기술과 같은 이름으로 정규화되면 원래 이름 유지 |
| 사전에 없는 기술명 76종 (버전·괄호·AWS 접두어 차이가 대부분) | 사전 보강, 버전 번호·괄호 설명을 떼고 재검색 → 남은 것은 대부분 개념·클래스 이름 |

M3로 넘길 점검 항목:

- 인사이트가 0건. "Redis 꿀팁 모음"도 사례 4개로 쪼개짐 → 분류 프롬프트가 사례 쪽으로 치우침
- LLM이 개념·클래스 이름(`kafkaTemplate`, "관계형 데이터베이스")을 technologies에 넣음 → 프롬프트 보강 필요
- 버린 대안(Lua 스크립트)이 technologies에도 들어가는 경우가 있음
- 검색 순위: "선착순 쿠폰 동시성" 검색에 OAuth 전환 사례가 5위로 섞임 (OR 매칭의 영향, M5에서 튜닝)

### M2. 수집 확장

- 나머지 7개 블로그 수집기
  - 피드: 컬리
  - 사이트맵 + HTML: 카카오페이, LY
  - 사이트맵 + Next.js 스크립트 데이터 파싱: 카카오
  - WordPress 공식 REST API: 우아한형제들
  - 공개 JSON API: 토스(Design 카테고리 제외), D2
- 블로그별 파서 테스트용 샘플 저장
- **완료 기준**: 8곳 약 1,360편의 원문과 발행일 확보, 파서 테스트 통과

### M3. 파일럿과 추출 평가

- 파일럿 80편(블로그당 10편) 추출 → 파서, 글 유형 분류, 분류 목록, 추출 프롬프트 점검 → 분류 목록 조정
- 추출 정답셋 20~30편 작성 (강한 모델 초안 + 직접 검수)
- 평가: 자동 지표(분류 일치율, 발췌 원문 존재율, 원문에 없는 버린 대안 비율) + LLM 채점 + 샘플 직접 검수
- OpenAI 모델 후보 비교
- **완료 기준**: 추출 모델 결정, 분류 목록 확정, 평가 결과 기록

### M4. 전체 추출

- 전체 글 추출 (Batch API 검토), 기술 사전에 없는 이름 리포트 검토 후 사전 보강
- **완료 기준**: `entries.jsonl` 완성, 발췌 검증 실패 항목 처리

### M5. 검색 평가와 튜닝

- 검색 평가셋 30개 작성 (질문 + 정답 항목)
- Recall@5, MRR 측정 → 검색 필드 가중치 조정, "결과가 적다" 기준 결정
- **하이브리드 검색 실험(필수)**: 로컬 임베딩 + BM25 결합을 BM25 단독과 비교. 도입 여부는 수치와 설치 부담(패키지 크기, 시작 시간)을 함께 보고 결정
- **완료 기준**: 평가 수치와 결정 근거 기록

### M6. 마무리와 배포

- `get_details`, `aggregate` 도구 설명 문구 확정
- README: 설치 방법(`uvx --from git+…`), Claude Code·Cursor 설정 예시, 지시문 스니펫
- 블로그별 이용약관 확인
- 깨끗한 환경에서 설치·실행 확인
- **완료 기준**: 다른 PC에서 README만 보고 설치해 사용할 수 있음

## 확장 마일스톤 (MVP 이후)

| 마일스톤 | 직무 근거 | 내용 | 완료 기준 |
| --- | --- | --- | --- |
| **M7. 에이전트 A/B 평가** | AI | 실제 개발 과제 20~30개를 MCP가 있을 때와 없을 때로 에이전트에게 풀게 하고 답변을 채점. 지표 후보: 국내 사례 근거 인용률, 지어낸 사례 수, 규모·트레이드오프 언급 여부, 도구 호출률 | 도구 유무에 따른 차이를 수치로 기록 |
| **M8. 자동 갱신 파이프라인** | 백엔드 | GitHub Actions 주기 실행, 새 글만 증분 수집·추출, 실패 재시도와 멱등성, 데이터를 GitHub Release로 배포하고 서버는 새 DB를 내려받음 (기획서 배포 로드맵의 "안정화 + 자동 갱신" 단계, 코드는 PyPI 배포로 전환) | 사람 개입 없이 새 글이 반영된 DB가 배포됨 |
| **M9. 원격 HTTP 서버** | 백엔드 | stdio는 유지하고 Streamable HTTP 방식을 추가해 클라우드에 배포. 요청 제한, 구조화 로깅, 지연 시간 모니터링 | URL만으로 연결해 쓸 수 있음. 호스팅 방식과 비용은 착수 시 결정 |

- 하이브리드 검색 실험은 M5에 필수 실험으로 포함했다.
- M7은 동작하는 서버만 있으면 되므로 가장 먼저 한다. M9는 M8의 데이터 배포 구조를 재사용하므로 M8 다음에 한다.

## 리스크

| 리스크 | 대응 |
| --- | --- |
| 비공식 API(토스, D2)나 Next.js 페이지 구조 변경 | MVP는 스냅샷이라 한 번만 수집. 원문 캐시를 보존해 재수집 없이 재추출 가능 |
| 추출 결과의 환각 | 발췌 원문 검증으로 자동 검출, 버린 대안은 명시된 경우만 추출 |
| 분류 목록이 실제 데이터와 안 맞음 | M1과 M3 파일럿에서 조기 점검 |
| 에이전트가 도구를 잘 호출하지 않음 | M1에서 실제 사용으로 확인하고 도구 설명 문구 조정. M7에서 호출률 측정 |
| 범위가 커져 완성하지 못함 | MVP(M1~M6)를 먼저 완성하고 확장은 하나씩 붙임. 각 마일스톤이 끝날 때마다 동작하는 상태 유지 |
