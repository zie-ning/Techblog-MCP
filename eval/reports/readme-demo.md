### 답변

#### 선착순 쿠폰 발급 설계

##### 핵심 원칙

문제는 두 가지이고 해법이 서로 다릅니다.

| 문제 | 원인 | 방어 수단 |
|---|---|---|
| **초과 발급** | 재고 확인과 차감 사이에 다른 요청이 끼어듦 (check-then-act) | 원자적 카운터 (Redis INCR / Lua) |
| **중복 발급** | 같은 사용자의 동시 요청, 클라이언트 재시도 | 사용자 단위 멱등 키 + DB 유니크 제약 |

그리고 실제 사례들이 공통으로 쓰는 구조는 **"빠른 저장소로 판정하고, 느린 저장소(DB)에는 비동기로 기록"** 하는 것입니다.

##### 권장 아키텍처

```
클라이언트 → (필요 시 가상 대기실) → API 서버
   1) Redis: 사용자 중복 체크 (SET NX / SADD)
   2) Redis: 수량 원자 차감 (INCR 후 상한 비교)
   3) 성공 시 MQ/Kafka에 발급 메시지 발행 → 즉시 "접수 성공" 응답
        ↓
   발급 워커 (처리량 throttling) → DB INSERT
        (UNIQUE(coupon_id, user_id)로 최종 방어)
```

1. **초과 발급 방지**: 수량 판정은 Redis에서만 합니다. DB 비관적 락은 수만 명 동시 접속에서 커넥션 풀이 고갈되므로 피합니다.
2. **중복 발급 방지**: Redis 키 `coupon:{id}:user:{uid}`를 `SET NX`로 잡아 1차 차단하고, DB의 `UNIQUE(coupon_id, user_id)`가 최종 안전망입니다. Redis가 유실돼도 DB가 막습니다.
3. **DB 보호**: 큐를 두고 Consumer에서 QPS를 제한해 DB가 감당 가능한 속도로만 쓰게 합니다.
4. **멱등성**: 메시지 재처리를 전제로 워커를 만들고, 유니크 제약 위반은 "이미 발급됨"으로 성공 처리합니다.
5. **트래픽 한계 초과 시**: Redis 단일 스레드 처리량보다 요청이 많다면 앞단에 대기열(가상 대기실)을 둡니다.

##### 국내 사례

###### 올리브영: 선착순 쿠폰, 미발급 0%를 향한 여정
출처: [올영세일 선착순 쿠폰, 미발급 0%를 향한 여정](https://oliveyoung.tech/2025-12-15/fcfs-coupon/)

가장 직접적으로 참고할 만한 사례입니다.

- **구조**: 온라인몰에서 Redis로 1차 수량 검사 → MQ → 워커가 2차 검증 후 DB 발급.
- **문제**: 2025년 6월 올영세일에서 평균 약 0.014%가 미발급됐습니다. 사용자는 성공 응답을 받았지만 워커의 2차 검증에서 실패했습니다. 원인은 (a) 1차 검증과 워커 반영 사이의 시간 간극, (b) Redis `GET`과 `INCR`이 분리돼 경합이 생긴 점이었습니다.
- **시도한 해법**:
  - Lua 스크립트로 원자화하면 미발급과 과발급이 0이 됐지만 **처리량이 약 21% 떨어져** 채택하지 않았습니다.
  - 최종 채택한 것은 **이중 카운터**입니다. 요청 수를 세는 `countReq`를 먼저 증가시켜 동시 요청을 차단하고, 통과한 요청만 실제 `count`를 증가시킵니다. 성능 저하는 약 8%였습니다. 여기에 수량 선차감도 함께 적용했습니다.
- **결과**: 부하 테스트(한도 1만 건)에서 개선 전 미발급 162건(1.62%)이 개선 후 0건이 됐고, 9월 실운영에서도 미발급 0건을 확인했습니다.
- **운영 팁**: 기능 플래그로 점진 적용했고, `count`와 `countReq`의 차이를 모니터링해 알람을 걸었습니다.

참고로 이 글은 중복 발급 방지 메커니즘 자체는 자세히 다루지 않았습니다. 쿠폰별·유저별 Redis 키를 쓴다는 정도입니다.

###### 토스: 선착순 포인트 지급
출처: [서버 증설 없이 처리하는 대규모 트래픽](https://toss.tech/article/monitoring-traffic)

쿠폰이 아닌 포인트 사례지만 구조가 같습니다.

- **집계**: Redis INCR로 지급 인원을 세고 상한을 비교합니다.
- **중복 지급 방지**: 같은 유저가 거의 동시에 두 번 요청하는 경우를 막으려고 API 요청 단위로 RedLock 분산 락을 겁니다. 지급 내역은 Redis에 먼저 쌓아 즉시 확인합니다.
- **DB 보호**: Kafka로 비동기 INSERT하고 Consumer에서 throttling으로 최대 QPS를 제한합니다.
- **Redis 부하 완화**: 로컬 캐시에서 먼저 세고 주기적으로 Redis에 반영하는 방법도 소개합니다. 다만 이 방식은 상한을 엄격하게 지키지 못하므로 서비스가 말하는 "선착순"의 정의와 맞는지 먼저 확인하라고 합니다.

###### 가상 대기실 (사례 확인은 제한적)
에스티씨랩의 넷퍼넬 같은 솔루션이 코로나19 백신 예약 등에 쓰인 사례가 있습니다([에스티씨랩 블로그](https://www.stclab.com/blog/surge-traffic-checklist)). 다만 이는 솔루션 업체 자료이고, 우아한형제들·카카오 등의 쿠폰 발급 구현 사례는 검색에서 찾지 못했습니다.

##### 선택 가이드

| 상황 | 추천 |
|---|---|
| 수만 명 동시, 수량 수천~수만 | Redis 원자 차감 + MQ 비동기 + DB 유니크 제약 (위 구조) |
| Redis 처리량도 부족할 만큼 극단적 | 앞단 대기열로 유입량 제어 |
| 정확성이 최우선, 트래픽은 보통 | Lua 스크립트 (올영은 처리량 21% 하락으로 포기했지만, 한 번에 정확히 끝나는 장점은 있음) |
| 상한이 느슨해도 되는 경우 | 로컬 카운트 후 Redis 주기 반영 (토스가 언급한 방식) |

##### 놓치기 쉬운 부분

- **Redis와 DB 정합성**: Redis에서 차감했는데 워커가 실패하면 수량이 새므로, 실패 시 보상(롤백) 로직과 `count` 대 DB 건수 비교 배치가 필요합니다.
- **Redis 장애 대비**: DB 기반 fallback을 준비하되, 성능 저하를 감수해야 합니다. 올영도 이를 고려 사항으로 언급했습니다.
- **응답 의미**: "접수 성공"과 "발급 완료"를 구분하고, 사용자에게 결과를 조회할 수단(폴링/푸시)을 줘야 합니다.
- **부하 테스트**: 올영처럼 한도 N건에 N보다 많은 요청을 쏴서 "정확히 N건, 1인 1매"를 검증하는 시나리오를 먼저 만드세요.

##### 한계 고지

검색에서 확인된 기업 사례는 올리브영과 토스 두 곳이고, 우아한형제들·카카오·쿠팡 등의 쿠폰 발급 전용 글은 찾지 못했습니다. 쿠팡 글은 읽기 트래픽 중심이라 제외했습니다. 그 외 자료는 개인 블로그와 강의 Q&A입니다.

## sonbae를 켠 실행 (두 번째, README와 GIF에 사용)

- `mcp__sonbae__search` {"query": "선착순 쿠폰 발급 동시성"}
- `mcp__sonbae__get_details` {"ids": ["case_1466", "case_0477", "case_1595"]}

### 답변

##### 먼저 결론

수만 명이 몰려도 병목은 대부분 "누가 먼저인가"를 판정하는 한 지점입니다. 설계는 아래 세 가지로 정리됩니다.

1. 수량 판정은 Redis에서 원자적으로 한다.
2. 중복은 `(coupon_id, user_id)` 유니크 제약으로 최종 방어한다.
3. DB 반영은 큐로 비동기화하고, 실패하면 수량을 되돌린다.

##### 국내 사례

**올리브영: 선착순 쿠폰 미발급 0%** ([원문](https://oliveyoung.tech/2025-12-15/fcfs-coupon/))
- 문제: 온라인몰의 Redis 1차 검사를 통과해 성공 응답을 받았는데, MQ를 거친 워커의 2차 검사에서 실패했습니다. Redis의 GET과 INCR이 분리되어 있어 밀리초 단위 동시 요청에서 경합도 있었습니다.
- 해결: 앞단에서 수량을 선차감하고, 실제 발급 수량 키와 별도로 "발급 요청 수량" 키를 두는 이중 카운터를 썼습니다. 워커의 DB 처리가 실패하면 선차감한 수량을 롤백합니다.
- 결과: 부하 테스트에서 제한 수량 10,000건 기준 미발급이 162건에서 0건으로 줄었습니다.
- 버린 대안: Lua 스크립트는 정합성은 해결했지만 약 21% 성능 저하와 단일 스레드 병목, 운영 복잡도 때문에 기각했습니다.

**올리브영: Redis Worker에서 RabbitMQ로** ([원문](https://oliveyoung.tech/2023-09-18/oliveyoung-coupon-rabbit/))
- Redis list를 큐로 쓰던 구조가 세일 기간의 과도한 요청 처리와 기능 확장에 한계가 있어 MQ로 옮겼습니다.
- 같은 회사의 [장애 사례](https://oliveyoung.tech/2025-10-28/coupon-mq-issue/)도 있습니다. 1,500만 건 대량 발급 중 RabbitMQ Classic Queue가 메모리를 과다 점유해 발급이 완전히 멈췄고, Quorum Queue로 전환했습니다. 큐를 쓰면 큐 자체가 새로운 장애 지점이 됩니다.

**토스: 선착순 포인트 지급** ([원문](https://toss.tech/article/monitoring-traffic))
- 중복 지급: 연속 요청 때문에 RedLock으로 API 요청에 분산 락을 걸었습니다.
- 지급 확인: 지급 내역을 Redis에 먼저 기록해 즉시 중복 여부를 판단합니다.
- DB 반영: Kafka로 비동기 처리하고, Consumer에서 Throttling을 걸어 DB Insert QPS를 제어합니다.
- 선착순 제한: Redis `INCR`로 인원을 세고 Cap 도달 여부를 확인합니다. 단시간에 Increment가 몰리면 Redis 스레드가 밀려 CPU가 오르는 문제가 있었고, 로컬 캐시에서 집계해 주기적으로 Redis에 반영하는 방법을 언급했습니다. 이 방식은 엄격한 Cap은 아니라고 글에서도 밝힙니다.

**참고: 카카오페이** ([원문](https://tech.kakaopay.com/post/troubleshooting-logs-as-a-junior-developer/))
- 포인트 중복 지급을 Redis와 Lettuce 기반 분산 스핀 락으로 막았습니다. 락을 못 얻은 요청은 바로 실패시키고, DB 비관적 락은 대안으로 버렸습니다.

##### 제안 (사례와 구분되는 제 의견)

1. **수량 차감**: `DECR`/`INCR` 단일 명령으로 원자적으로 처리하거나, 중복 체크까지 묶어야 하면 Lua를 씁니다. 올리브영은 Lua의 성능 비용 때문에 다른 길을 택했지만, 그건 자체 부하 테스트 결과입니다. 요청 규모가 수만 명 수준이면 Lua를 먼저 측정해 보는 편이 단순합니다.
2. **중복 방지**: Redis `SET`(유저별 키)이나 Lua 안의 `SADD`로 1차 방어하고, DB에는 `UNIQUE(coupon_id, user_id)`를 반드시 둡니다. Redis 판정이 틀려도 DB가 최종 안전망이 됩니다.
3. **응답 계약**: "성공 응답"이 Redis 선차감 시점인지 DB 커밋 시점인지 명확히 정하세요. 올리브영의 문제는 정확히 이 간극에서 생겼습니다. 앞단 선차감이면 실패 시 보상(수량 복구)이 필수입니다.
4. **감시**: 발급 카운터와 DB 실제 건수를 주기적으로 대조하는 알람을 두세요. 올리브영도 두 카운터의 차이를 모니터링합니다.
5. **트래픽 방어**: 이벤트 시작 순간에는 대기열이나 레이트 리밋으로 앞단에서 걸러 두면 Redis와 DB 부담이 줄어듭니다.

##### 사례를 그대로 적용하기 어려운 점

- 올리브영은 이미 RabbitMQ 운영 경험과 인프라가 있었고, 토스는 Kafka 기반이 있었습니다. 처음부터 MQ를 도입할지는 규모와 팀 역량에 따라 다릅니다. 수만 명 수준이면 Redis 판정 후 DB 동기 저장도 충분할 수 있습니다.
- 위 수치는 각사의 부하 테스트나 운영 환경 기준이라 그대로 기대할 수는 없습니다.
- 이 검색은 8개 회사의 기술 블로그(2023-09 이후)에 한정되어 있어, 국내 전체 사례를 대표하지는 않습니다.

기술 스택(Redis 사용 여부, 예상 쿠폰 수량, 응답 지연 허용 범위)을 알려주시면 구체적인 구조와 코드로 이어서 설계해 드릴 수 있습니다.
