## 라벨링 기준

기준은 `docs/기획.md`의 결정(대상 글, 사례형 구조, 버린 대안, 기술명 정규화, 분류 목록 조정 기준)을 따른다.

### 구조화 유형 (`kind`)

| 유형 | 기준 |
| --- | --- |
| 사례 | 구체적인 상황에서 기술적 선택을 내렸고 근거(수치·비교·결과)가 있다 |
| 인사이트 | 문제-해법 쌍은 약하지만 다른 팀이 바로 적용할 기술적 내용이 있다. 여러 팁을 소개하는 글은 근거가 있어도 인사이트 1개 |
| 제외 | 개념·튜토리얼, 회고·조직 문화·협업 방식·직무 소개·행사 후기·채용, 발표 소개·목차만 있는 글 |

- 경계 글은 가장 맞는 유형을 `kind`에, 맞다고 볼 수 있는 다른 유형을 `kind_alternatives`에 넣고 이유를 `notes`에 쓴다.
- 행사·문화 글에 AI 도구나 실무 팁이 일부 나와도 제외한다. 글의 주제가 도구 적용 방법과 결과일 때만 인사이트·사례.

### 사례 나누기

- 독립적인 문제-해법 쌍마다 사례 하나. 같은 문제의 단계적 해결은 한 사례.
- 사소한 곁가지는 사례로 만들지 않는다. 대부분 1~3개.
- 항목 수는 정답과 정확히 같지 않아도 된다. 평가에서는 `summary`로 추출 결과의 사례와 대응시킨다.

### 분류

- 주 문제 유형은 해결의 목적 기준(쓴 기술이 아니라 무엇을 풀었나). 둘 다 말이 되면 `acceptable_problem_types`에 넣는다.
- 도메인은 그 시스템이 속한 서비스 영역. 개발 도구·사내 공통 플랫폼 자체가 대상일 때만 "사내 플랫폼·개발 도구".

### 기술과 버린 대안

- `technologies`: 실제로 쓴 제품·라이브러리·프레임워크·서비스. 기술 사전에 있으면 표준 이름, 없으면 흔히 쓰는 이름. 클래스명·일반 개념·사내 시스템 이름·버전은 넣지 않는다. 검토만 하고 버린 기술은 넣지 않는다.
- `rejected_alternatives`: 글에 "검토했지만 이런 이유로 쓰지 않았다"고 명시된 것만. `기술`(제품 자체) / `설계 방식`(패턴, 구현·설정·운영 방법).

### 핵심 사실 (`key_facts`)

추출 결과에 반드시 담겨야 할 것. 완결성 채점(5단계 LLM 채점)의 기준이 된다.

- 원문에 나온 조건: 트래픽·데이터 규모, 지연·가용성 요구, 기존 인프라·팀 제약
- 적용 결과 수치 (예: 처리 시간 n배 단축)
- 핵심 결정과 그 이유
- 항목당 2~5개. 원문에 수치가 없으면 결정과 이유만.
