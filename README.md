## 웹 검색으로 사례를 찾으면

에이전트에게 "국내 기업 사례 찾아 줘"라고 하면 웹 검색 상위에 걸린 SEO 블로그, 커뮤니티 글, 여러 글을 짜깁기한 요약을 근거로 가져옵니다. sonbae는 **국내 기업 기술 블로그에서만**, **원문에 실제로 있는 근거와 함께** 사례를 찾아 줍니다.

| | 에이전트 + 웹 검색 | 에이전트 + sonbae |
| --- | --- | --- |
| 출처 | SEO 블로그, 커뮤니티 글, 짜깁기 요약이 섞임 | 8개 기업 기술 블로그만 |
| 근거 | 에이전트가 읽은 페이지의 요약 (검증 없음) | 원문 발췌. 원문에 실제로 있는지 코드로 검증 |
| 형태 | 글마다 제각각 | 문제 상황 / 해결 방법 / 성능·운영 포인트 / 버린 대안 |
| 사례가 없을 때 | 검색 결과는 늘 나와서 관련 낮은 글이 섞이기 쉬움 | 관련도 기준에 못 미치면 "결과 없음" |
| 집계 | 어려움 | "메시징 문제에 어떤 기술을 많이 썼나" 같은 기술·문제별 집계 |

개발 과제 35개(과제마다 3회)로 비교했을 때, 웹 검색으로 사례를 찾게 한 에이전트보다 sonbae를 쓴 에이전트의 답변이 105쌍 중 61쌍에서 나았고 24쌍에서 못했습니다. 실무 고려(67승 12패)와 판단 근거(60승 9패)에서 차이가 컸습니다. ([평가 방법과 결과](docs/milestones/M7.md))

### 같은 질문, 두 에이전트

> 선착순 쿠폰 발급 기능을 만들려고 해. 이벤트 시작 순간 수만 명이 몰릴 때 중복 발급과 초과 발급을 막으려면 어떻게 설계해야 할까? 국내 기업들이 실제로 어떻게 풀었는지 사례를 찾아서 참고해 줘.

Claude Code(Sonnet)에 이 질문을 웹 검색만 켜고 한 번, sonbae만 켜고 한 번 물었습니다(2026-10-14, [실행 기록과 전체 답변](eval/reports/readme-demo.md)).

<summary><b>sonbae를 쓴 답변 일부 보기</b></summary>

> **올리브영: 올영세일 선착순 쿠폰** ([원문](https://oliveyoung.tech/2025-12-15/fcfs-coupon/))
> - **구조**: 온라인몰이 Redis로 1차 검증 → RabbitMQ → 워커가 2차 검증과 DB 발급을 하는 비동기 구조입니다.
> - **문제**: 1차 검증을 통과해 "발급 성공"으로 응답했는데, 워커의 2차 검증에서 실패해 미발급이 생겼습니다. 평균 약 0.014%(1만 건당 1.4건) 수준이었지만 응답과 실제 결과가 달라 CS가 발생했습니다. 원인은 1차·2차 검사 사이의 시간 간극과, Redis GET과 INCR이 분리되어 있어 생긴 경합이었습니다.
> - **해결**: 앞단에서 수량을 선차감하고, 실제 발급 수량 키와 별도로 발급 요청 수량 키를 두는 이중 카운터를 조합했습니다. 워커의 DB 처리가 실패하면 선차감한 수량을 롤백합니다.
> - **결과**: 부하 테스트에서 제한 수량 1만 건 기준 미발급이 162건에서 0건으로 줄었고, 운영에서도 적용 4일차부터 0건이었으며 처리량 저하가 없었다고 합니다.
> - **버린 대안**: Lua 스크립트는 정합성은 해결했지만 약 21% 성능 저하와 Redis 단일 스레드 병목 우려로 기각했습니다.
>
> **2. 제안 (위 사례와 구분한 제 의견)**
>
> **핵심 원칙: 판정은 단일 원자 연산으로, DB는 나중에.**
>
> 1. **발급 판정은 Redis에서 원자적으로 처리합니다.**
>    - `INCR` 결과값이 한도 이하이면 통과, 초과면 즉시 탈락시킵니다. 올리브영이 겪은 GET→INCR 분리 경합을 피하려는 것입니다.
>    - 다른 방법으로는 Lua 스크립트(올리브영은 성능 이유로 기각)나 선차감 후 롤백이 있습니다. 직접 부하 테스트로 선택하는 것을 권합니다.
> 2. **중복 발급은 별도로 막습니다.**
>    - `SADD coupon:{id}:users {userId}`의 반환값으로 사용자당 1회를 판정하는 방식을 권합니다.
>    - 최후 방어선으로 DB `UNIQUE(coupon_id, user_id)` 제약을 두십시오. Redis가 유실되거나 장애가 나도 중복은 DB가 막습니다.
>
> (이하 생략)

## 설치

[uv](https://docs.astral.sh/uv/getting-started/installation/)와 [Git](https://git-scm.com/downloads)이 필요합니다. Python은 uv가 알아서 준비합니다.

```bash
uv tool install git+https://github.com/zie-ning/sonbae
claude mcp add --scope user sonbae -- sonbae
```

Claude Code에서 `/mcp`를 입력해 `sonbae`가 연결됐는지 확인하면 끝입니다. 첫 질문 때 검색 DB(약 15MB)를 내려받느라 10초쯤 늦을 수 있습니다.

<summary><b>Cursor·다른 클라이언트에 등록하기</b></summary>

**Cursor**: `~/.cursor/mcp.json`(모든 프로젝트) 또는 프로젝트의 `.cursor/mcp.json`에 추가합니다.

```json
    "sonbae": {
      "command": "sonbae"
    }
  }
}
```

**다른 MCP 클라이언트**: stdio 서버를 지원하면 `sonbae` 명령을 등록하면 됩니다. 클라이언트가 명령을 찾지 못하면 `uv tool dir --bin`이 알려 주는 폴더의 전체 경로(Windows는 `sonbae.exe`)를 쓰세요.

Claude Code의 `--scope user`는 모든 프로젝트에서 쓰는 설정입니다. 지금 프로젝트에서만 쓰려면 빼세요.

<details>
<summary><b>Voyage API 키로 검색 품질 높이기 (권장)</b></summary>

키가 있으면 표현이 달라도 뜻이 같은 사례를 찾고, DB에 없는 주제는 "결과 없음"으로 더 잘 거릅니다(평가셋 기준 상위 5건 안 정답 비율 0.55 → 0.75). 키가 없어도 단어로 찾는 검색은 그대로 됩니다.

1. [Voyage AI 대시보드](https://dashboard.voyageai.com/)에서 가입하고 API keys에서 키를 만듭니다. 계정마다 무료 토큰(2억)이 있고, 검색 한 번에 약 3만 토큰(무료 한도를 넘으면 약 $0.0015)을 씁니다. 결제 수단을 등록하지 않으면 분당 호출이 제한돼 검색이 키 없는 방식으로 대체될 수 있습니다.
2. 등록할 때 `VOYAGE_API_KEY` 환경 변수로 넣습니다.

```bash
claude mcp add --scope user sonbae -e VOYAGE_API_KEY=<키> -- sonbae
```

Cursor는 `"env": { "VOYAGE_API_KEY": "<키>" }`를 서버 설정에 추가합니다.

키를 설정하면 `search`의 검색어와 후보 항목 요약(DB에 있는 요약문)이 Voyage API로 전송됩니다. 대화 내용이나 작업 중인 코드는 보내지 않습니다. Voyage 호출이 실패하거나 8초 넘게 걸리면 단어로 찾는 방식으로 대신 검색하고 결과에 그 사실을 표시합니다.

</details>

## 이렇게 물어보세요

평소처럼 질문하면 에이전트가 알아서 sonbae를 씁니다.

- **설계를 시작하기 전에**: "결제 API 멱등성을 설계하려는데, 국내 기업들은 어떻게 했어?"
- **기술을 고를 때**: "메시지 큐로 Kafka와 RabbitMQ 중 고민 중이야. 실제 도입 사례를 비교해 줘."
- **경향을 볼 때**: "캐싱 문제에 어떤 기술 사례가 많아?"
- **직접 부르기**: `/sonbae 선착순 쿠폰` (Claude Code에서는 `/mcp__sonbae__sonbae`). 사례를 찾아 "참고 사례"와 "제안"으로 나눠 답합니다.

| 도구 | 하는 일 |
| --- | --- |
| `search` | 문제 상황·주제로 사례 검색 (최대 10건). 문제 유형·도메인·기술 필터 |
| `get_details` | 사례의 전체 내용, 필드별 원문 발췌, 원문 링크 (한 번에 5건) |
| `aggregate` | 기술·문제 유형·도메인·회사·버린 대안별 사례 수 |

## 검색 결과는 이렇게 생겼습니다

`search("선착순 쿠폰 중복 발급 방지")`의 실제 결과 중 하나입니다. 에이전트는 이 카드를 보고 필요한 사례를 `get_details`로 열어 원문 발췌까지 확인합니다.

```text
[case_1466] 올리브영 · 2025-12-15 · 동시성·락, 메시징·비동기 처리, 데이터 정합성·트랜잭션 / 커머스·주문·재고
제목: 올영세일 선착순 쿠폰, 미발급 0%를 향한 여정
문제 상황: 2025년 6월 올영세일에서 7일간 대규모 선착순 쿠폰 행사를 운영하는 동안, 발급 성공 응답 후 워커의 2차 유효성 검사가 실패해 쿠폰이 미발급되는 문제가 발생했다.
해결 방법: 발급 수량을 온라인몰 앞단에서 선차감하고, 발급 요청 수량을 별도 Redis 키로 관리하는 이중 카운터 전략을 조합해 최종 적용했다.
성능·운영: 부하 테스트에서 제한 수량 10,000건의 미발급 건수가 162건에서 0건으로 줄었고, 미발급률이 1.62%에서 0%로 개선됐다.
기술: Redis, RabbitMQ
버린 대안: Lua 스크립트 적용
원문: https://oliveyoung.tech/2025-12-15/fcfs-coupon/
```

- **원문 근거를 검증합니다.** 사례의 모든 필드에는 원문 발췌가 붙어 있고, 그 발췌가 원문에 실제로 있는지 코드로 검사했습니다. LLM이 지어낸 내용은 걸러집니다.
- **버린 대안까지 담습니다.** 글에 "이건 검토했지만 쓰지 않았다"가 있으면 함께 정리해, 왜 그 선택을 했는지 볼 수 있습니다.
- **없으면 없다고 합니다.** 관련 사례가 기준에 못 미치면 "결과 없음"을 돌려주고, 에이전트에게 사례를 지어내지 말라고 안내합니다.

## 한계

- 8개 기업 블로그의 2023-09 이후 글만 다룹니다. 그 밖의 주제는 "결과 없음"이 나옵니다.
- 집계는 블로그에 쓴 사례 수입니다. 회사의 실제 기술 도입 현황이나 업계 전체를 대표하지 않습니다.
- Voyage 키가 없으면 단어로 찾기 때문에, 글과 다른 표현으로 물으면 못 찾을 수 있습니다. 결과가 없으면 검색어를 나누거나 다른 표현(한국어/영어 표기 등)으로 다시 찾게 하세요.
- 비슷하지만 다른 주제(예: "스마트 TV 앱 성능"에 모바일 앱 성능 글)가 가끔 결과에 섞입니다.

- **도구 호출 허용**: 세 도구 모두 검색 DB를 읽기만 하므로 "항상 허용"을 골라도 됩니다(`search`는 Voyage 키가 있으면 검색어를 Voyage API로 보냅니다). Claude Code에서는 허용 창에서 "Yes, and don't ask again"을 고르거나, `settings.json`의 `permissions.allow`에 `"mcp__sonbae"`를 넣습니다.

```markdown
## 기술 블로그 사례 참고
동시성, 캐싱, 메시징, 장애 대응, LLM 활용처럼 선택지가 있는 설계를 시작하기 전에
sonbae MCP의 search 도구로 국내 기업 사례를 먼저 확인한다.
검색어는 한 주제의 짧은 명사구로 쓰고, 여러 하위 주제는 나눠서 검색한다.
사례를 인용할 때는 회사명과 원문 링크를 밝히고, 결과에 없는 사례는 만들어내지 않는다.
사례는 참고 자료로 소개하고, 이 프로젝트의 상황과 다른 점을 짚어 내 제안과 구분한다.
```

<details>
<summary><b>업데이트와 문제 해결</b></summary>

- **데이터 갱신**: 매주 월요일 새 글을 반영한 DB를 배포합니다. 서버가 하루 한 번 새 DB가 있는지 확인해 받아 두고 다음 실행부터 씁니다. 코드를 업데이트하지 않아도 새 데이터를 받습니다.
- **서버 업데이트**: `uv tool upgrade sonbae` 후 클라이언트를 다시 시작합니다.
- **삭제**: `uv tool uninstall sonbae`. 검색 DB는 아래 폴더를 지우면 됩니다.
- **검색 DB 위치**: Windows `%LOCALAPPDATA%\sonbae`, macOS `~/Library/Caches/sonbae`, Linux `~/.cache/sonbae`. 내려받은 파일은 체크섬으로 검증하며, 지워도 다음 실행 때 다시 받습니다.
- **환경 변수**: `SONBAE_DB`는 이미 가진 DB 파일 경로를 쓸 때(내려받지 않음), `SONBAE_CACHE_DIR`는 DB를 받을 폴더를 바꿀 때 씁니다.
- **"not on your PATH" 경고 / 클라이언트에서 `sonbae`를 찾지 못함**: `uv tool update-shell`을 실행하고 터미널과 클라이언트를 완전히 다시 시작하거나, 등록할 때 `uv tool dir --bin` 폴더의 전체 경로를 쓰세요.
- **"검색 DB를 내려받지 못했습니다"**: 첫 실행에는 GitHub에 접속할 수 있어야 합니다. 네트워크를 확인하고 다시 질문하면 다시 시도합니다.
- **Windows에서 설치 중 `Filename too long`**: `git config --global core.longpaths true`로 Git의 긴 경로 지원을 켜고 다시 시도하세요.
- **옛 이름(`techblog-mcp`)으로 설치했다면**: `uv tool uninstall techblog-mcp`로 지우고 위 설치·등록을 다시 하세요. 자세한 내용은 [개발 문서](docs/개발.md#옛-이름에서-옮겨-오기)에 있습니다.
- `uvx --from git+…`로 등록하는 방법도 있지만, 켤 때마다 GitHub를 확인해 기동이 2~3초 느리고 오프라인에서는 켜지지 않아 권하지 않습니다.

</details>

## 데이터 출처와 저작권

- 원문의 저작권은 각 회사에 있습니다. 이 저장소와 배포 DB에는 원문 전체가 없고, LLM이 쓴 요약, 필드당 1~2문장의 원문 발췌, 원문 링크만 있습니다. 에이전트가 사례를 소개할 때는 회사명과 원문 링크를 함께 밝히도록 안내합니다.
- 수집할 때는 크롤러임을 밝히는 User-Agent를 쓰고, robots.txt를 지키며, 요청 사이에 간격을 두었습니다.
- **삭제 요청**: 블로그 운영 측에서 자사 글이 포함되지 않기를 원하면 [GitHub 이슈](https://github.com/zie-ning/sonbae/issues)로 알려 주세요. 해당 항목을 배포 DB에서 빼겠습니다.
