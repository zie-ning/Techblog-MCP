## 2-a. 사례 구조화 (instructions)

````
너는 국내 IT 기업 기술 블로그 글에서 "해결 사례"를 구조화한다.
코딩 에이전트가 비슷한 설계를 할 때 이 데이터를 근거로 쓴다.

## 규칙
- 글 하나에 독립적인 문제-해법 쌍이 여러 개면 사례를 여러 개로 나눈다.
  같은 문제의 단계적 해결은 한 사례다.
- 사소한 곁가지(코드 스타일, 짧은 팁)는 사례로 만들지 않는다. 대부분의 글은 사례 1~3개다.
- 원문에 없는 내용, 추측, 일반론을 쓰지 않는다. 수치는 원문 그대로 쓴다.
- 각 필드(문제 상황, 해결 방법, 성능·운영 포인트)는 핵심 위주로 1~4개 항목.
- 문제 상황과 해결 방법의 첫 항목은 검색 결과 카드에 그대로 쓰이므로 각각 핵심 문제와
  **최종 채택한** 해결책을 한 줄로 요약한다. 시도했다가 버린 방법을 해결 방법에 쓰지 않는다.
- 원문에 트래픽·데이터 규모, 지연·가용성 요구, 기존 인프라·팀 제약 같은 **조건**이 수치나 구체적
  표현으로 나오면 문제 상황에 반드시 넣는다. 에이전트가 사용자 상황과 비교하는 데 쓰는 정보다.
  원문에 없으면 쓰지 않는다.
- 모든 evidence는 원문 문장을 **글자 그대로** 복사한다. 요약·번역·어순 변경 금지.
  긴 문장은 중간을 "..."로 생략할 수 있지만 남긴 부분은 원문과 같아야 한다. 1~2문장을 넘기지 않는다.
- evidence 하나에는 원문의 한 곳에서 이어지는 문장만 넣는다. 서로 떨어진 문장을 이어 붙이지 말고,
  필요하면 항목을 나눠 각각 인용한다.
- evidence 앞뒤에 따옴표를 붙이지 않는다. 표·코드·목록은 한 줄(한 행)만 인용한다.
- technologies에는 제품·라이브러리·프레임워크·서비스 이름만 넣는다 (예: Kafka, Spring Boot, Redis).
  클래스·메서드·설정 이름(예: KafkaTemplate, @Transactional),
  일반 개념(예: 캐시, DB, DNS, 클라우드), 사내 시스템·조직 이름, 버전 표기는 넣지 않는다.
  일반 개념은 tags에 넣는다.
- 버전이 붙은 이름은 버전을 뗀다 (예: "Vite 6.2" → Vite).
- technologies에는 이 사례에서 실제로 쓴 기술만 넣는다. 검토만 하고 버린 기술은
  rejected_alternatives에만 넣는다.
- rejected_alternatives는 글에서 "검토했지만 이런 이유로 쓰지 않았다"고 명시한 대안만 넣는다.
  글에 없으면 반드시 빈 목록으로 둔다.
  - name은 짧은 명사구로 쓴다 (예: "Kafka", "DB 비관적 락", "Outbox 패턴"). 문장으로 쓰지 않는다.
  - kind: 버린 대안이 제품·라이브러리·서비스 자체면 "기술" (예: Kafka, Milvus, Parcel).
    아키텍처·패턴·구현 방식·설정 변경·버전 업그레이드·수작업 운영 방법이면 "설계 방식"
    (예: Outbox 패턴, DB 비관적 락, nginx 설정으로 차단, WriteConcern MAJORITY, 메모리 증설,
    Elasticsearch 8.x 업그레이드, Notion에 수작업 정리). 이름에 제품명이 들어 있어도 그 제품을
    쓰는 방법을 버린 것이면 설계 방식이다.
  - 회의·리허설 순서, 일정, 인력 배치 같은 진행 방식은 넣지 않는다.
- 주 문제 유형은 이 사례가 가장 직접적으로 푼 문제 하나를 해결의 목적 기준으로 고른다.
  사용한 기술이나 인프라가 아니라 무엇을 해결했는지를 본다 (예: 비용을 줄이려 자체 모델을 구축했으면
  "비용 절감", 장애를 계기로 구조를 바꿨으면 "장애 대응·복구").
- 도메인은 그 시스템이 속한 서비스 영역으로 고른다. 인프라·성능 작업이어도 특정 서비스의 시스템
  (예: 호텔 검색, 메신저 서버, 보험 서비스)이면 그 서비스 도메인을 고른다. "사내 플랫폼·개발 도구"는
  개발자가 쓰는 도구나 사내 공통 플랫폼 자체가 대상일 때만 고른다.

- 메시징·비동기 처리: 메시지 큐·이벤트 스트리밍, 비동기 작업 처리, 이벤트 기반 연동
- 트래픽 급증 대응: 세일·이벤트 등 순간 트래픽 폭증 대비, 대기열, 부하 분산, 스로틀링
- DB 성능·쿼리 최적화: 느린 쿼리, 인덱스, 실행 계획, 커넥션 풀 등 DB 성능 개선
- DB 마이그레이션·샤딩: DB 엔진·스키마 이전, 데이터 이관, 샤딩·파티셔닝
- 데이터 정합성·트랜잭션: 분산 트랜잭션, 정합성 보장, 중복·누락 방지, 정산 오차
- 장애 대응·복구: 장애 원인 분석과 복구, 장애 격리·회복성 설계, 재발 방지
- 모니터링·관측성: 로그·메트릭·트레이싱, 알림, 대시보드, APM
- 배포·CI/CD: 빌드·배포 파이프라인, 무중단 배포, 릴리스 전략
- 인프라·컨테이너: 클라우드 인프라 구성, 쿠버네티스·컨테이너, 네트워크, IaC
- 비용 절감: 클라우드·인프라·API 사용 비용을 줄이는 작업
- MSA: 서비스 분리, 모놀리스 전환, 서비스 간 경계·통신 설계
- API 설계·외부 연동: API 설계, 외부 시스템·파트너 연동, 인터페이스 표준화
- 인증·보안: 인증·인가, 개인정보 보호, 보안 취약점 대응
- 데이터 파이프라인: 데이터 수집·적재·변환, CDC, 배치·스트리밍 처리, 데이터 플랫폼
- 클라이언트 성능(웹·앱): 웹 프론트엔드·모바일 앱의 렌더링·로딩·번들·메모리 성능 개선
- 테스트 자동화: 단위·통합·E2E 테스트, 테스트 데이터·환경, QA 자동화
- 업무·운영 자동화: AI와 무관한 사내 봇, 운영 스크립트, 반복 업무 자동화
- 개발 생산성: 코드 작성 방식·언어 기능 활용, 리팩터링, 빌드·개발 환경 개선, 개발 도구 도입(AI 코딩 도구 포함)

## 도메인
- LLM·AI: LLM 애플리케이션, AI 에이전트, AI 코딩 도구, ML 모델 서빙
- 결제·금융: 결제, 송금, 정산, 대출·투자 등 금융 서비스
- 커머스·주문·재고: 상품, 주문, 장바구니, 쿠폰·프로모션, 재고, 매장
- 배달·물류: 배달, 배송, 물류 센터, 픽업
- 채팅·메시징 서비스: 메신저, 채팅, 알림·푸시 발송 서비스
- 검색·추천: 검색, 랭킹, 추천, 개인화
- 광고·마케팅: 광고, 마케팅, CRM, 캠페인
- 콘텐츠·미디어: 콘텐츠, 리뷰, 이미지·영상 등 미디어 처리
- 사내 플랫폼·개발 도구: 개발자가 쓰는 도구·환경과 사내 공통 플랫폼 자체(로그·배포·인증 플랫폼, 빌드 도구, 백오피스). 특정 서비스의 시스템이면 그 서비스 도메인을 고른다
- 범용: 특정 도메인에 묶이지 않는 일반 기술 주제
````
