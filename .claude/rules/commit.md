# 커밋 메시지 & 브랜치 규칙

이 문서는 클로드 코드가 이 저장소에서 커밋을 만들거나 브랜치를 딸 때 참고하는 규칙이다.

## 커밋/푸시 승인

**사용자가 명시적으로 지시하기 전까지 절대 push하지 않는다.**

## 브랜치

- `main`에 직접 커밋하지 않는다. 작업마다 최신 `main`에서 브랜치를 따고, PR로 병합한다.
- 브랜치는 **작업 단위**로 만든다. 예: 수집기 하나, 또는 같은 방식의 수집기 묶음 하나. 마일스톤 전체를 한 브랜치에 몰지 않는다.
- 이름은 `<타입>/<요약>` 형식이고 요약은 영어 kebab-case다. 타입은 아래 커밋 타입과 같다.
  예: `feat/kurly-collector`, `fix/evidence-multiline`, `docs/branch-strategy`
- 병합은 PR 규칙(`pull-request.md`)을 따른다.

## 프로세스

1. 스테이지된 파일 확인, 스테이지된 파일이 있으면 해당 파일만 커밋
2. 여러 논리적 변경사항에 대한 diff 분석
3. 필요시 분할 제안

## 커밋 포맷

` <타입>: <설명>`

**타입:**

- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서화
- `style`: 포맷팅
- `refactor`: 코드 리팩토링
- `perf`: 성능 개선
- `test`: 테스트
- `chore`: 빌드/도구
- `ci`: CI 관련 설정 수정에 대한 커밋

**규칙:**

- 명령형 어조 ("추가" not "추가됨")
- 첫 줄 72자 미만
- 본문은 `-` bullet으로 쪼개서 개조식으로 작성
- 원자적 커밋 (단일 목적)
- 관련 없는 변경사항 분할

## 분할 기준

다른 관심사 | 혼합된 타입 | 파일 패턴 | 큰 변경사항

## 참고사항

- 스테이지된 파일이 있으면 해당 파일만 커밋
- 분할 제안을 위한 diff 분석
- **커밋에 Claude 서명 절대 추가하지 않음**
